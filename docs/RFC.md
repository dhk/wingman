# Wingman Engineering RFC

This document records engineering decisions and the reasoning behind them. It answers "why is the codebase built this way," while [`DESIGN.md`](DESIGN.md) answers "what is the system" and [`../ROADMAP.md`](../ROADMAP.md) answers "in what order."

An RFC entry explains the current engineering position and its trade-offs. Entries with durable architectural consequences carry a **Durable decision** marker — a decision point we do not expect to revisit casually.

## How to add an entry

Append a numbered section with: the decision, the alternatives considered, the rationale, and what would cause us to revisit it. Do not delete superseded entries; mark them **Superseded by RFC-NNN** so the reasoning trail survives.

---

## RFC-001: Layered architecture with inward dependencies

**Decision.** Code is organized as `domain` → `application` → `infrastructure`, with `agents`, `tools`, `providers`, `policies`, `evaluation`, `reporting`, and `cli` as peers that depend inward. The domain layer imports no model SDKs, databases, web clients, or frameworks.

**Alternatives.** A flat package (faster to start, degrades quickly as connectors and providers accumulate); a plugin architecture (premature for a single-user local tool).

**Rationale.** Wingman's riskiest dependencies — model providers, connectors, persistence — are the ones most likely to change. Keeping them at the edge means the career-domain logic stays testable without network access and survives provider churn. See RFC-004.

**Revisit if.** The domain layer stays so thin that the layering is pure ceremony after Phase 2.

## RFC-002: Technical baseline

**Decision.** Python 3.12+, `uv` for dependencies and task running, Typer for the CLI, Pydantic for schemas, SQLite for persistence, pytest for tests, Ruff for lint/format, mypy in strict mode.

**Durable decision** — not expected to be revisited casually: private user data is stored locally by default; remote persistence and telemetry require separate explicit decisions. Accepted consequences: local setup is slightly more involved; privacy boundaries are easier to understand; connectors begin read-only; backups and migration need deliberate design. (Folded from former ADR 0001.)

**Alternatives.** Poetry/pip-tools (slower, more lockfile friction than uv); Click or argparse (more boilerplate than Typer for the same result); Postgres or a document store (operational weight a local-first single-user tool does not need).

**Rationale.** Every choice favors a tool that is fast, boring, and widely understood. SQLite in particular keeps the local-first promise trivially true: the user's data is one file on their disk.

**Note — DuckDB evaluated (2026-07), not adopted.** Wingman's workload is transactional (small inserts, point lookups, single-row evidence merges over thousands of rows), the corpus search depends on SQLite FTS5's incremental indexing and `snippet()` (RFC-007), the stdlib dependency footprint is a stated feature, and career data is a decades-horizon archive where SQLite's format stability is the conservative pick — so DuckDB offers no realizable advantage as the system of record. It remains the intended **analytical attachment** if a genuinely columnar workload arrives (the EVALUATION.md model-comparison matrix, Phase 5 prioritization/funnel analytics): DuckDB's `sqlite` scanner queries `wingman.db` in place, so adoption then is a read-side query engine over the existing store, not a migration.

**Revisit if.** Multi-device sync becomes a real requirement (storage), or the CLI grows subcommand complexity Typer handles poorly; for the analytical DuckDB attachment specifically, when a columnar workload (evaluation matrices, Phase 5 analytics) measurably outgrows SQLite queries.

## RFC-003: Deterministic controls, not model judgment

**Decision.** Schema validation, permission enforcement, approval gates, arithmetic scoring, deduplication, status transitions, file routing, and secrets handling are implemented in ordinary code. Models are used only where semantic judgment or language generation adds value.

**Alternatives.** "LLM everywhere" — letting a model validate, route, and score directly.

**Rationale.** The controls that keep Wingman safe (approval before external action, least privilege, provenance) must be auditable and must fail closed. A model cannot guarantee either. Deterministic controls are also free to run, which matters when they gate every operation.

**Revisit if.** Never for safety controls. Individual scoring components may gain model-assessed *inputs*, but aggregation stays deterministic.

## RFC-004: Model routing through capability classes

**Decision.** Application code requests a capability class — `extract_fast`, `synthesize_balanced`, `reason_frontier`, `critic_independent`, `research_websearch` — and configuration maps each class to a concrete provider and model. Model IDs never appear in domain or application code.

**Durable decision** — not expected to be revisited casually: domain and application code depend on internal interfaces, never provider SDKs; provider-specific implementations live under `src/wingman/providers/`. Accepted consequences: tests can use fakes; provider-specific features require explicit adapters; a small abstraction layer is the up-front cost. (Folded from former ADR 0002.)

This entry is the single home for runtime model-routing policy; other documents point here. The mapping from workload to approach:

| Workload | Approach |
|---|---|
| Parsing, validation, deterministic scoring | No model (RFC-003) |
| High-volume extraction and classification | `extract_fast` |
| Routine synthesis and drafting | `synthesize_balanced` |
| Difficult synthesis, high-consequence reasoning | `reason_frontier` |
| Independent critique of candidate artifacts | `critic_independent` |
| Open-web research (#222's person deep-dive, #350's company deep-dive) — the only class whose provider reaches beyond approved/named sources or user-dropped items | `research_websearch` |
| External-action policy checks | No model, deterministic policy engine (RFC-006) |

Build-time tooling (which model writes the code) is a separate concern, owned by [`product/BUILD_PLAN.md`](product/BUILD_PLAN.md) — the one place a concrete build-model name may appear.

**Alternatives.** Direct model IDs at call sites (simple, but every provider change is a code change scattered across the tree); a routing service (overkill locally).

**Rationale.** Model names, prices, and relative strengths change monthly. Capability classes make "swap the extraction model" a one-line config change and make model-comparison benchmarks (see [`EVALUATION.md`](EVALUATION.md)) possible without code churn.

**Revisit if.** The five classes prove to be the wrong granularity in practice.

## RFC-005: Provenance metadata on every influential record

**Decision.** Any record that can influence a recommendation carries: stable ID, source type, source locator, source timestamp when known, ingestion timestamp, content hash where appropriate, transformation history, confidence, a fact/inference/hypothesis classification, and user-override metadata. Conflicting source values are preserved side by side, never silently overwritten.

**Alternatives.** Provenance only on "important" records (the importance judgment is exactly what goes wrong); provenance added later (retrofitting provenance onto existing data is close to impossible).

**Rationale.** Wingman's value proposition is evidence-backed career judgment. A recommendation the user cannot trace to sources is indistinguishable from a hallucination. Provenance from record one is the cheapest point to buy it.

**Revisit if.** Not expected; field-level details may evolve with the schema.

## RFC-006: Human approval gates for all external actions

**Decision.** No email, message, application, calendar write, contact update, or post occurs without explicit approval at the point of action. Dry-run is the default for any future external write, and the confirmation displays the exact effect. Approval logic is deterministic code (RFC-003) in the `policies` layer.

**Alternatives.** Blanket pre-authorization ("approve all outreach this session") — rejected because approval fatigue plus batch authorization is how autonomous-agent horror stories happen.

**Rationale.** The product boundary — decision support, not autonomous action — is Wingman's defining constraint. Enforcing it structurally, rather than by convention, means no future feature can cross it by accident.

**Revisit if.** Never. This is a product invariant, not an engineering preference.

## RFC-007: Corpus retrieval via SQLite FTS5, embeddings deferred

**Decision.** The corpus — the user's writing (Substack posts, READMEs, LinkedIn exports, other documents) — is stored as ordinary SourceRecords plus CorpusDocuments and searched with SQLite's built-in FTS5 full-text index. Ingestion is explicit imports (files, directories, export zips), never live connectors. No vector database and no embedding model in this phase.

**Alternatives.** Embeddings + vector search (semantically stronger, but adds a model dependency to a retrieval path that should be deterministic, plus an index to keep consistent — and AGENTS.md requires a demonstrated need before adding a vector database); a separate search service (operational weight a local single-user tool does not need).

**Rationale.** One person's writing is hundreds of documents, not millions; FTS5 is deterministic, ships inside the stdlib's SQLite, keeps the local-first promise (the index lives in the same wingman.db file), and its failure mode is "no results", never a fabricated match. Retrieval feeds model steps (drafting, assessment) that already validate quotes verbatim, so a keyword-recall index is the right floor.

**Revisit if.** Drafting or assessment measurably misses relevant corpus evidence that semantic search would find — then embeddings become a documented decision with the storage and provider trade-offs written down.

## RFC-008: A local MCP server as the second presentation surface

**Decision.** Wingman exposes its use cases (status, evidence search, career profile, job assessment, resume ingestion) as a stdio MCP server (`wingman-mcp`) for MCP clients running on the same machine — Claude Desktop and Claude Code. The server is a thin presentation layer over the application layer: every tool runs the same deterministic validation pipelines as the CLI, and the connected model cannot bypass evidence rules. The workspace stays on the user's machine (stdio, no network listener), so the local-first invariant is untouched.

**Alternatives.** A REST API + web UI (a bigger surface with auth/TLS obligations, and no consumer today); a remote/hosted MCP server for claude.ai web and mobile (requires a network listener and auth — deferred until wanted, and then it gets its own entry); driving the CLI through a generic shell tool (works, but loses typed inputs and puts the workspace behind an unrestricted shell rather than five narrow tools).

**Rationale.** The primary way this product is actually used is through a Claude conversation. An MCP server turns that from copy-paste into typed tool calls while keeping Wingman's guarantees in Wingman's code. Stdio-local is the smallest server that delivers this, and adds no credentials, ports, or tenancy.

**Parity principle (added 2026-07).** The MCP surface tracks the CLI: every user-facing capability ships on both surfaces in the same change, as thin wrappers over the same application-layer functions. Adaptations are allowed only where the medium demands them — the CLI's interactive confirm-before-attach for feeds (RFC-011) becomes a two-tool pair over MCP (`feed_discover` reports; `feed_attach` runs only after the user's explicit yes in conversation), and file inputs are accepted as local paths. A CLI command without its MCP counterpart is a review finding, not a style choice.

**Revisit if.** A non-MCP consumer appears (REST/web UI), or remote access from claude.ai web/mobile is wanted (remote MCP with auth — a separate durable decision).

## RFC-009: Read-only public-feed fetching, explicitly invoked

**Decision.** Wingman's first network access: `wingman people fetch` reads the public, unauthenticated RSS feed of a person the user has explicitly put on their watchlist. The rules, enforced in one place (`infrastructure/fetch.py`):

- **Explicit invocation only.** A fetch happens when the user runs the command — never scheduled, never in the background, never as a side effect of another operation.
- **Read-only, HTTPS-only, unauthenticated.** GET requests to public endpoints; no credentials exist to attach, and non-HTTPS URLs are rejected.
- **Public content only, from declared sources.** Feeds belong to people the user added by hand or seeded from their own LinkedIn connections export. No crawling, no discovery beyond what the user configured. Scraping authenticated surfaces (LinkedIn itself) is explicitly out — exports only.
- **Fetched bytes enter the normal provenance pipeline.** Each post becomes a content-hashed immutable SourceRecord with the raw HTML archived in the inbox, deduplicated by hash, indexed as an ExternalDocument — separate from the user's own corpus so "my evidence" and "their point of view" never mix.
- **Failures are visible.** A feed that cannot be fetched or parsed reports an error; it never degrades silently into an empty result.

**Durable decision** — the *invariants* above (explicit, read-only, public, provenance-tracked) are the durable part; the set of supported feed types may grow.

**Alternatives.** Live connectors with scheduled sync (background network activity in a local-first privacy tool — deferred to Phase 8's connector architecture, which requires its own durable entry); scraping profile pages (violates platform terms and the least-privilege invariant); requiring manual downloads for everything (fails the reality that public writing is the product's raw material for relationship intelligence).

**Rationale.** Relationship intelligence needs other people's public writing, and an RSS feed is that writing in its author-published, terms-of-service-clean form. Confining network access to one function with hard invariants keeps the local-first promise auditable: the workspace never talks to the network unless the user just asked it to, and everything fetched is traceable to the command that fetched it.

**Revisit if.** Feed refresh becomes tedious enough that the user wants scheduled sync — that is Phase 8's connector architecture decision, not a quiet relaxation of this entry.

## RFC-010: Semantic similarity via embeddings, stored in SQLite

**Decision.** People similarity ("who thinks about what I think about", "if you like A and B, talk to C") is computed from text embeddings: a new `embed_semantic` capability class in `models.toml` maps to an embeddings provider (default `voyage`/`voyage-4`; `hashed` is a local, network-free fallback). Vectors are unit-length, stored as float32 blobs in `wingman.db`, and compared with a dot product (equal to cosine similarity for unit vectors) in plain Python. A person's vector is the normalized mean of their documents' vectors; the user's vector is the normalized mean of their corpus.

Boundaries that make this admissible:

- **Embedding is explicit data egress.** Document text is sent to the provider only by `wingman embed` — never as a side effect of ingesting, fetching, or searching. The command is the consent.
- **RFC-007 stands.** Evidence retrieval (`wingman evidence`, `wingman people evidence`) stays on deterministic FTS5. Embeddings serve *similarity*, a question keyword search cannot answer at all; they do not replace the retrieval path, whose revisit trigger has not fired.
- **No vector database.** One person's watchlist is hundreds of documents; brute-force dot products over in-memory vectors are instant. The vectors live in the same single SQLite file as everything else (RFC-002).
- **One model at a time.** Vectors from different embedding models are incomparable; similarity refuses to run over mixed-model vectors rather than returning garbage.

**Alternatives.** A vector database (operational weight without a workload that needs approximate search); model-judged similarity (an LLM ranking people per query — expensive, non-deterministic, unauditable as a ranking function; models are used later to *explain* a match with cited quotes, not to compute it); TF-IDF locally (the `hashed` provider is that floor, kept as the offline option).

**Rationale.** Similarity between bodies of writing is exactly what embeddings are for, and the deterministic-controls rule (RFC-003) is preserved: the model call produces data (vectors) once per document, while every ranking computed from them is auditable arithmetic. Voyage AI is the default provider per Anthropic's embeddings guidance; provider choice lives in `models.toml` like every other model name (RFC-004).

**Revisit if.** The watchlist grows to where brute force is slow (tens of thousands of embedded documents — then an ANN index becomes a documented decision), or drafting/assessment later wants semantic *retrieval* (that is RFC-007's own revisit trigger, decided on its own terms).

## RFC-011: General feeds and index-page sources (amends RFC-009)

**Decision.** A person may have multiple typed sources, not just a Substack URL: `rss` (RSS 2.0 or Atom — Substack, Medium, WordPress, Ghost, …) and `index_page` (a blog index on a site with no feed — common for VC firms and startup marketing sites, where the "CxO thinking via company blog" content lives). Sources are attributed to the `person` or, honestly, to an `organization` (a company blog post is presented as "via <org>", never as a fabricated personal byline). Two modest widenings of RFC-009, both bounded and user-configured:

- **Add-time discovery.** `wingman people add-feed` does one GET of the pasted URL, then follows HTML feed autodiscovery (`<link rel="alternate">`) or probes a short enumerable list of conventional feed paths — never a crawl. Discovery **never attaches without confirmation**: the same name can belong to different humans, and a discovered feed can be the wrong one, so the user gets the final say.
- **Index-page fetching.** For a configured `index_page` source, each fetch reads that one page, extracts post links living under the index path, and ingests at most a bounded number of not-yet-seen pages through the ordinary provenance pipeline (content-hashed SourceRecords, inbox archive, dedup).

Everything else RFC-009 established holds unchanged: explicit invocation only, read-only HTTPS to public endpoints (including across redirects), visible failures.

**Alternatives.** Substack-only forever (excludes exactly the investor/executive persona whose firms publish on feed-less Webflow sites); third-party feed-generation services (proxy the user's reading through another party); headless-browser scraping (fails the auditability and ToS bar); auto-attaching discovered feeds (see the wrong-human risk above).

**Rationale.** Public writing is the raw material of relationship intelligence, and it lives behind exactly two shapes: feeds (near-universal on personal-blog platforms) and feed-less marketing sites. Covering both with one confirm-gated command keeps the watchlist honest about attribution and keeps every fetched byte inside the existing provenance rules.

**Revisit if.** Index-page extraction proves too brittle against redesigns (then sitemap.xml `lastmod`-driven fetching becomes the refinement, still within these invariants), or per-author attribution on company blogs is wanted (post-page metadata reading — a further widening that gets its own look).

## RFC-012: Company dossiers as deterministic composition (Phase 3, slice ii)

**Decision.** `wingman company dossier <name>` produces the roadmap's dated company snapshot by composing artifacts the workspace has already validated: watched people at the company (via the Person `company` field), org-attributed sources (RFC-011), POV-card stances rendered with explicit labels (`[inference]` statement backed by a verbatim `[fact]` quote — RFC-005's fact/inference/hypothesis discipline made visible), embedding-based signals when available (alignment with the user's corpus, nearest companies), a staleness warning when the newest attributable document is older than 90 days, and an explicit Gaps section naming what is missing and the command that fills it. The dossier is deterministic — no model call, no network — and is written as dated Markdown under `reports/companies/`, the artifact convention from DESIGN.md.

Two deferrals, on the demonstrated-need rule:

- **No stored Organization entity yet.** Companies are derived at read time from Person records and document attribution. A first-class Organization row earns its place when there is user-supplied metadata to hang on it (aliases, notes, approved research sources) — not before.
- **No model-synthesized "company themes" yet.** The dossier's claims are inherited from per-person POV cards, which were already validated quote-by-quote. A company-level synthesis step (many documents → themes) is a further model surface that gets added when per-person stances prove insufficient.

**Alternatives.** Model-written dossiers (unauditable claims exactly where the roadmap demands labeled ones); live research at dossier time (Phase 3's "research plan / approved-source handling" — a bigger decision about network scope that deserves its own entry when built); storing dossiers in SQLite (they are cheap, derived, and dated — the filesystem under `reports/` is the record).

**Rationale.** Phase 3's usable outcome is "generate a dated company dossier". Every ingredient already existed with provenance attached; composing them deterministically ships the outcome without adding a model surface or a network path, and the Gaps section turns missing data into the next command to run — graceful degradation as a feature.

**Revisit if.** Per-company research sources arrive (then approved-source handling and refresh become the durable design), or users want cross-person synthesis beyond what POV cards carry.

## RFC-013: Resume import formats — PDF, DOCX, LaTeX, Google URLs

**Decision.** `wingman ingest` accepts, beyond Markdown/plain text: **PDF** (via `pypdf`, the project's one extraction dependency — PDF genuinely cannot be parsed with the standard library), **DOCX** (standard library only: the zip's `word/document.xml` carries every visible text run), **LaTeX** (a deterministic flattener — comments and command tokens stripped, braced argument text kept, `\item` → bullet), and `--url` for **link-accessible Google Docs/Drive documents** (Docs via its `export?format=txt` endpoint, Drive file links fetched and sniffed as PDF/DOCX/text; MCP counterpart `ingest_resume_url`). Extraction is deterministic and happens before hashing, so the stored text, the model's input, and every verbatim-evidence check see the same bytes. URL fetches are the existing RFC-009 shape — explicit, user-invoked, HTTPS-only — and the fetched artifact is archived to the inbox before extraction, keeping the original file as the provenance record. A permission-walled Google document returns HTML and fails visibly with sharing guidance.

**LaTeX difficulty assessment** (evaluated before building): a faithful conversion requires a TeX engine or pandoc — a heavy dependency for one input format, rejected. A deterministic flattener is ~40 lines with no dependency and preserves the visible words of moderncv/altacv-style resumes, which is sufficient because the downstream consumer is an extraction model reading flattened text, and its output is still evidence-validated verbatim against that same flattened text. Limitation accepted and documented: exotic macros degrade to their argument text; math and layout are not reproduced; an empty flatten fails visibly.

**Alternatives.** OCR for scanned PDFs (a model/system dependency for a rare case — the failure message tells the user to export text instead); Google API/OAuth integration (credentialed access contradicts the no-credentials fetch invariant; the export endpoint works for exactly the documents the user has chosen to make link-accessible); accepting arbitrary URLs (scope-creeps the fetch surface — non-Google URLs get a visible "download it and ingest the file" pointer).

**Rationale.** Resumes live in PDF and DOCX far more often than Markdown; requiring manual conversion was the biggest friction in Phase 1's front door. Each format gets the cheapest honest extraction that the evidence-validation gate can stand behind.

**Revisit if.** Scanned-PDF resumes turn out to be common (OCR becomes its own decision), or users need non-Google document hosts (the URL allowlist then becomes a configured, documented surface).

## RFC-014: Recent-news snapshots via a public news RSS endpoint

**Decision.** `wingman people news <name>` fetches recent news mentioning a person or their company from Google News's public RSS search endpoint — one explicit, user-invoked, read-only HTTPS GET of an unauthenticated public feed, squarely inside the RFC-009 invariants. Results are stored as a replace-on-refresh snapshot (a new `news_items` table, capped at 8 items), rendered as the fourth quadrant of the person export's 2x2 briefing dock with the fetch date and a staleness flag past 7 days. News items are never mixed into ExternalDocuments: a journalist's article about a person is not that person's writing, and keeping the stores separate keeps POV cards quoting only the person's own words.

**The privacy trade, stated plainly.** The query — the person's name and their company — is sent to the news provider when the user runs the command. That is the entire egress and it is disclosed in the command's help text; the command never runs implicitly (not part of `wingman sync` for now, precisely so the disclosure stays attached to the action).

**Alternatives.** News APIs with keys (credentialed egress for a commodity feed); scraping search result pages (ToS-hostile, brittle); asking the user to paste links (the manual fallback still works — any judgment about an article belongs to the user reading it either way).

**Rationale.** Outreach benefits from knowing what just happened at the person's company; a public RSS search is the cheapest honest source, and snapshot-replace semantics keep it a briefing input rather than a growing archive of third-party content.

**Revisit if.** The provider retires the endpoint (Bing News RSS is the drop-in shape), or users want news in `wingman sync` (then the disclosure has to move with it).

## RFC-015: Company research over user-approved sources (Phase 3, slice iii)

**Amended by RFC-060** (issue #349): "reduces each page deterministically to a snapshot" is no longer *all* a fetch keeps. A source may be marked `retain`, in which case the page's prose is ALSO kept as a company-attributed document, so a values page becomes something a stance can quote instead of only a hash saying it changed. Default OFF, per source; the fetch, the snapshot, the diff and the egress below are unchanged — only what survives the fetch differs. Everything else here stands.

**Decision.** Per-company research sources, added explicitly by the user and fetched only on explicit command — the network-scope decision RFC-012 deferred, now resolved. `wingman company add-source "X" <url> [--label]` records an approved HTTPS source for a company; **the act of adding is the approval** — no confirmation theater at fetch time. `wingman company sources "X"` lists them (`remove-source` withdraws one, snapshot included); `wingman company research "X"` makes one read-only GET per approved source (RFC-009 shape: explicit invocation, https-only, visible failures, one page per URL — no crawling), reduces each page deterministically to a snapshot (SHA-256 of visible text + the page's set of https links), stores it replace-on-refresh keyed `(company_key, url)`, and reports the diff against the previous snapshot: **new links are the hiring/announcement signal**, a changed text hash the weaker "page changed" signal, and "unchanged since \<date\>" an honest answer. A failed source keeps its previous snapshot and is reported, never fatal. The dossier gains a "Research (approved sources)" section rendering stored snapshots with a 30-day staleness flag — no fetch at dossier time, preserving RFC-012's determinism. MCP parity (RFC-008): `company_source(action=add|remove|list, ...)` following the watchlist single-tool convention, plus `company_research`.

**Alternatives.** Fetching at dossier time (couples an artifact to the network and breaks dossier determinism); crawling beyond the approved page (scope creep — the user approved one URL, one GET honors exactly that); a model summarizing the fetched page (unauditable claims where a link-set diff is deterministic and explainable); a first-class Organization entity (still deferred — a `(company_key, url)` table is the metadata that actually arrived; aliases/notes remain the demonstrated-need trigger).

**Rationale.** Careers pages and newsrooms are where hiring signals appear first, and which pages to trust is a judgment only the user can make. Naming the exact URLs turns "did anything change at X" into a deterministic diff of user-chosen pages instead of a crawl, keeping the egress surface enumerable: every URL Wingman will ever fetch for a company is visible in `company sources`.

**Revisit if.** Users want research inside `sync`/`make-it-so` (the fetch consent and cost move with it — an explicit flag, not a default), or want change history rather than a latest-snapshot diff (snapshot generations become a real archive), or want alerting (that is RFC-006 territory: Wingman still never sends anything).

## RFC-016: Model-synthesized company themes (resolves an RFC-012 deferral)

**Decision.** `wingman company pov "X" [--refresh]` synthesizes company-level themes from the company's document pool — the same pool the dossier reads: writing by watched people at the company plus org-attributed documents. It is the existing POV-card machinery pointed at a company: one synthesize_balanced call, every proposed theme kept **only if its quote appears verbatim in a stored document** (the fabrication guard is unchanged — a company theme is still only as real as the sentence it quotes). Author attribution rides each document's title into the prompt and onto each surviving stance's `doc_title`, so a theme always names who actually said it. The card is stored in `pov_cards` under the reserved id `__company__{company_key}` (the `__corpus__` pattern, extended); a stored card renders without any model call, `--refresh` rebuilds. The dossier renders the stored card deterministically in a "Company themes (synthesized …)" section — dossier generation itself still makes no model call — and names the command in Gaps when documents exist but no card does. MCP parity: `company_pov`.

**Alternatives.** Synthesizing at dossier time (adds a model call to a deterministic artifact); a separate themes table (the card shape — stances, quotes, topics, provenance — already fits, and one table means one validation path); skipping per-person attribution (loses exactly the information that makes a company card more than a merged person card).

**Rationale.** RFC-012 deferred company-level synthesis until per-person stances proved insufficient; the demonstrated need arrived — a dossier of several people's cards answers "what does each person argue," not "what does this company collectively argue about." Reusing the validated card pipeline ships the answer without a new model surface: same prompt contract, same verbatim gate, same storage.

**Revisit if.** Company pools outgrow the 20-document prompt budget (then selection within the pool — per-author quotas, recency windows — becomes its own decision), or themes need to diff over time (cards would need versioning, which `pov_cards`' replace-on-save deliberately avoids).

## RFC-017: Remote MCP — a local HTTP listener behind a user-managed tunnel

**Decision.** `wingman-mcp --http [--port N]` serves the existing MCP tool surface over streamable HTTP, **bound to 127.0.0.1 by default**, at a capability path `/mcp/<token>` where the token is generated once into the workspace (`mcp-http-token`, mode 0600) and rotated on demand with `--rotate-token` — rotation is revocation. Reaching it from claude.ai web/mobile is the user's tunnel choice, documented but not embedded: `tailscale serve` for tailnet-only access from their own devices, `tailscale funnel` (or an equivalent authenticated tunnel) when claude.ai's connector infrastructure must reach it. Wingman itself never opens a public listener: binding a non-loopback address requires an explicit `--host` and prints a warning naming what is being exposed. The stdio transport and the tool surface are unchanged — one server, two transports, zero new tools.

**The exposure trade, stated plainly.** The MCP surface can read the whole workspace and trigger fetches and model calls, so exposing it is exposing the workspace. The mitigations are layered and honest about their limits: loopback-only default (exposure requires a second, deliberate act — running a tunnel); an unguessable capability path (an attacker who cannot read the URL cannot speak to the server — but anyone who obtains the URL can, so treat it like a password and rotate on any doubt); TLS from the tunnel (Tailscale terminates HTTPS; wingman serves plain HTTP on loopback and never pretends otherwise). RFC-006 still holds at the bottom: nothing the remote surface can invoke sends anything on the user's behalf.

**Alternatives.** A hosted relay (moves the workspace — or a credential to it — off the user's machine; contradicts local-first at the root); OAuth with dynamic client registration (the protocol-blessed connector auth, but a full authorization-server implementation inside a local CLI tool is a liability out of proportion to a single-user server; the capability URL delivers single-user access control with rotation today); binding 0.0.0.0 with the token as the only guard (LAN exposure by default is exactly the surprise a local-first tool must not spring).

**Rationale.** The workspace lives on the user's machine and should stay there; what travels is the conversation. A loopback listener plus the user's own tunnel keeps the trust decision — and the off-switch — in the user's hands, reuses battle-tested infrastructure for TLS and reachability, and adds no third party to the data path that the user did not choose themselves.

**Revisit if.** claude.ai connectors require OAuth for custom MCP servers (then dynamic client registration becomes the cost of entry and gets its own design), or multiple clients need distinct revocable grants (per-client tokens), or the MCP SDK ships built-in auth worth adopting.

## RFC-018: Follow a company — assembled focus and the consented overnight deep-refresh

**Decision.** Two commands turn "I care about this company" into standing intelligence. `wingman company follow "X" [--url https://domain]` assembles the focus in one act: the company and every known person there **with writing attached** are enrolled on the reserved `overnight` watchlist; when the user names the domain, its conventional pages (`/careers`, `/jobs`, `/blog`, `/news`, `/newsroom`, `/about`) are probed with one GET each and the live ones become approved research sources (RFC-015's "adding is the approval" extends to this: the user named the domain in an explicit invocation, and the report lists exactly what was approved, each removable). Known people *without* writing are surfaced as suggestions, never silently enrolled — enrolling someone means their name will be sent to a news provider on every run, so it stays tied to having chosen to watch their writing. `wingman overnight` is the explicit **spend-the-tokens** command: every enrolled target gets the deep pipeline — research diffs, feed fetches, news, embeddings, fresh POV cards, company themes, briefs, exports — and the run ends in a dated digest under `reports/digests/`: what changed, what failed (honestly, per target), and deterministic follow-next suggestions (similar companies by embedding, themes to watch from company cards). MCP parity: `company_follow`, `overnight`.

**The consent amendment, stated plainly.** RFC-009's rule has been "the command is the consent," per invocation. Overnight runs stretch that: the user will schedule this command (cron/launchd — documented, not installed by Wingman) and sleep through its execution. The amended rule: **enrollment is standing consent** — durable, enumerable (`wingman watchlist show overnight` lists every target whose feeds, news queries, and research pages will be touched), and revocable (`wingman watchlist remove`). The schedule itself is still the user's act on their own machine; Wingman ships no daemon, and RFC-006 is untouched — a run reads and writes locally, and sends nothing on the user's behalf.

**Alternatives.** A resident scheduler inside Wingman (a daemon is an always-on consent the user cannot see; launchd/cron is inspectable and theirs); enrolling every known connection at the company (turns one follow into dozens of names sent to a news provider nightly — suggestion-only is the honest default); crawling the domain for sources (six conventional paths, one GET each, is the reasonable ceiling — RFC-015 stays one-page-one-GET); a model deciding what "changed" overnight (the digest composes deterministic outputs — diffs, counts, step results; the model surfaces stay inside the already-validated card/brief pipelines).

**Rationale.** The user's stated loop is: name a company, wake up to answers. Everything the deep pipeline runs already existed as consented single commands; this RFC adds only assembly (follow) and sequencing plus a digest (overnight), so the cheapest new surface delivers the loop while every invariant keeps its existing enforcement point. Answers-on-demand then falls to the search improvement already queued ahead of this work.

**Revisit if.** Users want per-target depth control (research-only vs full model refresh — a per-member flag on the enrollment record), or digests need trend memory across runs (digest diffing becomes its own store), or the suggestion surface should reach beyond the workspace (that is a new egress decision, not an extension of this one).

## RFC-019a / RFC-034a: bring-your-own-key wins over the environment

**Decision (amends RFC-019 and RFC-034).** The resolution ladder becomes
**workspace key file > environment > Keychain > host file > global file**. The
key someone provided for their own workspace is the key their calls use;
everything below it is somebody else's default. RFC-019's original
"an exported environment variable always wins", reaffirmed by RFC-034's
"the env-wins invariant survives untouched", no longer holds.

**Rationale.** Env-wins was right when one person ran one workspace on their own
machine: an export was that person's own deliberate act, and the ladder simply
preferred the most recent one. It stopped being right the moment a shared
process served several people (RFC-048). Then the environment belongs to the
*operator* and the workspace key belongs to the *tenant*, and env-wins means an
operator's stale export silently spends on a tenant's behalf — an attribution
and billing problem, not merely the misleading UI copy it also produced. RFC-048
had already carved out the exception for tenants (`strict_provider_keys` skips
the environment entirely); this generalises that rather than maintaining two
competing truths in one codebase. A form that stores a key it will not use is a
trap, which is the same objection RFC-034 raised against storing unverified
keys.

**Cost, accepted.** An operator can no longer override a stale or revoked
*stored* key by exporting the variable; a bad workspace key must be fixed where
it lives (`wingman keys set`, the web form, or deleting `keys.env`). The support
shape this creates — "I exported the right key and it still fails" — is the
price of the guarantee that a provided key is an honoured one. `wingman doctor`
names the winning source and every shadowed copy (#122), so the diagnosis is one
command.

**Unchanged.** The environment remains a full source, so CI, containers and a
fresh workspace behave exactly as before. Hydration still never overwrites a set
variable. No key is ever logged, and there is still no MCP tool for setting one
(RFC-019's parity exception).

**Revisit if.** A deployment needs central key rotation that must override every
workspace at once — that is a real need this ordering makes harder, and it would
argue for an explicit "managed key" source above the workspace rather than for
restoring env-wins.

## RFC-019: API keys in the macOS Keychain, hydrated at startup

**Decision.** `wingman keys set anthropic|voyage` stores an API key in the macOS Keychain via the system `security` CLI (service = the environment variable name, account = `wingman`, so items are recognizable in Keychain Access); `keys list` shows each key's current *source* — environment, keychain, or not set — never its value; `keys unset` removes one. At startup, both entrypoints (the CLI's root callback and `wingman-mcp`'s main) hydrate any known key that is absent from the environment. **Precedence: an exported environment variable always wins; the Keychain only fills gaps** — existing shell exports, launchd `EnvironmentVariables`, and CI secrets behave exactly as before. On systems without `security` (Linux, CI, containers) hydration is a silent no-op and `keys set` fails with a plain explanation. The payoff: `claude_desktop_config.json` needs no `env` block, launchd plists need no embedded secrets, and no wrapper scripts exist to get wrong.

**Parity exception (RFC-008), deliberate:** there is no MCP `keys` tool. Setting a key over MCP would route the secret through the model conversation — transcript, context window, provider logs — which is exactly where a credential must not travel. Key management is a terminal act.

**Alternatives.** A secrets file in the workspace (plaintext at rest — the thing being eliminated); an OS-agnostic keyring dependency (a real library, but wingman's one deployment target today is macOS and `security` is already on every Mac; the dependency earns its place when a second platform demonstrates need); passing the secret to `security` via stdin instead of argv (the `-w <value>` argv form is momentarily visible in the process list; accepted — standard practice for `security`, single-user machine, and the alternative is interactive-only).

**Rationale.** Keys kept appearing in exactly the wrong places: pasted into `claude_desktop_config.json`, embedded in launchd plists, hand-rolled wrapper scripts with wrong paths. One command puts the credential where macOS already guards secrets, and startup hydration makes every consumer — CLI, MCP stdio, MCP HTTP, scheduled overnight runs — just work without any file carrying a secret.

**Revisit if.** A second platform arrives (the `keyring` library becomes the honest answer), or more providers mean the known-key map should live in `models.toml` rather than code, or Keychain ACL prompts interfere with unattended launchd runs (then the run's first manual invocation with "Always Allow" becomes a documented setup step — it already is in the README).

## RFC-020: Warmth as a named signal vector, not a collapsed score

**Decision.** `_warmth()` in `reporting/export.py` returns a list of `WarmthSignal(name, points, description)` — one entry per deterministic signal the workspace actually holds (`direct_connection`, `email_on_file`, `shared_connections`) — instead of a single `(score, label, signals: list[str])` tuple. A separate `_warmth_label()` sums the vector into the display score/label (`cold`/`cool`/`warm`/`hot`) used for the dot-meter in the person export; the vector, not the collapsed number, is now the primary artifact, and the render path is the only consumer that still reduces it to one number. Rendered output (the dot-meter and the "; "-joined signal text) is unchanged — this is a data-shape decision, not a UX change.

**Rationale.** A 2026-07-18 competitive research pass (`docs/research/`) flagged the prior single-score design as inconsistent with the evidence-before-assertion invariant: an opaque number is itself an unsupported claim, and every comparator surveyed that does relationship scoring (Humantic AI, Crystal Knows) hides its formula behind an inference layer this project's manifesto rejects. Naming each signal keeps every point traceable to the record that produced it (RFC-005), and gives CLI/MCP callers a structured object to consume later without another data-shape migration.

**Scope boundary.** This RFC decomposes the *existing* three signals only. It does not add interaction-history signals (recency, frequency, shared context beyond common-company connections) — those require a new, user-approved data source (calendar/email import) and are their own future decision, not implied by this one.

**Alternatives.** Keep the collapsed score and add signal names as metadata alongside it (rejected — the collapsed number would still be the thing callers reach for first, reproducing the opacity problem); expose a 0–1 normalized weight per signal instead of raw points (rejected for now — the point values are already the whole formula, and normalizing adds a conversion step with no consumer that needs it yet).

**Revisit if.** A CLI or MCP surface wants to expose warmth as structured output (the vector is already shaped for that — `WarmthSignal.name`/`points`/`description` map directly to fields), or interaction-history import (RFC-018's v0.4 follow-on) lands and needs new signal types added to the vector.

## RFC-021: Rename, delete, and fix for people and companies

**Decision.** `people` and `company` objects gain three management operations, each exposed identically on CLI and MCP (RFC-008): **rename** (`wingman people rename "<current>" "<new>"`, `people_manage(action='rename', ...)`, and the company equivalents) changes a display name in place and fails if the new name already belongs to someone else; **delete** removes an object and everything keyed to it, not reversible; **fix** (people only) is a rename that falls back to a merge instead of failing on a name collision — `fix("Ed Wong", "Edmund Wong")` merges the "Ed Wong" record into an existing "Edmund Wong" if one exists (filling blank fields from the absorbed record, moving its documents/POV card/outreach brief, then deleting it), or plain-renames if "Edmund Wong" doesn't exist yet. Company also gets a narrower **delete-dossier**, which removes only the generated Markdown report files under `reports/companies/` without touching sources, research snapshots, or the POV card — for clearing stale reports before a regenerate.

**Why people needed a merge path and companies didn't.** A person is a real row with a stable `person_id`; every other person-keyed table (documents, POV card, news, outreach brief) references that ID, so a rename never touches them — only the display name and any watchlist membership move. But `add_person`'s dedup keys on exact normalized name, so "Ed Wong" and "Edmund Wong" (or "Rushil" and "Rushil Ram") silently create two records instead of one — a plain rename would then collide once the fuller name already exists. Company has no such row at all: it is a normalized-name key (`company_key`) shared across `company_sources`, `research_snapshots`, and a synthetic `pov_cards` identity (`company_card_id`, RFC-016), so a company rename is a re-key across those tables plus watchlist memberships, not a merge — the concept of "two company rows to merge" doesn't exist in this schema, only stray rows under the wrong key.

**Alternatives.** A single generic `object_manage(kind, action, ...)` tool across both types (rejected — people and company operations have different failure semantics, per above; a single signature would blur that rather than clarify it). Automatic fuzzy-merge on every `people_add` call, so "Ed Wong" would have matched "Edmund Wong" without a separate fix step (rejected — silent fuzzy matching risks merging two different people who happen to share a name fragment; an explicit `fix` call keeps the merge decision a human one, consistent with the deterministic-controls principle, RFC-003). A confirmation prompt before delete (rejected for parity with existing destructive commands like `watchlist remove` and `company remove-source`, which already act on the command name alone with no extra gate).

**Rationale.** The direct trigger was operational, not speculative: enrolling contacts under first-name-only placeholders (`people_add "Rushil" --company Anthropic`) before their full details were known, then discovering the correct name later, is a normal sequence for a tool meant to be used incrementally — and with no rename/delete/merge, every correction permanently forked a duplicate, dead-ended record. Company rename/delete closes the same gap for the RFC-018/RFC-015 side: a mistyped or superseded company name (a domain typo, a rebrand) had no path back to a clean state either.

**Revisit if.** A "kind" of merge conflict arises where neither record should simply win (e.g. both have different but equally-valid data in the same field) — today `merge_person` always prefers the `keep` record's non-empty values, which is fine for filling blanks but not for adjudicating real conflicts; or company rename needs to also migrate `Person.company` free-text fields for consistency (not done today — a renamed company's watched people keep their old company string until next touched).

## RFC-022: Unified search across every store, keyword plus semantic

**Decision.** `wingman search "<query>"` (MCP: `search`) answers "what does the workspace know about X" in one call, across every store: the user's corpus and watched people's writing (SQLite FTS5, real relevance-ranked snippets — the two existing evidence paths, reused not reimplemented), POV stances and company themes (token match over statement + verbatim quote + doc title), news snapshots (title match, newest first), research-snapshot links (where the hiring signals live), and outreach briefs (talking points + intro bullets). Keyword matching is AND over query tokens everywhere — the same semantics FTS5 defaults to. On top of it, a **semantic pass** embeds the query (`input_type="query"`, the same one-model-at-a-time RFC-010 machinery as everything else) and surfaces embedded documents that match by meaning above a minimum cosine similarity, deduplicated against the keyword hits and labeled `[semantic]` with their similarity score — paraphrase recall, visibly distinct from exact matches. Results are **interleaved by per-store rank**: every store's best answer surfaces before any store's third-best, deterministically. Each hit carries kind, attribution (who), date, and source.

**The egress, stated plainly.** With a remote embeddings provider configured (voyage), the query text is sent to that provider — the same trip document text makes during `wingman embed`, now made per search, and disclosed in the command's and tool's help text. With the local `hashed` provider nothing leaves the machine; with no embeddings at all the semantic pass is skipped **with a visible note saying why** — degradation is reported, never silent. Semantic-by-default was a deliberate user decision: the person whose workspace this is chose recall over query privacy, and the disclosure keeps the choice informed.

**Alternatives.** Keyword-only with an opt-in `--semantic` flag (the initial design — rejected by the user as friction: a search that silently misses paraphrased content fails its purpose, and the egress is the same class the user already accepted for documents); one merged FTS index over everything (a denormalized copy of every store to keep in sync — rank interleaving over per-store queries gets the single-list outcome without a second source of truth); score normalization across stores (BM25, token counts, and cosines are not commensurable; pretending they are produces confident nonsense ordering — rank position is the honest common currency).

**Rationale.** The overnight pipeline (RFC-018) made accumulation cheap; retrieval was the bottleneck — five commands, two ranking systems, four unsearchable stores. One tool that sweeps everything, with meaning-level recall over the embedded stores, is what makes the conversational surface work: an MCP client calls `search` first and gets everything the workspace knows, cited, instead of guessing which silo to query.

**Revisit if.** Users want a query-privacy mode (a `--local` flag skipping the semantic pass is one line), or stores grow enough that per-store scans of structured artifacts (stances, briefs) need real indexes, or digests/reports on disk should join the sweep (a files store with its own staleness questions).

## RFC-023: Opt-in local usage telemetry, with transcript harvesting

**Decision.** `wingman telemetry on` turns on a local usage journal — rows in the workspace's own SQLite database, **default off, never transmitted, and Wingman ships no transmitter for it**. When enabled it records: every CLI invocation (argv, outcome, duration — via the console-script wrapper, so nothing is instrumented per command), every MCP tool call with its arguments and result text (the conversation-adjacent trace of how a model client actually drives the workspace — captured by wrapping the registered tools once, at import), and anything imported by `wingman telemetry harvest-transcript <session.jsonl>`, which parses a Claude Code session transcript into events with their original timestamps: user messages, assistant replies, every Bash invocation mentioning wingman, and every wingman MCP call. `telemetry status|show|export` read the journal (export = JSONL under reports/); the MCP `telemetry` tool exposes status/show so a conversation can analyze its own usage. Recording never breaks the command being recorded — every telemetry failure degrades to a log line.

**Consent, stated plainly.** This journal exists because the workspace owner asked for it in so many words — a conscious, explicit opt-in, recorded here. Conversation text is captured **unredacted by owner decision**: the owner is the author of every message involved and chose understanding over minimization. Two boundaries hold anyway: `wingman keys set` values are credentials, not usage, and are never journaled; and enabling/disabling is CLI-only (like key management) so the toggle stays a terminal act by the human, not something a connected model can flip.

**Alternatives.** A remote analytics service (contradicts local-first at the root; there is nothing this journal needs that SQLite doesn't provide); per-command instrumentation (drift guaranteed — the entry-point wrapper and the one-time tool wrap cover every surface without touching feature code); redaction/anonymization pipelines (machinery without a beneficiary in a single-owner workspace — revisit the day a second person's consent is involved).

**Rationale.** "How is this actually being used" is the question every next-version decision depends on, and the honest data lives in exactly three places: CLI history, MCP traffic, and the Claude conversations where the work happened. Capturing all three locally makes the workspace self-describing without a byte of egress.

**Revisit if.** A second user's data enters any journal path (redaction stops being machinery without a beneficiary and becomes mandatory), or journal size needs retention policy (a prune command mirroring backups' keep-N), or Claude Desktop gains local transcripts worth harvesting (today only Claude Code writes them).

## RFC-024: From hiring signal to application — posting fetch and the application pack

**Decision.** Two additions close the loop the overnight pipeline opens. `wingman assess --url <posting>` (MCP: `assess_job_url`) fetches a job posting straight from its URL — one explicit, user-invoked HTTPS GET in the RFC-009 shape, the page reduced to its visible text and archived under `inbox/` so the fetch stays the provenance record — then assessed exactly like a pasted description (verdicts still cite only real profile items; login walls and JS-only pages fail visibly with a save-the-file fallback). `wingman pack "<role>"` (MCP: `pack`) composes the **application pack** for an assessed opportunity, deterministically and with no model call: the cited fit summary (met/partial/gap/unknown per requirement with the profile items behind each verdict), **cover-letter fodder** — bullets pairing each met/partial requirement with a verbatim quote from the user's own profile evidence, explicitly raw material to be composed in the user's voice (RFC-006 unchanged: Wingman never writes the letter and never sends) — and the company intelligence already validated in the workspace: synthesized themes, people the user knows there, approved research sources. The company is inferred from the role title against known companies, overridable with `--company`. Packs land under `reports/packs/` styled for the standard md-to-pdf render; the overnight digest's job-link actions now carry the runnable `wingman assess --url` command as evidence, so the morning path is signal → assessment → pack in three commands.

**Alternatives.** A model-written pack (unauditable exactly where the artifact must be most defensible — every line in a pack traces to an assessment verdict or a stored quote); auto-assessing new careers links inside overnight (turns one consented GET of an approved page into N unconsented GETs of arbitrary link targets plus model spend — the digest hands the user the command instead, keeping the invocation the consent); a cover-letter draft (the never-sends boundary exists precisely so the user's voice is the product — fodder, not prose).

**Rationale.** The pipeline accumulated signals but dead-ended at them: a new careers link required hand-copying a JD into a file, and no artifact assembled the evidence for a specific role. These are the two smallest pieces that make the north star concrete — a dated, citable "why I am the obvious candidate" document produced minutes after a posting appears.

**Revisit if.** Postings behind heavy JS become the norm (a readability/rendering dependency becomes its own decision), or packs need role-specific narrative beyond fodder (that is Phase 6/7 drafting-and-voice territory with its own critic pass), or opportunity volume justifies the Phase 5 scored daily brief.

## RFC-025: Feature requests — the first gated external write

**Decision.** "feature request: <idea>", said to any Claude surface connected to Wingman, becomes a GitHub issue — through a gate that is structural, not behavioral. The MCP `feature_request` tool's docstring carries the protocol (read the idea; ask clarifying questions when anything material is ambiguous; compose title and body; preview), and the tool itself refuses to file until `confirmed=true`: the unconfirmed call returns the exact issue text for the user to approve, so a model cannot skip the gate by being confident. The CLI twin (`wingman feature request`) previews and prompts unless `--yes`. Filing shells out to the **user's own `gh` CLI and auth** against a repo the user configured once (`wingman feature repo owner/name`, stored as a workspace file); Wingman holds no GitHub credential. Failures — no repo set, gh missing or unauthenticated, missing label — are reported with the fixing command. Filed issues are journaled in telemetry when it's on.

**Why this doesn't break RFC-006.** The invariant is *human approval before external action*, and this is the first feature to exercise the gate rather than avoid it: the trigger is an explicit user utterance, the exact payload is previewed, the confirmation is per-action, and the destination is the user's own repository under their own credentials. The never-sends posture for outreach — messages to other people — is untouched and stays absolute.

**Alternatives.** A GitHub token inside Wingman (a credential to hold and leak; `gh` already solves auth and is present on the target machine); filing from the conversational client's own GitHub tools (works only where the client has them — the MCP tool makes the capability uniform across Desktop, Code, and claude.ai); storing requests locally for manual filing (an inbox nobody drains; the friction defeats the purpose of capture-in-the-moment).

**Rationale.** Feature ideas arrive mid-conversation and die there. Capture at the moment of utterance, with the clarifying questions asked while context is hot, turns "I keep meaning to write that down" into a labeled, bodied issue — while the structural gate keeps the external-write boundary exactly as auditable as RFC-006 demands.

**Revisit if.** More external writes want the same shape (a general gated-action framework earns its place), or non-GitHub trackers arrive (the runner seam already isolates `gh`), or multi-user workspaces make "the user's own repo" ambiguous.

## RFC-026: Evidence quotes are verbatim modulo whitespace; Markdown is normalized on extraction

**Decision.** Two changes to how model quotes are checked against sources, prompted by a real import failure: a hand-maintained Markdown source-of-truth resume with hard-wrapped bullets had its strongest achievements rejected because the model quoted each sentence as read while the byte-for-byte containment check couldn't find it across the line breaks. First, every verbatim gate — resume ingestion, job-requirement extraction, POV stances, outreach quotes, and the quoted-span check on intro bullets (#67) — now folds runs of whitespace to a single space on both sides before the containment check (`application/evidence.fold_whitespace`). The check stays deterministic and exactly as strong on content: every non-space character must still match, in order; only wrapping and indentation are forgiven. Second, `.md`/`.markdown` files are normalized at extraction (`resume_formats.markdown_text`): hard-wrapped lines are joined back into their sentence, blockquote/bold/backtick markers are dropped, horizontal rules become paragraph breaks, while headings, bullets, tables, paragraph breaks, and fenced code keep their shape. The normalized text is what gets hashed, archived against, and quoted against — the "same text the model saw" invariant is preserved, and stored evidence quotes come out clean instead of carrying embedded wraps.

**Alternatives.** Prompting the model harder to copy line breaks (models read documents logically, not typographically; fighting that loses to the model on every provider change); fuzzy or similarity-threshold matching (reintroduces exactly the fabrication surface the verbatim gate exists to close — whitespace folding is the largest tolerance that admits zero content difference); normalizing only at the gates and leaving Markdown raw (works, but stored quotes and the archived source then disagree about wrapping, and PDF-style extraction noise would still leak into career.md renders).

**Rationale.** The verbatim gate is Wingman's core honesty mechanism, and it was rejecting true statements for presentation reasons — the worst failure mode for a trust feature, because users learn to ignore rejections. Folding whitespace keeps the gate's guarantee (a quote is real text from the real source) while dropping its false positives to the one class that cannot matter: how lines were wrapped.

**Revisit if.** Models start normalizing unicode punctuation inside quotes (en dashes, `→`, `×` — that would need a declared, versioned character-folding table, a materially bigger tolerance than whitespace), or a format arrives where whitespace is content (aligned columns in plain-text resumes) and needs an opt-out.

## RFC-027: Career-profile management — the manual correction workflow, finally

**Decision.** `wingman profile` (MCP: `profile_manage(action=list|rm|resolve|clear)`) closes the gap found in live use: re-ingesting an evolving source-of-truth document accumulates items — the same skill re-proposed with different wording lands as a side-by-side conflict row per RFC's dedupe rules — and nothing short of raw SQL could remove or resolve one, though people and companies have had manage tools since RFC-021. `profile list` shows every item with its id (active by kind, then unresolved conflicts); items are addressed by any unambiguous id prefix, git-style, because nobody types a UUID. `profile rm <id>` deletes one item. `profile resolve <id>` settles a duplicate: the named item is kept and promoted to active, and every rival sharing its kind and name key — the old active, other challengers — is dropped, so "resolve" always converges to exactly one row per name. `profile clear` (confirm-gated in the CLI) empties the table for a clean re-ingest; the same source record is reused on re-ingest, only the items are rebuilt. Every mutation re-renders career.json/career.md so the artifacts never drift from the table, and the help text says plainly that stored job assessments cite item ids that stop existing — re-run assess for anything that matters.

**Alternatives.** An `ingest --replace` mode that supersedes items from prior versions of the same document (attractive, but it needs a document-lineage concept Wingman doesn't have, and it silently deletes where an explicit resolve shows the user both candidates first); resolving conflicts automatically by recency or confidence (the conflict exists because two model runs phrased the same fact differently — picking a winner is exactly the judgment the user should make once, cheaply); editing items in place (correction-by-replacement keeps the evidence invariant simple: every stored item is still exactly what one validated extraction produced).

**Rationale.** Phase 1 promised "conflict detection and a manual correction workflow" and shipped only the detection half; the correction half turned out to be the first thing real usage demanded — three ingests of one evolving document produced a conflict pile with no drain. The fix is the smallest surface that makes the profile owned rather than append-only: see, remove, pick winners, start over.

**Revisit if.** Source-of-truth re-ingestion becomes the dominant flow (that's the trigger to design document lineage and `ingest --replace` on top of these primitives), or profiles grow beyond prefix-addressing comfort, or a bulk resolve ("keep newest everywhere") earns its place after real resolve sessions show a pattern.

## RFC-028: Document lineage — a new version of a document supersedes its own claims

**Decision.** Source records now carry a `document_key` — the document's own name, derived deterministically from the filename with inbox stamp prefixes stripped and case folded — and ingestion uses it to tell "a newer version of the same document" apart from "a different document." When a version of a document is ingested, every earlier record with the same key is its superseded lineage, and `persist_items` applies three rules. A re-proposed claim whose stored counterpart rests **entirely** on that lineage is *updated*: the old item is marked `superseded` (a new `ItemStatus`, kept for provenance — old packs and assessments still resolve it by id — but invisible to career renders, fit assessment, and the profile listing) and the new version's item becomes active. A stored claim resting on **any other** source — a LinkedIn export, a second document — still becomes a side-by-side conflict, because a document can only speak for itself. And after persisting, a retirement sweep marks superseded every remaining item resting entirely on the replaced lineage: claims the new version dropped are gone because the user deleted them, and stale conflict rows from pre-lineage ingests drain automatically — the same-name-different-wording pile heals on the next re-ingest with no manual resolution. `IngestReport` and the CLI/MCP summaries gain `Updated` and `Retired` counts; the `ingest_resume_text` MCP docstring now states that `filename` is the document's identity. The migration adds the column to existing databases on open and backfills keys from archived locator basenames, so lineage works retroactively.

**Alternatives.** An explicit `ingest --replace` flag (the user must remember it precisely in the flow where they're moving fast; filename identity is the intent they already expressed); content-similarity lineage detection (a heuristic where a deterministic rule exists — the filename — and misfires silently exactly when documents are near-duplicates for other reasons); deleting superseded items instead of retiring them (breaks every stored assessment and pack that cites an item id; status-based invisibility costs one enum value and keeps provenance whole); treating all same-name proposals as updates regardless of evidence source (silently discards genuine cross-source disagreement — the conflict feature's entire reason to exist).

**Rationale.** RFC-027 gave the profile a mop; this removes the spill. The source-of-truth workflow — edit the document, re-ingest, repeat — is the primary loop the profile exists to serve, and append-only semantics made that loop quadratically messy: every revision conflicted with every prior phrasing. "One document, one truth, latest version wins for its own claims" matches what an author of an evolving document means by saving a new version, while the evidence-subset rule preserves the one thing conflicts are actually for: two independent sources that disagree.

**Revisit if.** Users need two live documents with one filename (a per-ingest lineage override flag becomes worth its cognitive cost), or retire-on-drop proves too aggressive for partial documents (e.g. ingesting a one-section excerpt would retire everything else from that lineage — if excerpt ingestion becomes a real flow, "declarative about its own claims" needs a scope narrower than the whole document), or superseded rows accumulate enough to want a prune command alongside backups' keep-N.

## RFC-029: Company-attached feeds — no person in the loop

**Decision.** `wingman company add-feed "<name>" <url>` (MCP: `company_feed(action=attach|list|remove|fetch)`) attaches a blog/newsroom feed directly to a company. Found in live use: feeds were person-keyed throughout, so following a company's blog meant inventing a placeholder human and org-tagging their feed — a workaround an agent actually proposed mid-session. The fix formalizes the placeholder instead of fighting the data model: a **company anchor**, a system-owned Person row whose id is the company's `__company__{key}` — the reserved namespace company POV cards already use (RFC-016) — named "<Company> (company)". Feeds attached through it are forced to organization attribution with the company as org_name, so provenance stays honest: posts belong to the company, never to a fictional byline. The entire person-keyed pipeline — fetch/dedupe (RFC-009/011), external documents, news, themes (RFC-016), dossiers, search — works unchanged on top. Anchors are invisible where people are: filtered from `people list` (CLI and MCP) and from the dossier's "People watched here" (their documents still count, and their feeds render under "Organization sources"); `people rename/delete/fix` refuse them with a pointer to the company surface; `company rename` re-keys the anchor and carries its documents and news along; `company delete` removes it and everything keyed to it. Overnight runs fetch a followed company's feeds before the themes pass, and fresh posts produce a digest action.

**Alternatives.** A first-class company entity with its own feeds table (the honest long-term shape, but it duplicates the person pipeline — documents, FTS, embeddings, news, fetch — for one attribution difference; the anchor gets identical behavior for a fraction of the surface, and a future company entity can absorb anchors mechanically since they're already keyed by company); keeping the placeholder-person workaround documented but informal (leaves listings lying about who's a person and leaves rename/delete able to orphan company data); attaching feeds to `company_sources` (RFC-015's research plumbing snapshots pages and diffs links — feeds need item-level parse, dedupe, and document storage, which is the people pipeline, not the research one).

**Rationale.** Companies publish; people publish; Wingman cared about the difference in exactly the wrong place. The signal the user wants — "Cursor shipped something" — should not require pretending a human wrote it. Reusing the `__company__` namespace means one reserved-id convention covers every company-shaped thing riding person-shaped storage, and the attribution invariant (org-attributed, org_name always set) keeps the evidence layer honest about whose words these are.

**Revisit if.** A third company-shaped rider on person storage appears (that's the trigger to design the first-class company entity and migrate anchors into it), or anchor visibility rules grow special cases beyond list-filtering (a sign the disguise is leaking), or company feeds need per-feed labels/freshness policy diverging from person feeds.

## RFC-030: The application answer bank — refined Q+A+context, reused across applications

**Decision.** `wingman answers` (MCP: `answer_bank(action=find|save|list|show|remove)`) stores the product of application work that previously evaporated: the question as asked, the answer the user refined until it was concise and theirs, and the application context (company, role title, date) it was refined for. The refinement itself is conversational and stays in the client — the tool's docstring carries the protocol, RFC-025-style: when the user announces an application and pastes questions, the connected model must (1) call `find` first and offer any similar already-banked answer as the starting point, (2) iterate with the user — AskUserQuestion where the client supports it — until the user confirms the wording, never saving a one-shot draft, and (3) only then `save` the triple. Revision by id keeps the record's identity and context: a re-refined answer is the same bank entry, better. Records live in the workspace database with an FTS index over question and answer; `find` runs a crash-proof OR-token query (#68 discipline) so "why do you want to work at Cursor" recalls the answer refined for Woven; banked answers also surface in unified workspace search (RFC-022) as their own store.

**Alternatives.** Markdown files under reports/ (greppable but unsearchable-by-similarity, unrevisable-in-place, and invisible to the search interleave; the bank's whole value is recall, which is a query problem); storing draft history per answer (the refined result is the asset — history is conversation, and telemetry already journals conversations when the user opts in); auto-saving model drafts without the confirmation gate (fills the bank with wording the user never owned, which poisons recall — the gate is what makes a recalled answer trustworthy enough to reuse).

**Rationale.** Application questions repeat — "why us," "describe a hard problem," "tell us about a production incident" — but the twenty minutes spent tightening an answer was being spent again for every application. Persisting only user-confirmed wording turns each application into training data for the next one, in the user's own voice, with provenance (which company, which role, when) attached.

**Revisit if.** The bank grows enough that OR-token recall gets noisy (the RFC-010 semantic pass over answers is the upgrade, same shape as search's), or answers want linking to opportunities/packs (an application timeline is a Phase 9 post-mortem concern), or a second interactive protocol lands in a docstring (two is a pattern — extract a shared protocol convention).

## RFC-031: Digest action triage — the user's verdicts stop the roll-over

**Decision.** The morning digest's action list was accumulating "uninteresting" items day after day because nothing remembered what the user had already decided to ignore. Wingman now remembers — and deliberately does not guess. Every digest action carries a stable **key** (same kind of action about the same subject, same key across runs: `company-posts:{company}`, `person-posts:{name}`, `research:{company}:{url}`, `fix-source:{company}:{url}`), printed on a `key:` line under the action. `wingman actions mute <key>` suppresses that key forever; `snooze <key> --days N` hides it until a date (expired snoozes prune themselves on read); `unmute` reverses; `list` shows standing verdicts. Overnight assembly applies the verdicts before the action cap — a suppressed item can never crowd out a live one — and the digest notes how many actions were suppressed so the filter is always visible, never silent. The MCP twin `action_triage` carries the interactive protocol in its docstring (RFC-025/030 convention): when the user asks to triage their digest, the connected client walks the action list item by item — AskUserQuestion where available, Keep / Mute forever / Snooze per item — and records each verdict; it never mutes on its own judgment. What counts as uninteresting is defined by the user, one verdict at a time, and those verdicts ARE the filtering logic.

**Alternatives.** Heuristic decay (auto-drop after N appearances — deletes exactly the slow-burning items a job search lives on, and the user never finds out what was dropped); model-judged interestingness (unauditable, and drifts with every provider change; the digest is a trust surface); per-day dismissals with no memory (that's the roll-over problem restated); a "seen count" annotation without suppression (information without relief).

**Rationale.** A daily brief earns its keep by what it leaves out, but only the reader knows what deserves leaving out. Persistent, reversible, per-key verdicts give the user an editor's spike instead of an inbox: the "review what changed" page they never care about disappears once, forever, with one word — and the visible suppression count keeps the system honest about what it's not showing.

**Revisit if.** Verdict counts grow into the dozens (pattern-level mutes — "everything about company X except openings" — earn a rule syntax), or the Phase 5 scored brief lands (scoring and suppression should compose: verdicts as a hard filter before ranking, not a score input), or users want mute-from-the-digest-file (an annotation syntax parsed back would be a new consent surface).

## RFC-032: Managing the server process — pidfile-verified stop, and wingman-ctl

**Decision.** `wingman-mcp --http` now writes a pidfile (`mcp-http.pid`, cleared on clean exit), and `wingman mcp status|stop` manages exactly that process: stop is deterministic — no pattern-matching over the process table — and every pidfile read verifies the recorded pid is alive **and** still a wingman-mcp before trusting it, so a stale file left by a crash or reboot can never signal an innocent process that reused the pid. Stop is TERM, a five-second grace, then KILL; both commands are deliberately CLI-only (an RFC-008 parity exception with the same shape as restore and keys: an MCP tool that stops the server carrying the call would sever its own connection mid-reply). The stdio servers Claude Desktop and CLI sessions spawn are **never** touched by `wingman mcp stop` — they are other applications' children, and killing them breaks live sessions wingman doesn't own. The place where killing them *is* the point — upgrades — gets `scripts/wingman-ctl`: `status` (what's running, who owns each process, what's safe to stop), `start`/`stop` (the HTTP server via the pidfile commands), `stop-all` (adds the client-owned servers, with a consent prompt and a plain statement of which clients must be restarted), and `upgrade` (pull → reinstall → stop-all → restart the HTTP server only if it was running, ordered so everything that comes back runs the new build and a failed pull touches nothing).

**Alternatives.** A broad `wingman shutdown` killing every wingman process (a tool whose posture is "nothing happens implicitly" reaching out to kill other applications' subprocesses is surprising exactly where trust matters, and it can't do the part that matters after — restarting the clients); pgrep/pkill patterns instead of a pidfile (heuristic where determinism is available, and the reason `stop-all` lives in a script that shows its reasoning rather than in the CLI); a supervisor dependency (launchd/systemd already exist per-platform and are documented in INSTALL/SERVER — wingman should compose with them, not replace them).

**Rationale.** Upgrades were leaving stale processes running old code, and the safe kill required knowing which of four identical-looking `wingman-mcp` processes belonged to whom. The split follows ownership: wingman manages the one process the user starts, the script orchestrates the boundary-crossing case with consent, and clients keep owning theirs.

**Revisit if.** Clients migrate to the HTTP server (stdio servers stop existing and `stop-all` decays to `stop`), or the pidfile needs to carry more (port, started-at) for multi-instance setups, or launchd/systemd management becomes the norm (then `wingman mcp` should learn to detect "managed by supervisor — use launchctl/systemctl" and say so instead of signalling).

## RFC-033: The read surface — a small web UI for glancing and files

**Decision.** `wingman-mcp --http` now also serves `/ui/<token>` — the first surface that is neither CLI nor MCP, scoped by one sentence: conversation is for thinking; the web page is for what conversation is bad at, glancing and files. It serves what the workspace already renders — today's digest (the styled HTML twin) as the landing link, then every digest, pack, dossier, and export under `reports/`, grouped and dated — plus a single upload form for the two artifacts that cannot travel through a chat: a LinkedIn export zip and a resume file. Uploads are size-capped, land in the inbox with an archive stamp like any other ingested artifact, and flow through the ordinary pipelines (`import_linkedin`, `ingest_resume` — lineage, supersede, and evidence rules all apply); the result page is the ingest report. The security shape is RFC-017's, reused rather than invented: the same capability-path token (constant-time compared; wrong token and wrong path return the same plain 404, so there is no token oracle), loopback bind, the user's own tunnel for reach. File serving is confined to `reports/` by resolved-path check with an allow-listed suffix set — the database, inbox, and token file next door are structurally unreachable. This is a deliberate RFC-008 parity exception in the third direction: the UI must never grow write surfaces beyond the upload form (no search, no triage buttons, no graph browsing) — the conversational client is that interface, and duplicating it here is the road to the hosted-product pivot that stays parked.

**Alternatives.** A separate web app with accounts and sessions (a security surface wingman deliberately doesn't have; the capability token is already the session, and a second auth system would be the most dangerous code in the repo); serving raw markdown only (the styled twins exist precisely to be read; a UI that ignores them re-creates the problem); pushing uploads through MCP (a zip cannot be pasted into a chat, and a resume traveling through model context to reach the ingest pipeline is a needless detour for a file the pipeline reads directly); building nothing (the second-user onboarding then requires SSH for every artifact, which is exactly the friction this removes).

**Rationale.** The multi-instance design's second user needs a path onto the system that never requires a terminal, and the first user wants the digest on a phone. Both are read-and-file problems. Serving the artifacts the workspace already produces, behind the token it already has, on the server it already runs, is the smallest UI that can exist — and the scope sentence in its module docstring is the fence that keeps it smallest.

**Revisit if.** The key-entry form gets its real customer (a second user who balks at one SSH session — it belongs behind the same token, writing only the two known env var names), or anyone proposes an interactive feature for the UI (the answer is "that's the conversational client's job" until a case survives that sentence), or a third artifact class needs uploading (a general inbox-drop endpoint may then beat per-type handling).

## RFC-034: Validated key intake — the workspace key file and the web form

**Decision.** The web UI (RFC-033) gains the key-entry form, and it never stores an unverified secret: each submitted key is checked against its own provider first — Anthropic via `models.list` (free, authenticated), Voyage via one minimal embed — and a key that fails verification is reported and discarded, never written. Verified keys land in a new third resolution source, the workspace key file (`keys.env`, 0600, values never logged): RFC-019's order becomes **environment > Keychain > workspace file**, with a set environment variable still winning absolutely — the form says so when a stored key is shadowed by the service environment, instead of pretending. Because hydration also updates the running process's environment when the variable is unset, a key entered through the form is live immediately, no service restart. This completes the no-terminal second-user path: with RFC-033's uploads plus this form, onboarding needs SSH exactly zero times.

**Alternatives.** Storing first and letting the next model call fail (turns a typo into a mystery failure an hour later in an overnight run — verification at intake converts it into an immediate, named error at the moment the user can fix it); a syntactic prefix check only (`sk-ant-…` proves shape, not validity — revoked and truncated keys pass it); pasting keys through the conversational client (deliberately rejected in RFC-019 and again here: a secret in chat transits model context; the form posts over the user's own TLS tunnel straight to their own instance); Linux libsecret support for `wingman keys` (a keyring dependency for headless servers where a 0600 file inside the already-private workspace is the platform norm).

**Rationale.** "Test the key when it's uploaded" is the difference between a form and a trap: the only person who can fix a bad key is the one currently holding it, so validity must be judged then, against the real provider, with the real answer. The workspace file keeps the secret exactly as protected as everything else in the workspace, and the env-wins invariant survives untouched — the form extends RFC-019's ladder downward rather than adding a competing truth.

**Revisit if.** A provider adds a free dedicated key-introspection endpoint (swap the probes), or key rotation wants a scheduled re-verification ("your Voyage key stopped working" belongs in doctor and the digest, not in a 3 a.m. traceback), or a third key joins KNOWN_KEYS (the form and validators are table-driven; a third row should be one dict entry each).

## RFC-035: Job interest scoring — embedding recall, an explicit criteria doc, a judged brief

**Decision.** Wingman identifies the jobs the user would care about in three layers, each auditable, none of them guessing in the dark. **Recall:** every posting the feeds surface is embedded (the RFC-010 Voyage machinery, reused) and ranked by cosine against anchor sets derived from the user's own acts — packs built and assessments pursued as positives, muted and rejected items (RFC-031 verdicts) as negatives. Recall is cheap, runs inside overnight, and only decides what earns a closer look. **Judgment:** the top survivors are scored by a model judge against `job-criteria.md`, a small human-readable workspace document holding hard filters (location, seniority band, comp floor), weighted wants, and explicit anti-signals. A posting that fails a hard filter never reaches the brief regardless of similarity; every score arrives with quotes from the posting as evidence, per the evidence-gate ethos everywhere else in wingman. **Learning:** verdicts on the scored brief reuse the RFC-031 triage keys (interested / skip, one word of why), and a periodic contrast pass — the jobs pursued against the jobs dismissed — *proposes* edits to the criteria doc, which the user approves or rejects; it never applies its own conclusions. The criteria doc, not any latent vector, is the source of truth for "what I care about": correcting the system is editing a paragraph, not retraining anything. Seeding is an interview, docstring-protocol style (RFC-025/030/031 convention): the connected client interviews the user — AskUserQuestion where the client supports it — and writes the first `job-criteria.md` only after the user confirms the wording.

**Alternatives.** Pure vector-similarity ranking (similarity measures *like my past*, not *what I want* — it cannot express hard constraints or asymmetric preferences: "wants platform scope" and "done with platform scope" embed nearly identically, and the scheme confidently resurfaces jobs the user has outgrown); key-phrase extraction from similarity matrices — clustering plus discriminative-term extraction (a large-n technique: at the tens of labeled examples a job search actually produces, the extracted phrases are noise wearing confidence, and the output is a term-weight vector nobody can read, edit, or argue with); training a preference classifier on verdicts (same sample starvation, plus provider drift — and the brief is a trust surface, RFC-031's argument verbatim); learning preferences implicitly with no criteria doc (when the system is wrong there is nothing to correct except by generating more labeled misery).

**Rationale.** The vector-space instinct is right and half-wired already — embeddings are the only recall layer that survives job-title vocabulary ("Member of Technical Staff" / "Staff ML Engineer" / "Applied Scientist"). The correction is where phrases live: vectors recall, they do not decide. Moving "what I care about" into an explicit document makes the sample-size problem irrelevant, makes every layer legible (anchors are the user's own acts, criteria are their own words, scores carry quotes), and gives the learning loop a consent gate instead of silent drift. This is Phase 5's scored daily brief, with the feedback loop that makes it sharpen instead of stale.

**Revisit if.** Verdict volume reaches the hundreds (a trained reranker becomes viable — as a recall aid, never as the judge), or the criteria doc sprawls past a page (section it per role-family before inventing weights syntax), or postings outpace the judge budget (cap scored items per run and say so in the brief, RFC-031's visible-suppression discipline), or the contrast pass tempts anyone toward auto-apply (it proposes; the approval gate is the design).

## RFC-036: Requirement resolution — captured Q&A evidence, and recall before asking

**Decision.** Two halves of one workflow (#96, #98). **Capture:** `qa_capture` (CLI: `wingman qa "<question>" "<answer>"`) persists a clarifying Q&A as durable profile evidence with zero model calls: the pair is written to the inbox as a source file, recorded as a SourceRecord (`source_type qa_note`, `document_key qa:<question-key>`), and becomes one ACTIVE ProfileItem — name: the question; detail and evidence quote: the answer VERBATIM, which resolves trivially against the file just written, so evidence-before-assertion holds without an extraction pass. Re-answering the same question flows through the ordinary RFC-028 lineage machinery: the earlier answer is superseded, never stacked as a conflict — the question is an evolving one-claim document the user keeps current. **Recall:** `resolve_requirement` returns what the workspace already knows about one requirement — similar banked answers (RFC-030) plus the unified search interleave (RFC-022) — and its docstring carries the order-of-operations protocol (RFC-025/030/031/035 convention): one requirement at a time; recall FIRST and offer the close match; ask the user only when nothing fits (AskUserQuestion where supported); offer `qa_capture` for the fresh answer so the gap never resurfaces; capture substance as terse raw bullets — prose refinement is a later phase, never this one. The capture protocol has its own gate: the connected model shows the exact text to be stored and saves only after the user agrees — their words, verbatim, never a silent paraphrase.

**Alternatives.** Routing answers through the resume/source-of-truth re-ingest (a full extraction pass plus a model call to persist one sentence the user just said — and the answer isn't part of any document they maintain); storing in the answer bank (RFC-030 stores refined wording for application forms; this is raw substance for assessment evidence — different lifecycle, different consumer, and the bank's confirmation gate exists precisely because its records ARE wording); free-text notes files (invisible to assess, which cites profile items by ID); auto-capturing every user reply in an assess conversation (consent theater — the offer-and-confirm gate is what makes the stored record trustworthy).

**Rationale.** `wingman assess` already tells the user to "note the answer" with no mechanism to do so — the answer evaporated with the chat and the same Unknown resurfaced on the next role. Making the capture deterministic (no model between the user's words and the stored evidence) keeps the trust chain one link long, and making recall mandatory-first turns accumulated answers into fewer questions over time: the system gets quieter as it learns, which is the whole point.

**Revisit if.** Captured items want richer typing than the four profile kinds (a "statement" kind is a schema migration with renderer fan-out — wait for real pressure), or requirement recall wants semantic ranking (RFC-010's embedding pass over qa notes, same shape as answers'), or a guided end-to-end resolution loop (iterate every Unknown of an opportunity in one session) earns its own surface — build it on these two primitives, not beside them.

## RFC-037: Relationship objectives — the thesis per person, the tickler, the log, the review

**Decision.** Every watched person can carry a **relationship objective**: why the user is investing (the goal), what they believe about the path (the thesis), and the next intended move — the user's own confirmed words, persisted, editable, seeded and revised by the angles interview (docstring-protocol convention, RFC-025/030/031/035/036: the connected client interviews, drafts, shows, and saves only after the user confirms the wording). Four pieces build on machinery that already exists. **The objective doc** is the source of truth for that relationship, RFC-035-style: any model proposal about the person must cite it plus evidence (their writing, logged interactions) — never a free-floating judgment. **The tickler** is objective-driven digest actions keyed `relationship:{person}` — "the Brandon objective is peer exchange; yesterday's post is the opening" — riding RFC-031 verdicts, where snooze IS the tickler cadence and mute ends the thread's nudges. Today's digest only reacts to events (new posts); objectives make it also act on intent. **The interaction log** records what actually happened ("coffee with R., discussed X") the qa_capture way (RFC-036): deterministic, person-attributed, the user's words as the evidence quote, zero model calls — the raw material every future brief and thesis revision cites. **The review** is the RFC-035 loop re-aimed: when objectives go stale, the digest nudges a relationship review (triageable key, user-set cadence via snooze); the interview walks each stale objective — strengthened, stalled, thesis wrong? — Keep / Update, confirmed wording only.

**Alternatives.** A confidence-scored next-best-action engine (RFC-031's rejection applies verbatim: unauditable, provider-drifting, and the digest is a trust surface — a recommender may PROPOSE against the user's written thesis with quoted evidence, never rank by its own confidence); momentum metrics now ("measure momentum, not elapsed time" requires interaction data — email, replies, meetings — that wingman deliberately lacks pending the consent design in #53/Phase 8; a metric without measurement is confident fiction); replacing application metrics with relationship metrics (false opposition — the same thread is often both a relationship and a funnel; relationship health is an added axis); relationship graph visualization (RFC-033's scope fence: the web page is for glancing and files, and graph exploration is Woven's job); interest inference (POV cards already extract STATED interests with verbatim quotes; inferring unstated ones is guessing about people, which is worse than guessing about jobs); intro recommendations (already tracked as the Woven warm-path integration, #81 — one implementation, not two).

**Rationale.** A week of angles conversations (who is this person, why engage, what's the play) produced exactly the objective/thesis/next-move triple — and every word evaporated into chat while the mechanical outputs (feeds, briefs) persisted. The asymmetry is backwards: the judgment is the asset. Persisting it under the same trust architecture as job scoring — user-authored doc decides, model proposes with evidence, verdicts filter, review loop keeps it current — turns each relationship into something wingman can actually help operate, without ever guessing what the user wants from another human being.

**Revisit if.** Interaction data becomes importable (the #53 consent RFC lands) — then momentum becomes measurable and the review can cite it; or objectives multiply past the dozens (per-person doc files vs a table column becomes a real schema question); or the Woven integration (#81) lands (warm paths should inform theses, and the objective doc is where an intro recommendation would cite its justification); or a second user's objectives need isolation guarantees beyond the workspace boundary (they shouldn't — but verify before sharing an instance).

## RFC-038: The changelog — a generated static file, not a live git read

**Decision.** Wingman's own development activity — "what's new in wingman?" — is now visible as a fifth web UI tab (`Changelog (N new today / M last 7 days)`) and an MCP tool (`changelog`), sourced from merged PR titles, verbatim, dated newest-first, filtered by a small deterministic pattern list (`src/wingman/domain/changelog.py: is_user_facing`) that excludes only titles unambiguously reading as internal repo bookkeeping — session-snapshot notes, review-remediation follow-ups, admin-page-only fixes. No model rewrite; when a title's status is unclear it stays in, per the issue's own instruction.

The consequential choice is where the data comes from at runtime. This repo's merge commits already carry the PR title and number in the subject (`git log --first-parent` walks a clean one-entry-per-PR mainline), which made a live `git log` read the obvious first idea — zero new egress, fits RFC-009's explicit-invocation posture. It does not survive contact with how wingman is actually installed: `uv tool install` — both the git-URL form and the "install from a local checkout" form docs/INSTALL.md documents — builds a wheel and installs it into an isolated tool venv. Checked empirically against a real running instance (`/Users/…/.local/share/uv/tools/wingman`, installed via `uv tool install .` from this checkout, the exact documented path): the installed tree contains a plain copy of `wingman/` under `site-packages`, no `.git` anywhere. hatch-vcs bakes the version string into the wheel's `dist-info` name at *build* time; nothing about that leaves live git history reachable at *run* time. A server process — MCP stdio, MCP HTTP, or the web UI — has no git history to read, on a Mac install or the documented lobster server install alike.

So the source of truth is `src/wingman/changelog_data.py`, a committed, plain Python module — packaged the same as any other file under `src/wingman` (`pyproject.toml`'s `packages = ["src/wingman"]`, no separate data-file wiring needed) — holding a static tuple of `(date, pr, title)`. It is regenerated by `scripts/generate_changelog.py`, run by hand before a release (the same moment `docs/RELEASES.md` is written), which walks `git log --first-parent` in the dev checkout (where `.git` unquestionably exists) and writes the file, `ruff format`-ed for consistency. The domain module (`is_user_facing`, count math) stays separate from the generated data so the filtering logic is unit-testable without regenerating anything.

**Alternatives.** Live `git log` at runtime (fails on every documented install path, as verified above — not a hypothetical edge case); `gh pr list --state merged` at runtime (a new network call and, per RFC-009's spirit, a new credential-management surface — `gh` auth — for a server process that has otherwise never needed one; also breaks offline); `gh pr list` *at generation time* instead of `git log` (would give slightly more accurate merge timestamps than a commit's own date, but adds a `gh`-auth dependency to the generation script for a repo whose commit subjects already carry the same title/number pair — not worth it unless the commit-subject convention breaks); shipping the changelog as a separate non-Python data file (JSON/YAML) (works, but needs explicit wheel packaging config `hatch-vcs`/`hatchling` doesn't already provide for free, where a `.py` module needs none).

**Rationale.** The static-file approach is the only one of the options that is simultaneously zero-runtime-egress (RFC-009 in spirit, even though this data isn't privacy-sensitive), zero-new-credential (nothing for `wingman keys`/RFC-019 to manage), and correct on every install path this project documents and actually uses — verified against a real install rather than assumed from the docs.

**Revisit if.** The commit-subject convention (`Title (#N)` / `Merge pull request #N from …` with the PR title as the merge commit's body) stops holding — a squash-merge setting change, say — in which case the generation script's two regexes need a third case, or a `gh pr list` pass at generation time becomes the more accurate source; or the filter's small pattern list starts visibly hiding real changes (the fix is deleting or narrowing a pattern, not building a classifier — RFC-004's "no model for exact matching / deterministic dedup" ethos applies here too).

**Addendum (#202, 2026-08-04).** "Regenerated by hand before a release" turned out to mean, in practice, "regenerated whenever someone remembers" — the file went 61 merged PRs stale with no signal, and `changelog` reported a confident "0 new" instead of an unverified one, which a downstream agent relayed as fact. The runtime constraint above didn't change (still no live git access), so the fix keeps the static-file shape and adds three things: the generator now stamps the exact commit it ran at (`changelog_data.GENERATED_FROM_COMMIT`); `render_changelog` compares that against the running build's own hatch-vcs-embedded commit hash and leads with a plain warning on mismatch, rather than silently rendering counts from data it can't vouch for; and `wingman-ctl upgrade`/`cycle` now regenerate the file automatically on every upgrade (best-effort — never blocks the upgrade itself), so drift should stay at most one commit in the common case. A CI test (`tests/unit/test_changelog_freshness.py`) is the backstop for whenever that automation doesn't run, failing loudly if the committed file falls more than a generous margin behind `HEAD`.

## RFC-039: The guided diagnostic ladder — `wingman doctor --deep`

**Decision.** A live incident (dhk's own instance silently down for hours behind a stray process bound to the wrong `--port`) exposed the actual gap in RFC-032's pidfile verification: it confirms a recorded pid is alive and named `wingman-mcp`, never that it is bound to the port it claims. A second incident (both instances down simultaneously) added three more concrete failure modes: a cross-account port squatter that neither account's own status check could see; `lsof -i :<port>` (no `-n`) hanging on a reverse-DNS lookup; and systemd's own restart-rate-limit silently no-oping a plain `restart`. `wingman doctor --deep` is a five-step ladder addressing all four, in the same git-rebase-style UX as the incident's own manual process: each invocation evaluates and prints exactly one step's result and one concrete next action, then stops. **Step 1** (`src/wingman/infrastructure/portcheck.py`) cross-checks the pidfile's recorded pid against who is *actually* `LISTEN`ing on the port — via `ss -H -tlnp` first (never resolves DNS, so it cannot reproduce the hang), falling back to `lsof -n -P` (the two flags whose absence caused it) only where `ss` doesn't exist (macOS), with a hard subprocess timeout either way as a backstop. The port lookup is a separate call from identity resolution (`ps -o user=,command=`), so a foreign account's process that can't be identified is still reported as *present and squatting* rather than silently dropped — the exact #138 scenario. **Step 2/3** curl the existing unauthenticated `/health` route (RFC-033) over loopback, then over the detected tunnel host — isolating "process is unhealthy" from "tunnel routing is broken." **Step 4** surfaces process state and a log tail (or `journalctl` for a systemd-managed unit) automatically, so the operator never has to know the log path. **Step 5** (`systemd_check.py`) detects `Result=start-limit-hit` on the `wingman-mcp.service` unit and names the exact `reset-failed && restart` fix, without running it — every step prints, none of them mutate, matching the rest of the ladder's "diagnose and instruct" shape rather than taking action on the operator's behalf. Progress is a persisted cursor only (`doctor-deep-state.json`); each step's condition is re-evaluated live on every call rather than remembered, so "did the operator's fix work" is answered by re-probing, not by a manual checkbox — a bare rerun naturally advances once the underlying fact changes, and `--continue` force-advances past a step that is only informational or whose fix happens outside this process.

**Alternatives.** Auto-running the fixes (`kill`ing a squatting pid, calling `systemctl reset-failed`) instead of printing them (rejected: the ladder's step 1 finding is sometimes "someone else's live process," and a diagnostic tool that can decide to kill a process it doesn't recognize is the exact tool that could have caused, not caught, the incident); dumping the whole ladder in one shot (the #137 request explicitly asks for one step at a time — a wall of diagnostic output is what the incident's own ad hoc 6-command ladder already was, and this exists to replace that); keeping `lsof -i` as the primary check (already disproven live — no `-n`/`-P` means an unrelated connection's reverse-DNS lookup can hang the entire diagnostic tool, worse than the problem it's diagnosing); a single non-resumable `wingman doctor --deep` that reruns all five checks every time (loses the "one instruction, stop" pacing the git-rebase framing is explicitly modeled on).

**Rationale.** Every gap this closes was a real, timed cost on a real incident — hours where `wg status` said "running" while the actual endpoint was dead, an `lsof` hang that ate a debugging session, and a systemd rate limit discovered only by reading raw `journalctl`. Encoding the ladder as re-evaluated pure steps rather than a scripted sequence of shell commands means the same logic backs both the CLI ladder and any future entry point (a web UI diagnostic view, an MCP tool) without re-deriving the port/systemd checks twice.

**Revisit if.** A sixth failure mode earns its own step (append to `_STEPS`, same shape); the ladder wants to run non-interactively for a monitoring integration (the pure `run_step`/`StepResult` functions already support that — only the CLI's one-step-per-call framing would need a `--all` escape hatch); or `--continue`'s "force past regardless of live result" semantics prove confusing in practice (the alternative is a stricter git-rebase-literal model where only an explicit user acknowledgment, not a bare rerun, can advance past a failed step).

## RFC-040: One canonical host key file — `~/.config/keys.env` in the resolution ladder

**Superseded by RFC-046** — the single flat file split into
`~/.config/wingman/{secrets.env,wingman.env}` once a second, non-secret
setting (`WINGMAN_REPO`) needed to live in the same place; the reasoning
below (a single canonical location beats per-launch-path drift) is
unchanged, only the file layout is.

**Decision.** RFC-019/034's key resolution ladder gains a fourth source, inserted between the Keychain and the workspace file: **environment > Keychain (macOS) > `~/.config/keys.env` (new) > the workspace's own `keys.env`**. `wingman.infrastructure.keys.ensure_env` now reads this host file directly — the same "hydrate whatever's absent from the environment" pass that already pulls from the Keychain and the workspace file, extended with one more step — so the CLI and MCP server both see these keys on a fresh shell with zero exports, with no systemd `EnvironmentFile=` or `.profile` sourcing required (though either still works: a real exported variable is still the top of the ladder and always wins). This directly answers a live incident: the 2026-07-22 lobster migration stalled on systemd's opaque `Result: resources` because the service's `EnvironmentFile` pointed at `~/.config/wingman.env` while the actual keys lived in shell exports set by a different coding session — two different places, silently out of sync, and nothing said so. `wingman doctor` (not `--deep`; this is a fast, always-on check) now calls the new `resolve_key_sources` and prints one line per known key naming the winning source, and turns a `FAIL` when the same key is defined in more than one source with a *different* value — a same-value duplicate is not worth a warning, but a different-value duplicate is exactly the "which file is canonical" confusion that cost real time. `docs/SERVER.md` standardizes on the file (mode 600) and switches both systemd unit templates to the dash-tolerant `EnvironmentFile=-%h/.config/keys.env` (a missing file degrades gracefully instead of the opaque `Result: resources` failure).

Reporting the *winning* source correctly required one non-obvious piece of plumbing: by the time `doctor`'s command body runs, `_bootstrap` has already called `ensure_env`, which has already copied a Keychain/host-file/workspace-file value into `os.environ` — so reading `os.environ` at report time can no longer distinguish "this was really exported" from "wingman itself just hydrated it there." `_bootstrap` now snapshots `dict(os.environ)` into a module-level `_pre_hydration_env` *before* calling `ensure_env`, and `doctor` reports against that pre-hydration snapshot instead of the live (already-mutated) environment.

**Alternatives.** Keeping `~/.config/wingman.env` as a systemd-only `EnvironmentFile` convention, undocumented as a wingman-read source (the status quo that caused the incident: it only works for whichever process was launched with that specific `EnvironmentFile=` line, so a `wingman` CLI invocation in an interactive SSH session, or an instance started via `wingman-ctl`'s `nohup` path rather than systemd, never sees it — three different launch paths, three different chances to be out of sync); making the host file the *top* of the ladder, above a real environment variable (breaks the RFC-019 invariant "an exported environment variable always wins," which existing shell exports, launchd `EnvironmentVariables`, and CI secrets all depend on); one shared file per box regardless of Unix account (defeats shape B's per-account isolation outright — `~/.config/keys.env` is deliberately *inside* `$HOME`, so shape B's "each person owns their own account" boundary keeps meaning something); silently picking a winner without reporting the losers (the ladder already resolved correctly before this change — `ensure_env`'s first-write-wins order was never actually broken — the missing piece was always visibility into *which* source won and whether another source disagreed, which is what actually costs debugging time).

**Rationale.** The resolution-order bug was never really a bug — `ensure_env`'s ladder was deterministic all along. What cost hours on 2026-07-22 was invisibility: two files existed, both plausible, and nothing said which one (if either) the running process actually used. Adding one more file without adding the source report would have made the confusion worse, not better (now three plausible files instead of two); the report is the point, and the host file is just the resolution-order entry that report needed to be honest about (a workspace-file-only ladder had nowhere to put "you keep your keys on this host, not in this one workspace" — the actual shape-B/server pattern).

**Revisit if.** A third key joins `KNOWN_KEYS` (the host-file parser and `resolve_key_sources` are both table-driven off that same dict — no new code path); Linux gains a real keyring wingman should prefer over a plain file (the host file was chosen as "the platform norm for a headless server," matching RFC-034's reasoning for the workspace file — a keyring dependency would need its own trade-off writeup); or shape C (one Unix account, N workspaces — `MULTI-INSTANCE-DESIGN.md`) turns out to need genuinely different keys per workspace on one account often enough that "use a per-service `EnvironmentFile`" stops being sufficient guidance (today it works, since a real exported variable still outranks the host file, but it's manual per instance).

## RFC-041: Per-instance self-restart, gated by that instance's own token

**Decision.** Each instance's own web UI (RFC-033) gains exactly one mutating action beyond the upload/key forms it already had: a "Restart server" button in the Manage panel, `POST {prefix}/ui/{token}/restart`, gated by that same instance's own capability token — the one already guarding `/mcp` and `/ui`, no new credential. It is reachable only by that instance's own token (never any other instance's, and never surfaced on the shared admin page, `wingman.admin`) and does exactly one thing: for a systemd-managed instance (detected via `systemctl --user is-active wingman-mcp.service` — a `--user` unit is inherently scoped to the calling account, so this check can never see or touch another account's unit), it fires `systemctl --user restart wingman-mcp.service` and returns immediately, before systemd's own restart transaction gets far enough to signal the process handling the request. For an instance not managed by systemd (an interactive `wingman-mcp --http`, or `wingman-ctl`'s nohup path), the button reports that plainly and names the manual fix, rather than attempting a self-exec or process-replacement trick that could leave the instance down instead of merely stale — there is no supervisor to bring a nohup'd process back up after this one exits, so "restart" for that launch path stays an SSH-and-`wingman-ctl` operation.

This is the considered "safer middle ground" from the original ask (issue #133): the natural next question after the admin installations page (#130) shipped was whether that shared page should also support start/stop/backup. It should not — every other part of this design keeps mutation inside each Unix user's own account boundary (`systemd --user`, own pidfile, own `wingman backup`), and wiring cross-account control into the admin page would need real privilege escalation (passwordless sudo into other accounts, or running as root) to save an SSH hop, worsening exactly the "root can read everything" caveat `MULTI-INSTANCE-DESIGN.md` already flags as a known, unaddressed risk. `wingman.admin` stays read-only + launcher, unchanged by this RFC.

**Alternatives.** Wiring start/stop/backup into the shared admin page (rejected above — the whole reason this shipped as a per-instance token-gated action instead); a shared admin credential that can restart any instance (defeats the point — the boundary this design protects is the Unix account, and a shared restart credential re-creates the cross-account control surface the admin page deliberately never got); attempting a self-restart for non-systemd instances by re-exec'ing or spawning a detached replacement (meaningfully more code, on a launch path — Mac / interactive use — that `CLAUDE.md`'s own deployment facts already note is not the served production path: "lobster's workspace is the single writer"); scheduling the actual `systemctl restart` call a second or more in the future via `asyncio.call_later` to "guarantee" the response flushes first (unnecessary complexity — `Popen` returns in a few milliseconds, well before systemd's stop/start transaction can reach the point of signaling this process, and the simpler synchronous fire-and-forget call is easier to test deterministically).

**Rationale.** Tonight's actual pain (see #137/#138) was a restart with no safe, scoped mechanism — the fallback was a manual `pgrep`/`kill` that matched a substring shared across two different Unix users' processes, nearly signaling another user's live server. A per-instance, token-gated restart button removes exactly that failure mode for the common case ("the build didn't pick up") without reopening any cross-account control surface: the token that already proves "you're allowed to read and upload to this workspace" is reused, unchanged, as "you're allowed to restart it," rather than inventing a second credential or widening the first one's scope.

**Revisit if.** A second mutating action earns its own token-gated route (`wingman backup` was explicitly named as a possible follow-up in #133, scoped out of this first cut — same shape, same route family, its own review); the nohup/nested-process launch path becomes a real production target again (Mac serving returns, or a third deployment shape emerges) and self-restart for it gets designed properly instead of staying "SSH in"; or the nothing-JS constraint on this UI (`_tabset`'s docstring) gets revisited, at which point the restart button could gain a real confirm dialog instead of relying on "restart is brief downtime, not data loss" being an acceptable risk for a single click.
## RFC-042: Scheduled upgrade-all-users, root-run and systemd-restart-aware

**Decision.** A new standalone tool, `wingman-upgrade-all` (`src/wingman/infrastructure/upgrade_all.py`, its own `[project.scripts]` entry point — deliberately NOT a subcommand of the per-workspace `wingman` CLI, which bootstraps exactly one workspace via `WINGMAN_DATA_DIR` on every invocation and has no notion of "every user on this box"), keeps every configured shape-B user's install current in one scheduled pass: per user, `git pull --ff-only`, then `uv tool install --reinstall`, then `systemctl --user restart wingman-mcp.service` — run via `sudo -u <user> env XDG_RUNTIME_DIR=/run/user/<uid> …`, the env variable being required for `systemctl --user` invoked via `sudo` from root to reach that user's own session bus at all. Each step's failure is reported with the same "nothing was touched" / "nothing was restarted" language `wingman-ctl upgrade` already uses, and stops only *that* user's sequence — `upgrade_all` iterates independently per user (with a defensive catch-all so even a buggy injected runner can't abort the loop), matching #125's explicit requirement that one broken checkout never blocks the others. Explicitly the systemd restart path, never `wingman-ctl`'s `nohup` path: #125's own finding was that running `wingman-ctl upgrade` under a systemd-managed account kills the process out from under systemd and relaunches it unmanaged, and `Restart=on-failure` won't recover a graceful stop. Scheduled via a root-owned **system** unit + timer (`docs/SERVER.md`), matching the `wingman-overnight.timer` convention but at system rather than `--user` scope, since only root can act across accounts.

The trust shape is deliberately different from RFC-041's self-restart action: that one is reachable over HTTP, gated by a per-instance token, and confined to acting on the SAME account's own instance precisely because it is network-exposed to a comparatively less-trusted caller (anyone holding that one token). This tool is never exposed over HTTP, runs only as root on a schedule root itself configures, and crosses account boundaries — but that crossing grants no NEW privilege: root already owns every file on the box regardless of whether this tool exists, so the tool is closer in spirit to `unattended-upgrades` than to a control-plane feature. It gets its own separate root-owned `uv tool install` (never sharing any user's own install or touching any workspace/key), so a failure or compromise in this tool cannot reach into a workspace's data — it only ever runs `git`/`uv`/`systemctl` commands, never opens a database or reads a key.

**Alternatives.** A `--user` timer per person, each upgrading only themselves (avoids the root/cross-account trust question entirely, but is N independent timers to set up and monitor — not "one scheduled run," and doesn't satisfy #125's actual ask of a single administrative action covering every user); wiring this into the shared admin page (`wingman.admin`) as a button (rejected on the same grounds as RFC-041 — that page is a network-reachable, lower-trust surface, and mutating other accounts from it needs real privilege escalation for no offsetting benefit over a scheduled root job the owner already controls); shelling out to `wingman-ctl upgrade` per user via `sudo -u` (the exact mechanical mismatch #125 itself identified — `wingman-ctl`'s `nohup` path fights systemd's process management on a systemd-managed account); a Python subcommand under the main `wingman` Typer app (doesn't fit — that app's bootstrap callback assumes a single resolved workspace, and this tool needs neither a workspace nor the API-key hydration every other command gets for free).

**Rationale.** The mechanical mismatch (#125's own finding) meant the obvious shortcut — reuse `wingman-ctl upgrade` — was actually wrong, not just inconvenient, on a systemd-managed account. Writing the orchestration in Python with the same injectable-runner pattern used throughout this repo's other process/system tooling (`mcp_process.py`, `portcheck.py`, `systemd_check.py`, `self_restart.py`) keeps it fully unit-testable without a real multi-user box — every command sequence, every failure branch, and the cross-user isolation guarantee are exercised in `tests/unit/test_upgrade_all.py` against a scripted runner. What isn't and can't be verified outside a real box: the actual `sudo -u`/`XDG_RUNTIME_DIR`/systemd-user-bus mechanics — that remains the one piece to confirm empirically on lobster before trusting this fully unattended, called out explicitly rather than claimed as verified.

**Revisit if.** A third shape-B user's checkout deviates from the `~/src/wingman` convention (the tool reports them as skipped rather than silently mis-locating their repo — worth a config file, `installations.toml`-style, once more than one person needs a non-default path); the live `sudo -u`/`XDG_RUNTIME_DIR` mechanics turn out not to work as documented on lobster (the one part of this design not exercised against a real multi-user systemd box — fix the wrapper in `_sudo_as`, the tests already pin the exact command shape so a fix is a small, verifiable diff); or upgrade failures want richer alerting than `journalctl` (a digest-surfaced admin notice, say) once silent per-run logs prove insufficient in practice.
## RFC-043: Warm-path lookups via Woven — on-demand, no persistence, no identity mapping

**Decision.** Wingman tracks people and companies for a job search but has no visibility into who in the user's actual network could make an introduction. Woven (a separate project, `dhk/woven`) already builds a warm-intro-path graph from pooled LinkedIn exports and exposes it as its own MCP server — pooled, multi-owner data that stays Woven's, not wingman's, to hold. `#81` asked for the bridge and flagged three open questions; this RFC resolves all three in the direction of least new surface. **Wingman becomes a live MCP *client* of Woven, on demand only** — `infrastructure/woven_client.py` opens a `streamablehttp_client` session (the same transport wingman's own `--http` server already speaks, RFC-017), calls one named tool, and closes the session; nothing is cached, nothing is written to the wingman workspace, and no periodic sync exists. Every lookup is triggered by an explicit command (`wingman people warm-path "<name>"` / `company warm-path "<name>"`, MCP twin `woven_warm_path`), so RFC-009's "the invocation is the consent" posture extends unmodified to a second local server instead of needing a new consent primitive. **Identity resolution is entirely Woven's.** Woven has no persistent node IDs — only `normalizeId(name)` and its own fuzzy `search_people`/`company_overview` matching (aliases, nicknames, typo tolerance) — so wingman does not attempt a second, worse name-matching pass on top: a tracked `Person.name` / company string goes to Woven verbatim, and whatever ambiguity or near-namesake confusion Woven's own result surfaces is shown to the user exactly as returned, never resolved silently on wingman's behalf (invariant #8, no invented familiarity). **Not wired into the overnight digest.** Overnight is unattended (RFC-018); adding a second live cross-process dependency to an unattended run is a new failure mode this RFC declines to take on until there's a concrete pull for it — on-demand-only sidesteps that question entirely rather than guessing an answer. Configuration is one environment variable, `WINGMAN_WOVEN_URL` — absent means the feature is inert with a clear message, never a crash; there is no assumed local path or port, because none has been verified against how Woven is actually deployed on the user's machine.

**Alternatives.** A periodic sync that imports Woven's graph (or a relevant slice of it) into wingman's own storage (rejected: pooled multi-owner network data is a different trust boundary than wingman's own workspace, and persisting a copy raises data-retention and staleness questions nothing here has reviewed — RFC-020 punted on interaction-history import for exactly this reason, and the same caution applies to a full relationship graph a fortiori); wingman-side identity mapping — maintaining its own `Person` ↔ Woven-node correspondence table (rejected: Woven's fuzzy matcher already exists and is tuned for this graph; a second, wingman-side matcher would only be a worse copy, and a stored mapping is one more place identity could silently go stale); folding warm-path results into `people_brief`/`company_dossier` automatically (deferred, not rejected — `people_brief`'s evidence-gate pipeline validates every claim against a stored, quoted source; Woven's answer is neither, and bolting it on as an unvalidated extra paragraph would blur a boundary the brief exists to keep sharp. A separate command keeps the provenance obvious: "this came from Woven, live, right now"); a stdio-subprocess bridge instead of HTTP (rejected for now: correct in principle, but it would require wingman to know how to launch Woven's process, which is exactly the undocumented deployment detail this RFC declines to guess at — HTTP just needs a URL the user supplies once they know where Woven is running).

**Rationale.** The three open questions in #81 all had the same shape: each admits a version that expands wingman's footprint (store data it doesn't own, invent identity resolution Woven already solved better, or add a hidden dependency to an unattended run) and a version that doesn't. Taking the narrower answer every time keeps the integration real — it works today, calling Woven's actual tools over its actual protocol — without committing to graph-staleness handling, a second identity system, or unattended-run reliability that nobody has asked for yet.

**Revisit if.** A concrete use case wants warm-path context inside the digest or a brief (the plumbing already returns plain text; the remaining work is a validation/citation story for `people_brief`, not a new network call); Woven grows persistent node IDs (the fuzzy-match-only posture was a response to their absence, not a preference); a second local MCP server wingman wants to bridge to shows up (this module's shape — config'd URL, on-demand call, no persistence — is the template, not a one-off); or `WINGMAN_WOVEN_URL` proves to need per-invocation auth (`streamablehttp_client` already accepts an `auth` parameter; the config surface would grow by one more env var, not a redesign).

## RFC-044: The heap — capture-first, unconditional; sorting deliberately deferred

**Decision.** `#113`'s full spec — drop URLs and screenshots, rate the heat, sort on demand with model-driven extraction and company clustering, route on confirmation — is a real pipeline (image handling, an extraction model call, identity disambiguation across drops) that deserves its own design pass. This RFC ships only the half that has no open design questions: **capture**. `wingman heap add <item> [<item>...]` (MCP twin `heap(action='add')`) writes each item — a URL or any short text reference — into a new `heap_items` table completely unconditionally: no fetch, no validation beyond "non-empty," no failure mode for a malformed URL, matching the issue's own acceptance criterion verbatim. Every item carries a **heat** rating (`hot`/`warm`/`cold`, default `warm`) captured at drop time and never inferred — the one piece of judgment the spec asks for that a deterministic default can supply without guessing, so capture never blocks on a question. `wingman heap show` lists everything hottest-first (`HeapItem.added_at` breaks ties within a band); `wingman heap remove <id>` drops one item by id-prefix, the same disambiguation shape as `wingman answers remove`. Overnight gains exactly one new digest action: `heap-hot`, firing once with a count when any hot item is unsorted, riding ordinary RFC-031 triage (mute turns it off, snooze sets the cadence) — the issue's "hot items nag, cold items never do" requirement, satisfied without needing classification to exist yet, since heat alone is enough to decide what nags.

**Explicitly not shipped here:** `heap sort`'s classification pass, screenshot extraction (the `extract_fast` capability class call over image content), company clustering, and confirmation-gated routing. All four require design decisions this RFC does not make — what "classify" returns and how confidently, how a screenshot's extracted claims get a source record, what a cluster boundary is when nothing has been fetched yet — and shipping a rushed first cut of any of them under time pressure would bake in guesses about a genuinely agentic pipeline. `HeapItem` has no `status`/`cluster`/`extracted` fields yet; the schema is deliberately minimal so the sort design isn't constrained by a hasty capture-phase schema decision.

**Alternatives.** Shipping a naive heuristic classifier now (regex-sniff "looks like a LinkedIn URL," "looks like a job posting domain") to get *something* for `heap sort` (rejected: the issue's actual motivating example — the 7/23 Cursor lead — was decided by a screenshot's content, not the URL shape; a heuristic classifier would look like progress while missing exactly the case that motivated the feature, and RFC-004's "no model for exact matching" cuts the other way here too — classification-with-real-signal needs the model pass, not a regex pretending to be one); storing items with a `sorted: bool` flag now so the schema doesn't need a migration later (rejected: a bool can't express "sorted into which cluster, with what confidence," so it would just be dead weight guessed at before the sort design exists — SQLite schema changes in this codebase are additive `CREATE TABLE IF NOT EXISTS` statements, cheap enough that deferring the field costs nothing); waiting to ship capture until the whole pipeline is designed (rejected: capture alone is independently useful — RFC-037's "usable vertical slices" ethos applies here too, and #113's own acceptance criteria are written as separable bullets for `heap add`/`heap show` vs. `heap sort`).

**Rationale.** The instruction to build this ("use judgment," per the issue's own sizing) is best honored by shipping the part that's actually settled — capture-is-unconditional, heat-defaults-so-it-never-blocks, hot-nags/cold-doesn't — rather than forcing decisions about extraction and clustering that the issue itself poses as open questions, not settled requirements.

**Revisit if.** Someone hits the capture-without-sort gap enough to want `heap sort` designed properly (start from the issue's screenshot-extraction acceptance criteria, likely its own RFC given the model-call and identity-disambiguation surface); the heap grows past a size where an unclustered `heap show` stops being scannable (a `--heat` filter or `--limit` is the cheap fix before clustering becomes necessary); or capture wants a second heat-independent input (e.g., an expiry date) — `HeapItem` gains a field, additive, same as every other table in this schema.

## RFC-045: New-link accumulation across research runs — the dossier revisit RFC-015 anticipated

**Decision.** `research_company()`'s per-source diff (RFC-015) already computes which links are new since the previous snapshot; that finding was previously shown once — in the CLI report and the overnight digest — and then lost, because `research_snapshots` is replace-on-refresh and only ever holds the *latest* link set. A company dossier built between two research runs therefore had nothing but a link count to show, even when several runs had each turned up a new posting. Two small additive tables close the gap: `new_link_events (company_key, url, source_url, discovered_at)`, appended to (`INSERT ... ON CONFLICT DO NOTHING`, first-sighting wins) every time `research_company` finds a link not in the previous snapshot; and `dossier_state (company_key, last_generated_at)`, a one-row-per-company cursor written every time `build_company_dossier` runs. The dossier's "Research (approved sources)" section gains a sibling, `## New since last dossier (N)`: every event with `discovered_at` after the stored cursor (or the full history, if the company has never had a dossier built), newest 20 listed with an "N earlier links not shown" tail, then the cursor advances. `remove_company_source`, `delete_company_sources`, and `move_company_sources` were extended to purge or re-key both new tables, matching the existing treatment of `research_snapshots`.

**Alternatives.** Diffing the dossier's own "last run" against "now" instead of a persisted cursor (rejected: the dossier is deterministic, local-data-only composition per RFC-012 — it has no independent notion of "since when," and inventing one at read time would be the kind of derived-and-recomputed logic the events table exists to avoid); widening `research_snapshots` into a real snapshot-per-fetch archive (rejected here, though it is RFC-015's own named revisit trigger — an archive answers "what did the page look like on date X," a much bigger surface than "what links were new," and the dossier only ever needed the latter); keeping new-link history in memory / recomputing at dossier time by walking prior digests (rejected: digests are dated Markdown files, not a queryable store, and RFC-012 already rejected coupling dossier composition to anything outside SQLite plus the workspace's own validated records); a single `last_dossier_at` timestamp with no event log, diffing the *current* snapshot's link set against some earlier saved link set (rejected: a link that appears, disappears, and reappears would either be silently missed or double-counted — an append-only event log with first-sighting-wins semantics is the deterministic answer RFC-004 asks for, not a recomputed heuristic).

**Rationale.** RFC-015 named this exact gap in its own "Revisit if" clause: "want change history rather than a latest-snapshot diff (snapshot generations become a real archive)." The dossier's actual need turned out to be narrower than a full archive — a running list of what's new since the reader last looked — so the smaller of the two shapes ships first, keeping `research_snapshots`'s replace-on-refresh contract untouched and adding exactly the accumulation the dossier's "New since last dossier" section needs to say something real instead of nothing.

**Revisit if.** Users want the full snapshot-history archive RFC-015 flagged (browsing what a page looked like on any past date, not just which links were new); the event log grows large enough that per-company history needs pruning (a retention window, or folding old events into a single "N links before \<date\>" summary row); or the digest wants to read this same accumulating history instead of its own single-run diff (then the digest's "new" section and the dossier's should likely share one code path).

## RFC-046: Split canonical host config — `wingman.env` (settings) and `secrets.env` (secrets)

**Durable decision** — not expected to be revisited casually: the resolution ladder's host file (RFC-040, `~/.config/keys.env`) splits into two files under one directory, `~/.config/wingman/wingman.env` (non-secret host/path settings) and `~/.config/wingman/secrets.env` (`ANTHROPIC_API_KEY`, `VOYAGE_API_KEY` — exactly `keys.py`'s existing `KNOWN_KEYS`), mirroring `dhk/alexandria`#31's `alexandria.env`/`secrets.env` split. `wingman.infrastructure.keys` keeps owning `secrets.env`'s steady-state path and lenient partition-on-`=` reader, unchanged in shape from RFC-040 beyond the new location — real production secrets already live there and this PR does not risk that proven parser. A new module, `wingman.infrastructure.host_config`, owns `wingman.env`: a small, table-driven `HOST_SETTINGS` frozenset (today, only `WINGMAN_REPO` — the setting `scripts/wingman-ctl` needs to find this checkout from a launch context that never exported it, e.g. cron or a fresh SSH session before `.bashrc` runs) read with a stricter, quote-aware `shlex`-based parser that raises with `file:line` context on a malformed line, since this file is hand-edited far more often than secrets.env.

This was a live production concern, not a design exercise: `wingman-ctl`'s own host-file fallback (a separate, at-review-time-still-open PR) had just started reading a `WINGMAN_REPO=` line out of the *same* `~/.config/keys.env` used for API keys — the exact non-secret-setting-in-the-secrets-file symptom RFC-040's own design (a single flat file, `KNOWN_KEYS`-shaped) was never meant to carry, and exactly what alexandria's split had already moved away from for the sibling project. Firm cutover, per explicit owner instruction: nothing in this codebase reads the old flat file in steady state once migrated — but the one-time transition itself had to be automatic and lossless, because a real, already-populated `~/.config/keys.env` exists on the owner's actual production server (lobster) right now, holding real working API keys. `wingman.infrastructure.host_config.migrate_legacy_host_file` runs unconditionally (idempotent, a few `Path.exists()` checks once already migrated) at the top of `ensure_env` and, separately and first, at both process entrypoints (`cli.main._bootstrap`, `mcp_server.main`) so each can print its own result — the CLI to stderr, the server to its log — because a migration touching someone's production keys must never be a silent background action. The migration reads every non-blank, non-comment line of the old file with the *old*, lenient parser (never the new strict one — a real file must not fail a migration just because the migration got pickier than the code that wrote it): a recognized secret name goes to `secrets.env`; everything else — a recognized setting like `WINGMAN_REPO`, or any other line a human or systemd had riding along in the old file for its double life as a systemd `EnvironmentFile` (e.g. `WINGMAN_ALLOWED_HOSTS`, `WINGMAN_TUNNEL_PORT`, both documented in `docs/SERVER.md` as valid there even though wingman's own Python ladder never parsed them) — goes to `wingman.env` verbatim, so nothing that worked via that role stops working. The old file is only ever renamed to a timestamped `keys.env.migrated-YYYYMMDD` backup, and only after both new files are written successfully; migration is skipped entirely (not attempted, not overwritten) whenever *either* new file already exists, even if the old file is still sitting right there too — that combination means a human already started or completed a manual move, and automatic migration must never guess at reconciling it. `wingman doctor` reports the current host-config layout on every run and turns that specific leftover-old-file-plus-new-layout combination into a named, non-silent check rather than papering over it.

**Alternatives.** Keeping the flat file and just documenting "don't put non-secret settings in here" (rejected — the wingman-ctl PR did exactly that under real time pressure, from a script that has no Python-side `KNOWN_KEYS` table to consult; a convention with no structural enforcement is the same failure class RFC-040 itself was created to fix, one layer up); making `wingman.env` the *only* new file, and leaving secrets inline in it too, just renamed (rejected — defeats the actual point, which is a file whose contents are safe to loosen permissions on, hand to another script, or paste into a chat without redaction, versus one that never should be); triggering migration only from `wingman init` or a dedicated `wingman migrate-host-config` command instead of automatically (rejected — `init` is not part of every invocation and a server already past its first `init` would never see it; a dedicated command is one more manual step on a production box for something that can be proven safe to do unconditionally, and the owner's explicit ask was "no separate manual step required"); a full alexandria-style `render_environment_file`/`ensure_environment_file` merge-into-existing-content mechanism (considered — alexandria's version exists to support a fully automated *installer* that repeatedly re-applies managed settings over hand-edited files; wingman has no such installer today, migration only ever writes brand-new files gated by the idempotency check above, so the merge machinery would have no caller and was left out as exactly the gold-plating the design brief warned against — the atomic-write-with-backup half of that pattern *was* kept, since migration needs it regardless); extending `HOST_SETTINGS` up front with `WINGMAN_DATA_DIR` and other `WINGMAN_*` names found in `config.py`/`mcp_server.py` (considered and scoped out — those are read from the process environment or a systemd `Environment=` line today, never from a host file, so there is no concrete driving need yet; the frozenset is where a future one gets added, one name at a time, once something actually needs it).

**Rationale.** The two files carry genuinely different trust levels and edit frequencies, and RFC-040's flat file conflated them the moment a second, non-secret setting needed a canonical home — the same shape of confusion #122 existed to resolve for keys specifically, recurring one layer up. Splitting the parsers to match (lenient/permissive for the proven secrets path, strict/quote-aware with real error messages for the newer, more-often-hand-edited settings path) follows alexandria's own precedent for exactly this shape of file, without forcing secrets.env through a stricter contract that has no driving need and only adds risk to a file already holding real production credentials.

**Revisit if.** A second non-secret setting needs recognizing in `wingman.env` (the frozenset is one line); `WINGMAN_DATA_DIR` or another `config.py`-owned setting gains a real need to be host-file-configurable rather than environment/systemd-only (extends `HOST_SETTINGS` and `load_config`'s ladder together, with its own review — not assumed here); the `wingman-ctl` PR that motivated this (open as of this writing) merges and needs a follow-up to point its own `~/.config/keys.env` grep at `~/.config/wingman/wingman.env` instead — flagged explicitly in this PR's description as a known follow-up, not done here to avoid depending on an unmerged branch; or a real automated installer is built for wingman (mirroring alexandria's `deploy/install.py`), at which point the merge-preserving `render_environment_file`/`ensure_environment_file` pattern this RFC scoped out becomes worth adding for real.

## RFC-047: A global-keys tier, and attribution-by-body-stamp for a shared GitHub credential

**Decision.** RFC-046's ladder is home-dir-scoped per account by construction — exactly what gives `dhk` and `trent` isolated `secrets.env`/`wingman.env` files, and exactly the thing that has no answer for a credential that's deliberately meant to be *the same value on every account*, not a per-account setting. Issue #205's Trent-can't-file-feature-requests gap (his account has no GitHub identity at all, by design, per #167) needed exactly that: one fine-grained PAT, scoped to `dhk/wingman`'s Issues only, shared by every account. The ladder gains one more rung: `/etc/wingman/global-secrets.env` (root-provisioned, group-readable, mode 640), inserted *below* the per-account host file so an account-specific override always wins over the shared default, never the reverse. `GITHUB_API_ISSUES_KEY` is `keys.py`'s first resident of this tier, added to `KNOWN_KEYS` alongside `ANTHROPIC_API_KEY`/`VOYAGE_API_KEY` — it gets Keychain support, `ensure_env` hydration, and `wingman doctor` reporting for free, the same generic machinery every other known key already has. `_test_github` (a cheap `GET /user` call — account identity isn't repo-scoped, so it works regardless of which repo(s) the fine-grained PAT is restricted to) slots into the existing `test_key`/`test_keys` dispatch the same way `_test_anthropic`/`_test_voyage` do.

Sharing the token trades away something real: GitHub's own "opened by" field can no longer say who actually filed an issue — it'll always show whichever account owns the PAT. `application.feature_request.stamp_operator` answers that in the body instead: a new `WINGMAN_OPERATOR_NAME` host setting (added to `host_config.HOST_SETTINGS` alongside `WINGMAN_REPO`, same table-driven mechanism) gets appended as a `Submitted by: <name>` line, once, before the body is ever shown in a preview or filed — callers stamp it exactly once and pass the same body to both `render_preview` and `file_feature_request`, so what's previewed is provably what gets filed, never a preview that lies about what's about to leave the machine (RFC-025's own gate). An account with its own GitHub identity has no need for the setting — `stamp_operator` is a no-op when it's unset, so `dhk`'s own filing behavior (or anyone who later gets their own PAT, per the per-account design this RFC's own alternative considered) is unaffected either way.

The one piece of plumbing this needed that didn't already exist: `gh` itself only recognizes `GH_TOKEN`/`GITHUB_TOKEN` natively, so `feature_request._default_runner` translates `GITHUB_API_ISSUES_KEY` (wingman's own resolved name) into `GH_TOKEN` in the subprocess's environment at the point it actually shells out — read-only, never overwritten when the key isn't set, so an account already using `gh auth login` is untouched.

**Alternatives.** A per-account PAT for every person, each under their own GitHub account (considered first, in conversation — rejected for now because Trent has no GitHub account and creating one was a bigger ask than the owner wanted to make right now; this stays the natural upgrade path later, and nothing here forecloses it — `stamp_operator` simply becomes a no-op for an account with its own identity, no migration needed); putting `GITHUB_API_ISSUES_KEY` in each account's own `secrets.env`, copied by hand to every account that needs it (rejected — works today but drifts on rotation with no single place to update it, the exact problem a "global" tier exists to solve once, rather than solving badly N times); a world-readable global file instead of a `wingman` group (rejected — a real credential, even a narrowly-scoped one, shouldn't be readable by every account on the box just because two accounts need it); enforcing "issues only, this repo only" purely via the fine-grained PAT's own scoping and skipping the GitHub-role layer (rejected — the PAT alone still allows commenting/closing/labeling beyond what `feature_request.py`'s own code calls, so the account's GitHub role (Triage, not Write) is the layer that actually enforces "no code access," the PAT scoping narrows what's possible even if the code path changes later).

**Rationale.** Two genuinely separate problems were tangled together in the original ask — "share one credential across accounts" and "still know who used it" — and RFC-046's per-account ladder had no natural answer to the first, while GitHub's own audit trail had no answer to the second once the first was solved by sharing. Splitting them into a new ladder tier (mechanical: where does the value live) and an application-level stamp (contextual: whose intent produced this issue) keeps each piece simple and keeps the existing per-account ladder's isolation guarantee completely intact — nothing about `ANTHROPIC_API_KEY`/`VOYAGE_API_KEY`'s resolution changed at all.

**Revisit if.** Trent (or anyone else) gets their own GitHub account and a personal fine-grained PAT — `stamp_operator` already degrades gracefully (no-op once `WINGMAN_OPERATOR_NAME` is unset), so the transition is additive, not a rewrite; the global tier gains a second resident beyond `GITHUB_API_ISSUES_KEY` (the file and the group already exist; nothing else needs designing); or `wingman feature-request` grows callers beyond `gh issue create` (a comment or close action would need its own review of whether the shared PAT's scope still matches — the safety argument above assumes wingman's own code stays this narrow).

## RFC-048: One shared multi-tenant process — share-nothing data, capability tokens per tenant

**Durable decision, explicitly supersedes `docs/OAUTH-MULTITENANCY-CONSIDERATION.md`'s "not yet."** That document's core argument — OS-level UID isolation between `dhk` and `trent` is currently free, and multi-tenancy would make wingman's own code the trust boundary instead of the kernel — was correct at n=2, and is not being re-derived or overturned here. What changed is the number: onboarding two more people (`jason`, a real second tenant; `bob`, an owner-controlled test/staging tenant) under shape B's one-Unix-account-per-person model means two more accounts, ports, systemd units, and an ever-growing `WINGMAN_UPGRADE_USERS` list — precisely the trigger `docs/MULTI-INSTANCE-DESIGN.md` and the OAuth document both named in their own "Revisit if" clauses: *"A third user appears… three friends is a product; the hosted-tiers assessment stops being parked."* At four tenants, the owner made the call explicitly, in daylight, as its own decision — not inferred from operational pain, matching exactly what the OAuth document asked for before this calculus should be redone.

**Decision.** One shared OS process serves every tenant. Data stays share-nothing: one SQLite DB per tenant, unchanged in shape from today, just relocated under a per-tenant `data_dir`. Auth stays capability tokens, one per tenant — no OAuth, no new login/session system (RFC-033's own reasoning, "the capability token is already the session, and a second auth system would be the most dangerous code in the repo," was re-affirmed rather than revisited). Concretely:

- **Tenant registry** (`wingman.infrastructure.tenants`): a root-owned file listing only `{slug, data_dir}` per tenant — no secrets. Tokens live where they already do (`<data_dir>/mcp-http-token`, RFC-017, unchanged — `wingman mcp --rotate-token` keeps working as an ordinary per-tenant CLI action) and API keys live where they already do (`<data_dir>/keys.env`, RFC-034, unchanged). Centralizing either would turn one file's compromise into every tenant's credentials leaking at once — exactly backwards from share-nothing. `TenantIndex` builds an in-memory `sha256(token) -> Tenant` map at startup (a plain hash lookup carries no timing signal for a 24-byte random token, unlike a linear `compare_digest` scan) and exposes `reload()` so rotating one tenant's token, or adding a tenant, never requires restarting the shared process — a restart would drop every other tenant's in-flight session.
- **Request-scoped `Config` resolution, not a rewrite of every call site.** Every MCP tool and webui handler already calls `load_config()` (`infrastructure/config.py`) exactly once per invocation, reading `WINGMAN_DATA_DIR` from `os.environ`. `load_config()` becomes dual-mode: a `contextvars.ContextVar[Config]`, bound via `tenant_config_scope(config)` for the duration of one request, wins when set; otherwise today's env-var resolution runs unchanged. A `ContextVar` is copied per asyncio task, never shared process-wide the way `os.environ` is — proven directly (`test_tenant_config_scope_is_isolated_across_concurrent_asyncio_tasks`) rather than assumed. CLI commands and stdio-mode MCP (Claude Desktop's local launch) never touch this scope at all — they stay single-workspace-per-invocation, completely unaffected.
- **The one genuinely novel mechanism, spiked and validated before committing further:** FastMCP's `streamable_http_app()` bakes a single fixed token into `settings.streamable_http_path` once at startup and exposes no hook to run tenant-resolution before its own routing. `wingman.infrastructure.tenant_asgi` sets `streamable_http_path = "{prefix}/mcp/{token}"` (a Starlette path *parameter*, matching any token) and, after FastMCP builds its app, replaces the one matching `Route`'s `.app` attribute with `TenantRoutingASGIApp` — a wrapper that reads `scope["path_params"]["token"]` (populated by Starlette's own router before a raw ASGI endpoint runs — verified against `starlette.routing.Route.matches`/`.handle`, not assumed), resolves it against the `TenantIndex`, binds that tenant's `Config` via `tenant_config_scope`, and delegates. An unrecognized token gets a 401 and is never delegated at all. This touches only `Route.path`/`.endpoint`/`.app` — long-standing public Starlette API — never an underscore-prefixed FastMCP internal, so an `mcp` package upgrade that changes FastMCP's *internal* construction of that ASGI app doesn't break this wrapper as long as `Route` stays `Route`-shaped. Validated against both a hand-built Starlette app and a *real* `server.streamable_http_app()` output, including true concurrent-request isolation via `httpx.AsyncClient`/`asyncio.gather` (`test_tenant_asgi.py`) — a go signal, not a hopeful guess.
- **Per-tenant API keys stay per-tenant-workspace files, never centralized — and a tenant with no key fails loud, never inherits a sibling's.** `Tenant.config()` resolves `anthropic_api_key`/`voyage_api_key` by reading *only* that tenant's own `keys.env` (`keys.read_workspace_keys`), never `os.environ`, never the RFC-046/047 host/global tiers (those are shared by whichever account runs the process — falling through would recreate the exact leak this closes, one layer up), and sets a new `Config.strict_provider_keys = True`. `providers.router` honors that flag by skipping `keys.resolve_provider_key`'s env-or-workspace-file fallback entirely. Two provider-level fallbacks that `Config.strict_provider_keys` alone would NOT have closed were found and fixed in the process, not assumed away: `VoyageEmbeddingProvider.embed()` had its own independent `os.environ` read inside the method body, orthogonal to what its constructor was given, and the Anthropic SDK itself falls back to env whenever `api_key=None` is passed (checked via `is not None`, not truthiness) — both providers gained a `strict: bool` parameter that suppresses their own internal env fallback, with `AnthropicProvider` passing `api_key=""` rather than omitting the argument to actually trigger the SDK's "explicit credential given" branch. Proven end-to-end, not just unit-by-unit: `test_multitenancy_e2e.py::test_tenant_with_no_key_never_inherits_a_sibling_tenants_key` sets a real `ANTHROPIC_API_KEY` in the shared process's environment (simulating an operator's leftover export) and confirms a tenant with no key of their own still gets `ProviderError`, never the leftover value.
- **This closes a hazard that was already latent in the codebase, fixed first and separately (RFC-048 "Phase 0," shipped ahead of the rest of this design as PR #207):** `keys.store_workspace_key()` used to mutate `os.environ` immediately after writing a submitted key to the workspace file — harmless with one workspace per process, but under a shared process it means one tenant's just-submitted key silently becomes *every* tenant's key for the process's remaining life. It no longer touches `os.environ` at all; `keys.resolve_provider_key()` (env-first, else workspace file, read fresh on every call) replaced the mutate-then-read pattern for the still-supported single-tenant/CLI ladder.
- **RFC-041's self-restart button is withdrawn under this model, not patched.** Its safety argument — "the token that authorizes this request is this instance's own, inside its own Unix account boundary" — depended on a boundary this design removes. Under one shared process, any tenant's own token, used exactly as RFC-041 designed, would restart every other tenant's in-flight session too. `register_ui` doesn't mount the `/restart` route at all when a tenant index is configured (`configure_tenant_index`, called before `register_ui`), `_restart_panel()` explains why instead of offering the button, and `ui_restart` itself independently refuses even if somehow reached — two layers, not one. A shared-process restart becomes an operator action outside any tenant's token scope; a supervisor-level rolling-restart replacement, if wanted later, is explicitly its own follow-up, not bundled here.
- **`admin.py`'s cross-instance installations page is deliberately left untouched**, not made tenant-aware. It exists to health-check *other processes at other ports* (shape B's shape); under one shared process there is no coherent "other instance" for the consolidated tenants to mean. It stays useful precisely because dhk/trent's still-separate shape-B processes coexist with the new shared process during the phased rollout below.
- **Overnight (RFC-018) still runs once per tenant DB**, since it's a batch job, not the live server — it needs no context-var machinery at all. `jason`/`bob` have no Unix account under this model, so "a per-account systemd-user timer" (today's pattern) doesn't extend to them; the replacement follows RFC-042's own precedent (`upgrade_all.py`'s independent-per-user loop, defensive per-tenant catch-all so one tenant's failure never blocks another) rather than inventing a new shape. Not yet built — scoped as Phase 2 work below.
- **Accepted trade-off, named rather than silently discovered:** every `@server.tool()` function is a plain (synchronous) `def`, called directly on the single asyncio event loop with no thread offload (confirmed by tracing FastMCP's own dispatch — no `anyio.to_thread.run_sync` anywhere in the vendored `mcp` package's call path). One tenant's multi-second Anthropic call serializes behind other tenants' concurrent requests. Not fixed here — `sqlite3` thread-safety and a broader async-offload design are their own project — accepted at the scoped tenant count (four). Revisit if latency complaints appear, or before a fifth tenant is added.

**Rollout (sequencing is itself part of the accepted decision, not incidental).** Phase 0 (env-mutation hazard, shipped, PR #207) and the mechanisms above (registry, dual-mode `load_config`, the ASGI wrapper, webui auth + restart-button removal) are built and tested against synthetic tenants — `dhk` and `trent` remain entirely on their existing shape-B deployment throughout, zero live-data risk. Phase 2 stands up the shared process for `jason`/`bob` only — new tenants, nothing to migrate, the lowest-risk way to prove the design against real (if new) usage, run for a real operating period before proceeding. Phase 3 migrates `dhk`/`trent`'s live data via `wingman backup`/`wingman restore` (`application/backup.py`, reused unmodified — already a consistent one-`Config`-at-a-time snapshot/restore, needs no new tooling), only after Phase 2 has run clean, with the old per-account units kept disabled-but-present as a rollback path for at least one full operating cycle before decommissioning. A bad Phase 2 outcome is the trigger to reconsider before Phase 3 ever touches live user data — not a target date.

**Alternatives.** Multi-tenancy via real login (OAuth or similar) instead of per-tenant capability tokens — rejected, per RFC-033's standing reasoning restated above; a bigger build for no corresponding gain, since the tenant count and threat model here don't need session revocation/refresh semantics a rotatable token file doesn't already give for free. A single shared multi-tenant *database* (row-level tenant scoping) instead of one SQLite file per tenant — the owner was explicit that per-tenant databases were fine ("I'm indifferent to that" was the only latitude given, toward simplicity, not away from it); share-nothing data removes an entire class of query-scoping bugs a shared schema would otherwise need to get right forever. Keeping N separate processes but adding a reverse proxy in front (partial consolidation) — doesn't reduce the actual operational surface this decision targets (still N systemd units, N ports, N upgrade-all entries) for a fraction of the benefit.

**Rationale.** Every mechanism above was chosen to make the new app-level trust surface as small and legible as possible, since that surface is precisely what this decision trades the kernel's free isolation for: a minimal registry with no secrets in it, tokens and keys read fresh from files that already existed for a different reason, one small ASGI wrapper touching only public framework API, and two independently-found-and-closed provider-level env fallbacks that a less careful pass would have left latent. Nothing here was accepted as "probably fine" — every claim in this entry has a corresponding test that exercises it directly, including the two adversarial ones that matter most: concurrent requests never cross tenant context, and a tenant with no key never inherits a leftover shared-process one.

**Revisit if.** Phase 2's real operating period surfaces a concurrency, key-isolation, or restart-blast-radius bug synthetic testing didn't catch — that's the signal to fix the mechanism before Phase 3 touches live data, not to proceed on schedule. A fifth tenant is proposed — revisit the accepted synchronous-dispatch trade-off first, not after. Anyone asks for actual shared or intersecting data across tenants ("do we both know her?") — out of scope entirely here, share-nothing is unchanged by this RFC, and that remains its own future federation design requiring per-query consent, per `docs/MULTI-INSTANCE-DESIGN.md`'s own "Revisit if." A deliberate hosted-product decision gets made (RFC-002's "hosted tiers" stop being parked) — this RFC's tenant-registry mechanism is a plausible building block, but that remains its own separate business decision, not a side effect of this one.

## RFC-049: Persona carve-off, Phase 1 — honest placeholder evidence for a rehomed profile

**Decision.** `wingman carve-off-persona <persona> <target>` (MCP: `carve_off_persona(persona, target_dir)`) is Phase 1 of #235: it gathers every ACTIVE `ProfileItem` captured under a persona in the coach's own workspace (Coaching Mode, docs/COACHING-MODE-DESIGN.md), rehomes each one as a first-person item (`persona_id` cleared, and the `interview.py`-only `" (persona:<id>)"` name suffix stripped so the target workspace's own future captures — which never produce that suffix — still match it by `name_key` instead of silently orphaning it from the dedup/supersede machinery), and seeds a TARGET workspace with them via `profile_store.persist_items` — the same dedup/supersede path every other ingestion route in this codebase already uses, exercised here rather than reinvented. `application/persona_carveoff.py` splits this into three pieces so Phase 2 (merging into an ALREADY-POPULATED target, using RFC-028's supersede/conflict rule so contradictions surface as a `CONFLICT` instead of being silently overwritten) can reuse the first two unmodified: `export_persona` (read-only — the caller's own workspace only), `seed_new_workspace` (refuses outright, `IngestError`, if the target already has any profile items — that refusal, not a merge, is Phase 1's entire scope boundary), and `carve_off_persona` (the CLI/MCP orchestrator: resolves the target directory, refuses if it equals the caller's own workspace, creates it if needed, and calls the first two).

**The evidence problem, and the choice.** `ProfileItem.evidence` is `list[EvidenceSpan]`, `min_length=1`, never optional, and each span's `source_record_id` points at a `SourceRecord` that — for every coaching capture today — was written only into the COACH's own workspace (`interview.py`'s `capture_interview_reaction`). Copying a `ProfileItem` as-is into a brand-new target workspace leaves that id dangling: nothing in the target's `source_records` table resolves it. Three options were on the table: (a) copy or synthesize a source record into the target so the reference resolves; (b) synthesize a source record that is explicit about being a stand-in, rather than resolving to something indistinguishable from a real one; (c) something else. Chosen: (a) and (b) together, because they turned out not to be in tension once actually built — for every referenced `source_record_id`, `_placeholder_record` writes ONE `SourceRecord` into the target reusing the SAME id (so no evidence span needs rewriting), `source_type="persona_carveoff_placeholder"`, and a `source_locator` that says in plain words this item was carved off from a coach's workspace, what the original record's `source_type`/`locator` were (for context), and that the original bytes were not copied — resolvable (a), and honest about its own provenance (b), at once. The evidence QUOTE itself needed no special handling either way: it already lives verbatim on the `ProfileItem` (`EvidenceSpan.quote`/`detail`), copied along with the item, and `reporting/career.py`'s citation rendering (`_cite`/footnotes) prints the quote from the `ProfileItem` and the record id as a bare string — it never dereferences the source record's own content — so citation display was already safe; the placeholder closes the *reference*-resolvability gap for callers that DO dereference (`storage.get_source_record`, e.g. `linkedin.py`'s supersession lookup), which get a real, honestly-labeled row back instead of `None`.

**Alternatives.** Copying the coach's real source record (rejected — for interview nominations it's an inbox note file containing the COACH's own capture note, which is the coach's private authorship, not the persona's; copying it into the persona's new workspace leaks material that was never the persona's to carry, for a citation feature that doesn't need it since the quote is already on the item); relaxing `EvidenceSpan.source_record_id`/`ProfileItem.evidence` to allow a dangling or optional reference (rejected — this is exactly the "evidence before assertion" / resolvable-evidence invariant AGENTS.md and RFC-028 both hold everywhere else; carving a persona off is not a reason to make evidence integrity a special case, and every future `get_source_record` caller would need its own defensive `None` check reinvented); deferring the whole evidence question by stripping evidence off carved-off items entirely (rejected outright by `ProfileItem`'s own schema — `evidence` is `min_length=1` — and would make every carved-off item literally unconstructable).

**Rationale.** The placeholder is the cheapest mechanism that keeps every existing reader of `ProfileItem.evidence`/`SourceRecord` working unmodified in the target workspace — dedup/supersede lookups, citation rendering, `wingman profile list` — while never fabricating a record that looks like it was really ingested there. "Honest about its own provenance" was the deciding property between the options: a reader who clicks through to `persona_carveoff_placeholder` gets the truth (carved off, original not copied, original type/locator for context) rather than either an error or a lie.

**Revisit if.** Phase 2 lands and finds `export_persona`'s ACTIVE-only, conflict-losers-excluded scope too narrow for the merge case (a resolved conflict might legitimately want its losing rival's evidence too, once the destination's own conflict-resolution UI can show it); a persona-scoped `ProfileItem` kind other than `INTERVIEW` starts being produced (achievement/skill/role/testimonial, per the coaching design doc's "persona-scoped" list) and needs its own name-suffix-stripping convention beyond `interview.py`'s; or placeholder records accumulate enough in real carved-off workspaces that a "these N items still cite un-migrated coach evidence" surfaced count becomes worth adding to `wingman status`.

## RFC-050: Sentiment intensity and a company-reason taxonomy on interview nominations (issue #240 v1)

**Amended by RFC-057** (issue #343): "two optional fields" below is now three — `value_statement` joins `intensity` and `company_reason` on the same capture path, with the same protocol-not-code enforcement and the same place in `persist_items`' equality check. Everything RFC-050 decides about the two enum fields themselves is unchanged.

**Decision.** `interview_react`/`wingman interview` gain two optional fields, captured alongside the existing Values/Mission-alignment nomination shape (`docs/PROFILE-BOOTSTRAP-DESIGN.md`) and persisted directly on the resulting `ProfileItem` — the capture layer for issue #240's v1 slice ("scored sentiment + company reason taxonomy"; v2's inference and v3's radar chart are separate, later PRs). **`intensity`** is a new `SentimentIntensity` `StrEnum` (`mild`/`moderate`/`strong`) on `domain.profile.ProfileItem`, applicable to every Values and Mission-alignment subtype (`values_pro/con`, `values_fallback_pro/con`, `mission_alignment_pro/con`) — never `alignment_of_perspective_*` or `network_admired`, which keep their own established shapes. It is a strength dimension layered ON TOP OF the polarity the subtype's own `_pro`/`_con` suffix already carries, not a second, independently-settable polarity axis: there is no `POSITIVE`/`NEGATIVE` value, only how strongly the already-known direction is felt. **`company_reason`** is a second new `StrEnum`, `CompanyReasonCategory` (`company`/`product`/`industry`), scoped only to the subtypes that name a company — `values_fallback_pro/con` and `mission_alignment_pro/con` — captured *alongside* the existing free-text `why`, never replacing it. Both are optional parameters on `capture_interview_reaction`/`interview_react`/`wingman interview`: **protocol-enforced, not code-enforced** — the calling agent's docstring instructs it to always ask for `intensity` on every Values/Mission-alignment capture and `company_reason` on every company-naming one, the identical enforcement class this codebase already uses for con-then-pro ordering and ask-#2-first (a docstring protocol, not a runtime gate) — but a value that IS supplied and doesn't match its enum is rejected outright, so this only tolerates *absence*, never a garbled answer. `persist_items`' dedupe/merge equality check (`application/profile_store.py`) now also compares `intensity`/`company_reason`, so a re-capture with the same `why` but a changed scale value registers as a real "updated" (RFC-028 supersession), not a false "already captured — nothing changed."

**Alternatives.** A single combined 5-value `StrEnum` spanning `strongly_negative`…`strongly_positive`, independent of the subtype's own `_pro`/`_con` polarity — rejected: redundant with, and able to silently disagree with, the polarity the subtype naming already encodes (a `values_con` capture marked "positive" would be a data-integrity bug this shape makes representable for no benefit). A bare `int` 1–5 Likert scale — rejected in favor of `StrEnum` specifically because that's this codebase's uniform precedent for every small, user's-own-call scale (`ClaimClassification`, `HeapHeat`, `FitVerdict`, `RequirementKind`) — a `StrEnum` value is self-documenting in a rendered response or JSON payload where a bare integer needs a lookup table every reader has to know. Making both fields hard-required at the `capture_interview_reaction` level, mirroring `mission_alignment`'s existing required `primary_purpose` — rejected because it would break every pre-#240 call site and test for `values_pro/con`/`values_fallback_*`/`mission_alignment_*`, none of which pass these new arguments; the softer, docstring-protocol enforcement (already this codebase's pattern for con-then-pro ordering and BP-06's echo-before-save) gets the same "always ask this" outcome in live use without a breaking API change. Storing `company_reason` only in the inbox note, the way `primary_purpose` is stored today — rejected: the issue explicitly asks for structured `ProfileItem` fields so v2's future per-person inference pass has something to query directly, not prose to re-parse.

**Rationale.** `ProfileItem`'s `payload` column is a JSON blob (`infrastructure/storage.py`), so both fields needed no migration — existing rows deserialize with `intensity=None`/`company_reason=None` by construction, which is also exactly the value every field should have for the interview subtypes this slice doesn't touch (`alignment_of_perspective_*`, `network_admired`) and for every other `ProfileItemKind` (achievement, skill, role, testimonial). Keeping `intensity` a magnitude-only enum instead of a full polarity+magnitude scale means the subtype naming stays the single source of truth for pro/con, which is exactly the same "one source of truth" discipline `ClaimClassification`+confidence already models for evidence strength elsewhere in this domain — precedent this design deliberately followed rather than inventing a parallel shape.

**Revisit if.** v2's inference pass finds `intensity`'s three levels too coarse to discriminate a per-person value dimension usefully (e.g. it wants a continuous score for radar-chart edge weighting) — that's the trigger to add a numeric field alongside the enum for that purpose, not to replace the enum, since the ordinal scale stays the right *capture* surface regardless of what a later derived field looks like. Real usage shows the docstring-protocol enforcement isn't landing — captures keep arriving with `intensity`/`company_reason` unset even when the subtype clearly calls for them — that's the trigger to reconsider hard-requiring them the way `primary_purpose` is required, accepting the breaking-change cost at that point. `company_reason`'s three categories prove too coarse for what v2 actually wants to group by — that's the trigger to extend the enum, not fork a second field alongside it.

## RFC-051: Value-dimension inference — `wingman values`/`my_values`, the v3 score contract (issue #240 v2)

**Decision.** `application/values.py`'s `build_value_profile` (CLI: `wingman values --refresh`; MCP: `my_values(refresh=True)`) reads a person's (or coaching Persona's) own accumulated `ProfileItem`s of kind `INTERVIEW` whose subtype carries RFC-050's `intensity` field (`values_pro/con`, `values_fallback_pro/con`, `mission_alignment_pro/con` — `application.interview.SENTIMENT_INTENSITY_SUBTYPES`, read from, not modified) and infers a small, named set of per-person **value axes** — issue #240's v2 slice, resolving the six design questions the issue posed:

**Points 1, 4 and 5 below are amended by RFC-056** (issue #340): the prompt is now `prompts/value_axes_v2.md`, and the SIGN of an item's contribution comes from a per-item `direction` the model states for each citation, never from the item's `_pro`/`_con` subtype suffix — reading it off the suffix inverted every axis evidenced by a condemnation. Everything else below stands.

1. **Inference mechanism.** One `synthesize_balanced` model call (`agents/values_analyst.py`, `prompts/value_axes_v1.md` — same "model proposes, code disposes" shape as `agents/pov_analyst.py`) proposes axis names, one-sentence descriptions, and which supplied `item_id`s support each one. Deterministic code then validates (an axis survives only if it cites at least one `item_id` actually supplied — unknown ids silently dropped, same guard as `pov.py`'s doc_id check) and **scores** every surviving axis — the model is never asked for, and its output is never trusted for, a number (AGENTS.md: "do not use a model for arithmetic").
2. **Minimum-data floor.** `MIN_ITEMS = 6` (mirrors `WINGMAN_INTERVIEW_MAX_PER_SUBTYPE`'s own default — "a full single subtype's worth" is the bar for having enough raw material) **and** `MIN_SUBTYPES = 2` (rules out a single lopsided subtype, e.g. six `values_pro` nominations and nothing else, from producing a profile — real axis inference needs contrast across at least two of the six eligible subtypes). Below the floor, `build_value_profile` raises `IngestError` before any model call, naming the exact deficit and pointing at `wingman interview`/`interview_react`.
3. **Axis count.** `MIN_AXES_REQUIRED = 3`, `MAX_AXES = 6` — the same "small, bounded, not a fixed preset" reasoning RFC-050 already applied to `company_reason`'s three categories. Below 3 points a radar chart (v3) barely reads as a shape; above 6 the "small set" the issue asks for stops being small. `MAX_AXES` truncates an over-eager proposal (same enforcement shape as `pov.py`'s `MAX_STANCES`); `MIN_AXES_REQUIRED` is checked on the *validated* result — too few axes survive real evidence, the whole run is rejected (nothing stored) the same way `pov.py` rejects zero surviving stances, rather than storing a thin profile.
4. **The v3 contract.** `domain.values.ValueAxis.score`: a `float` in `[-1.0, 1.0]` — the deterministic mean of its evidence's `signed_weight` (each cited item's captured `intensity`, mapped mild/moderate/strong → 1/3, 2/3, 1.0, signed by the subtype's `_pro`/`_con` suffix; an item captured before `intensity` was asked for scores as moderate rather than being dropped or forced to an extreme). `label`: a short deterministic prose bucket of the same score (`_label_for_score` — "strongly drawn to" … "mixed / ambivalent" … "strongly repelled by"), never model-proposed, so it can never disagree with the number. Both are the stable interface a later, separate v3 PR is expected to consume directly.
5. **Evidence/traceability.** Every `ValueAxis.evidence` entry (`ValueAxisEvidence`) carries the source `item_id`, `subtype`, nominee/org `target`, the verbatim `quote` (`ProfileItem.detail`), captured `intensity`, and this item's own `signed_weight` — an axis is never a bare number; every contribution to its score is individually inspectable back to a specific capture (RFC-005).
6. **Staleness.** `ValueProfile` is a stored, rebuilt-on-demand artifact — the same "rebuilt, not versioned" lifecycle `domain.pov.PovCard` already uses (a fresh `save_value_profile` call replaces the prior stored profile for that `subject_id`; no generation history). `ValueProfile.source_item_ids` records exactly which captures fed it, so `new_captures_since` answers "is this stale" deterministically (a set difference against currently-eligible items) with zero model calls; only an explicit `refresh=True`/`--refresh` actually re-invokes the model. `wingman values`/`my_values` surface the count ("N new captures since this was built") on every stored-profile read.

Storage: a new `value_profiles` table (`subject_id` unique, `payload` JSON, insert-or-replace-on-conflict — identical shape to `pov_cards`), keyed by the same `CORPUS_PERSON_ID`/`persona_card_id(...)` identity `application/pov.py` already establishes, so "your own" vs. "a persona's own" scoping (docs/COACHING-MODE-DESIGN.md's "my evidence and their point of view never mix") is reused rather than re-invented.

**Alternatives.** Asking the model to assign the score directly alongside the axis grouping — rejected outright by AGENTS.md's "do not use a model for arithmetic," and it would make the score un-auditable (no way to tell whether a 0.4 came from the evidence or the model's vibes). A fixed/standardized axis taxonomy (e.g. reusing `domain.pov.StanceDimension`) — rejected: the issue is explicit ("derive from content, we'll standardize later"; a shared axis set is out of scope here). Scoring only from the `_pro`/`_con` polarity, ignoring `intensity` entirely (a coarser, boolean-ish +1/-1 per item) — rejected: it would throw away exactly the structured signal RFC-050 was built to capture, and RFC-050's own "Revisit if" clause named this precise trigger ("v2... wants a continuous score for radar-chart edge weighting"). Treating an item's missing `intensity` as excluded from scoring (weight 0) rather than defaulted to moderate — rejected: it would silently under-count older/protocol-skipped captures relative to ones that happened to answer the strength question, biasing the score toward whichever captures are newer without saying so. Recomputing the profile live on every read instead of storing it — rejected: a per-request model call is slow and costs API usage for a value that changes only when new interview captures happen; the stored-artifact-plus-deterministic-staleness-check shape used everywhere else in this codebase (`PovCard`, `PersonDossier`) answers the same need cheaper.

**Rationale.** The score/label contract is deliberately the smallest interface that is both auditable (every number traces to specific evidence, per axis) and immediately renderable (a bounded float is exactly what a radar chart's per-axis radius needs, and the prose label serves any caller that wants text instead). Keeping axis *naming* a model judgment while keeping axis *scoring* pure arithmetic mirrors this codebase's existing division of labor everywhere a model touches a number-shaped output: `pov.py`'s quote validation is code, its stance *content* is model judgment; here, evidence *grouping* is model judgment, evidence *weighing* is code.

**Revisit if.** v3 (the radar-chart PR) finds `score`'s single float insufficient — e.g. it wants a confidence/spread value alongside the mean, since an axis backed by 2 items with opposite signs and one backed by 6 unanimous items currently produce the same "near-zero, ambivalent" shape — that's the trigger to add a second computed field (e.g. evidence count or variance) alongside `score`, not to change what `score` itself means. `MIN_ITEMS`/`MIN_SUBTYPES` prove too strict or too lax once real usage data exists (people plateauing just under the floor, or floor-clearing profiles that still read as noise) — tune the constants, not the shape of the gate. The `_INTENSITY_MAGNITUDE` default-to-moderate choice for missing `intensity` turns out to matter once RFC-050's docstring-protocol enforcement is revisited (if `intensity` becomes hard-required, the default path stops being reachable and can be deleted). Real usage wants axes compared *across* people/personas (e.g. "who on my network shares this axis") — that is a materially different, harder feature (cross-subject axis alignment, not per-subject derivation) and deserves its own design pass, not a retrofit here.

## RFC-052: SVG radar-chart rendering of a `ValueProfile` — CLI `values-chart`/MCP `values_chart` (issue #240 v3, closes #240)

**Decision.** `reporting/radar.py` adds one pure rendering function, `render_value_radar_svg(profile: ValueProfile, stale_new_captures: int = 0) -> str`, and one storage-aware wrapper, `export_value_radar(config, storage, persona=None, out_dir=None) -> Path`, plumbed through as CLI `wingman values-chart` and MCP `values_chart` — the v3 slice of issue #240, closing it. This is presentation only: no model call, no new scoring, `ValueAxis.score`/`label`/`evidence` (RFC-051's stable v3 contract) are read, never recomputed. Hand-rolled SVG built with stdlib `math` (polar coordinates) and f-string templating — AGENTS.md's minimal-dependency baseline rules out matplotlib/plotly, and SVG needs neither: it's directly viewable in a browser, embeddable via `<img>`/`<object>`, and self-contained (its `<style>` block is `design_tokens.DESIGN_TOKENS_CSS` plus a small component-rules layer, the same two-part composition `reporting.export.WINGMAN_PDF_CSS` already uses — so it picks up `prefers-color-scheme` dark mode for free, no JS).

**The signed-score-on-a-radar design question (posed directly by the issue).** A radar chart conventionally plots magnitude outward from a shared center, but `ValueAxis.score` is signed (`[-1.0, 1.0]`; negative means "repelled by," not merely "small"). Plotting `abs(score)` was rejected outright: a -0.9 axis and a +0.9 axis would draw as the identical far-from-center vertex, silently erasing the one bit of information (direction) the chart most needs to convey. The chosen remap is linear onto `[0, 1]`: `radius_fraction = (score + 1) / 2` — score -1.0 sits at the CENTER, a dashed "neutral ring" drawn at radius 0.5 marks score 0 (`_label_for_score`'s own "mixed / ambivalent" band), and the outer edge is score +1.0. This keeps the chart reading like an ordinary radar (a bigger shape still means "more/stronger") while making a repelled-from axis visually distinct from a merely-small one (it shrinks toward the center, rather than vanishing into it or mirroring its positive counterpart). The remapped radius alone still can't fully carry the sign for a quick glance, so it is never the only place the sign lives: every axis's raw signed `score` (`%+.2f`) and deterministic `label` are printed as legend text below the chart, AND carried in that axis's vertex `<title>` element (a native SVG hover tooltip, populated with `score`, `label`, `description`, and a short evidence excerpt — free per-axis inspectability an `<img>`-embedded PNG could never offer) — so the shape and the number are always cross-checkable, and hovering a point surfaces real evidence without cluttering the visual (issue's own suggestion, taken directly).

**File location.** `reports/charts/` under `config.reports_dir`, resolved by `_resolve_chart_dir` — the same "`--out` overrides, otherwise a fixed subdirectory of `reports_dir`" shape `reporting.export._resolve_out_dir` already established for `reports/pdf/`, followed rather than inventing a new convention. Filename is `{slug(subject_name)}-values-radar.svg` (`_slug` reused from `reporting.export`, the same cross-module private-import precedent `application/pack.py` already set for `_frontmatter`) — unstamped/undated, because `ValueProfile` itself is "rebuilt, not versioned" (RFC-051): a fresh chart overwrites the prior one for that subject, matching the artifact it's a picture of, not `export_company`'s dated-dossier convention.

**Refusal/staleness.** `export_value_radar` never calls a model and never builds a profile — it only reads `storage.get_value_profile(subject_id)`. No stored profile raises `IngestError` ("no value profile built for {subject} yet — run 'wingman values --refresh' ... first") before anything is rendered, reusing `application.values`'s own refusal *class* (an `IngestError` naming the exact next command) rather than inventing new error handling, exactly as the issue asked. A *stale* stored profile (`application.values.new_captures_since` > 0, reused unmodified) is NOT a refusal — it still renders, with the same "N new captures since this was built" note `wingman values`/`my_values` already print, shown both in the chart's own text (so a downloaded/shared SVG carries the warning) and in the CLI/MCP return text.

**Web UI.** No bespoke route: `webui._SERVE_TYPES` gains `.svg` → `image/svg+xml` and `webui._GROUP_NAMES` gains `"charts": "Value charts"` — two line additions — and the existing generic `_listed_files`/`_artifact_sections` machinery (already walking all of `reports_dir` by suffix for every other export type) picks the chart up automatically, listed and served exactly like a `.pdf`/`.md`/`.html` report. No inline `<img>` preview on the home page was added: no other report type gets one there either (all are link rows to `file/...`), so an SVG-specific exception would be the inconsistent choice, not the consistent one.

**Alternatives.** Plotting `abs(score)` (magnitude-only, discussed above) — rejected for erasing sign. A diverging *two-ring* chart (a full circle for positive axes, an inner circle for negative ones) — rejected as needlessly exotic for a "3-6 axes, glance at the shape" chart; the single center-to-edge remap plus a neutral ring reads as an ordinary radar chart to anyone who's seen one, which the issue's own "radar/spider chart" framing implies is the goal. A raster (PNG) export — never seriously considered: it would need a rendering library (a new dependency, explicitly ruled out) and would lose exactly the `<title>`-tooltip inspectability this design leans on. Embedding the chart inline as raw `<svg>` markup on the webui home page instead of a linked file — rejected for this slice: every other report type is a link, and inlining would be new, asymmetric webui surface area beyond what the issue scoped as "nice to have, not must-have" for v3.

**Rationale.** The whole design mirrors RFC-051's own "model proposes, code disposes; model names, code scores" division of labor one level further downstream: nothing here is a judgment call about what an axis *means* — `render_value_radar_svg` is a deterministic function of already-validated, already-scored data, so the chart can never disagree with `wingman values`'s text rendering of the same profile (both read the identical stored `ValueProfile`). Keeping the SVG self-contained (embedded `<style>`, no external stylesheet link) matches `reporting.export`'s posture of "nothing fetched at render time" (RFC-009) and means the file is exactly as portable dropped anywhere as `career.md`'s standalone Markdown is.

**Revisit if.** Axis count ever exceeds `MAX_AXES = 6` (a v2 constant change) — the fixed label-radius/legend-row geometry here was tuned for 3-6 spokes; a larger bound would need the layout constants revisited, not just axis count. Real usage wants the chart to visually distinguish *evidence volume* per axis (RFC-051's own "Revisit if" flags this as a `score` contract gap first) — once `ValueAxis` grows a confidence/spread field, this module should render it (e.g. vertex size or a shaded band) rather than ignoring it. The webui "linked file, not inline" choice reverses if a later redesign makes inline previews the norm for every report type, not just an exception carved out for charts. `<title>`-tooltip evidence excerpts prove too terse to be useful in practice — extend the excerpt or the tooltip content, not the underlying geometry.
## RFC-054: Persona carve-off, Phase 2 — merging into an already-populated target, no new flag

**Decision.** `wingman carve-off-persona <persona> <target>` (MCP: `carve_off_persona(persona, target_dir)`) now writes into a TARGET workspace that already has its own profile items, closing out #235: `seed_new_workspace`'s Phase-1 refusal (`IngestError` if `target_storage.count_profile_items() > 0`) is removed outright, with no replacement flag or confirmation gate. The command's whole body is now just: export the persona's items (`export_persona`, unchanged), then call `profile_store.persist_items` — the exact same RFC-028 dedup/supersede/conflict call every other ingestion path in this codebase (`ingest`, `linkedin` import, `interview` capture) already uses for "a new item that might collide with something already there." An item matching nothing existing is `accepted`; one matching an existing item's stored value merges new evidence in (`evidence_merged`) or is a no-op duplicate (`skipped_duplicates`); one that genuinely disagrees — same `name_key`, different `detail`/`classification`/`intensity`/`company_reason` — is never silently overwritten: it's stored as a side-by-side `ItemStatus.CONFLICT` row (`conflicts`), exactly like a second document or a LinkedIn re-import disagreeing with the profile today, visible via `wingman profile list` and settled via `wingman profile resolve <id>` (RFC-027) — no carve-off-specific resolution path, because none is needed. `render_carveoff_report` now prints every `ItemCounts` bucket that fired (added / evidence-merged / already-present / superseded / conflicts) instead of Phase 1's single "N item(s) seeded," and — only when `conflicts > 0` — an explicit line naming the count and pointing at `wingman profile list`/`resolve` against the target workspace, so a partial/contentious merge is never a quietly-successful-looking report. The CLI argument help and both docstrings (CLI, MCP) drop the "must be brand-new/empty" language and describe the merge behavior instead. One consequence of lifting the refusal needed its own fix: RFC-049's placeholder `SourceRecord`s deliberately reuse the same `record_id` on every export of the same persona, so re-carving the same persona into a target that already received an earlier carve-off of them would hit a `DuplicateRecordError` on the second placeholder insert even though nothing about the content changed; `seed_new_workspace` now skips inserting a placeholder whose id is already present in the target rather than propagating that as an unhandled exception at the CLI/MCP boundary.

**Alternatives.** A `--merge`/`--force` flag gating the non-empty-target path, so carving into a real, already-in-use profile requires an explicit opt-in distinct from the Phase-1 default — rejected. `persist_items` is already safe-by-construction for every other caller with zero extra confirmation gate: it never overwrites, it only adds, merges evidence, or produces an inspectable, reversible conflict row. Adding a gate here specifically would say carve-off's data is somehow more dangerous than a LinkedIn re-import or a second resume ingest hitting the same profile, which isn't true — both go through the identical function with identical guarantees. The gate would also just move the decision one step earlier without changing what happens: the person still has to look at `wingman profile list` afterward either way. A distinct subcommand (`carve-off-persona merge` vs. a hypothetical `carve-off-persona seed`) for the two target states — rejected: the two cases already share one code path end to end (`export_persona` → `seed_new_workspace`), and forking the command surface would be maintaining two names for a distinction `persist_items` already erases internally (an empty target is just the degenerate case where every item happens to accept). Auto-resolving carve-off conflicts by some heuristic (e.g. always prefer the carved-off/coach-captured version, or always prefer the target's own pre-existing version) — rejected outright by the issue's own acceptance criteria ("never silently overwritten; surfaced as a conflict for the person to resolve themselves") and by AGENTS.md's "never silently overwrite contradictory data."

**Rationale.** Phase 1's refusal existed only because the merge path wasn't built yet, not because merging is inherently riskier than any other ingestion route into this profile — the module's own docstring said as much ("Phase 2... via RFC-028's supersede/conflict rule"). Once `persist_items` is the thing doing the actual writing, the safety property carve-off needs (never silently overwrite) is already guaranteed by the same mechanism the rest of the codebase relies on for it, so adding a second, carve-off-specific safety mechanism on top would be redundant complexity rather than added safety. The report change matters independently of the flag decision: a merge that silently produced a conflict and said only "3 items seeded" would technically satisfy "never silently overwritten" while still leaving the person unaware anything needed their attention — the acceptance criterion is about the conflict being *surfaced*, not merely *not destroyed*.

**Revisit if.** Real usage shows people carving off into a workspace they don't actually control (e.g. a coach fat-fingering someone else's already-populated target) and wants an ownership/confirmation check before writing — that's a different problem (authorization, not merge safety) and would want its own gate, not a repurposed `--merge` flag. Conflict volume from carve-off specifically turns out to be high enough that generic `wingman profile resolve` one-at-a-time doesn't scale for a single carve-off event — that's the trigger for a carve-off-scoped bulk-resolve view (RFC-027's own "Revisit if" already names bulk resolve as a possible future primitive; carve-off would be a consumer of it, not a reason to build a separate one). `export_persona`'s ACTIVE-only, conflict-losers-excluded scope (RFC-049) turns out to matter for merge quality specifically (a losing rival in the coach's workspace might legitimately be the winner once merged against the target's own data) — noted in RFC-049's own "Revisit if" as a Phase-2 question; still open, not resolved by this RFC.
## RFC-053: Google Drive push for backups + digests — device-code OAuth, closed files only

**Decision.** Resolving #151's open question with the narrowest slice that actually needed deciding: the live SQLite workspace stays exactly where RFC-002/RFC-006 put it — local, single-writer, never synced. What changes is that two *already-closed, fully-written* artifacts can now leave the machine on request: a finished `wingman backup` tarball and the digest file `wingman overnight` writes. `docs/SERVER.md`'s own warning ("a live SQLite file does not sync safely through iCloud/Dropbox; a closed tarball does") is exactly why nothing earlier in either pipeline is a candidate — only the file that's already on disk, complete, ever gets pushed. Wiring every other report type (`export_pdf`, `company_dossier`, `pack`, ...) into this is explicit follow-up scope, matching how Coaching Mode and Profile Bootstrap shipped incrementally rather than all-at-once.

Auth is Google's OAuth device-code flow (`infrastructure/gdrive_auth.py`), not the browser-redirect "installed app" flow — lobster is headless, so there's no local browser to catch a redirect. `drive_auth` is dual-surfaced (CLI `wingman drive auth`, MCP tool `drive_auth`) as two stateless calls rather than one long-blocking one: no pending authorization on disk means *start* (calls Google's device-authorization endpoint, stashes `device_code`/expiry in `~/.config/wingman/gdrive-auth-pending.json` — the same small-pointer-file shape as Coaching Mode's `active-persona.json`, `infrastructure/coach_state.py`); a pending authorization on disk means *finish* (one poll against the token endpoint — "still waiting" until approved, then the refresh token lands in `~/.config/wingman/gdrive-credentials.json`, mode 600, and the pending file is removed). This is exactly the shape that lets Trent, who has no SSH access to lobster by design (#167), authorize from his own MCP connector: he sees the code and URL directly in his own Claude chat, approves on his phone, asks again.

Per-account refresh tokens, not a shared one — each Unix account authorizes independently with their own everyday Google login. Isolation is free: `~/.config/wingman/gdrive-credentials.json` is already home-dir-scoped exactly like RFC-046's `secrets.env`/`wingman.env` split, so dhk's token can only ever write to dhk's Drive. Scope is `drive.file` only — this app can see/write only files and folders it created itself, nothing else in anyone's Drive, and the Google Cloud Console project stays in "Testing" publishing status with an explicit allowlist of authorized emails rather than going through full app verification (appropriate for a handful of named users, not a public SaaS).

One shared OAuth client identifies the *app*, not any one server or user — the same reasoning `gh`/`rclone` ship their own public client identifiers. Since no real Google Cloud project exists yet (a manual Console step, explicitly out of scope for an agent), `WINGMAN_GDRIVE_CLIENT_ID`/`WINGMAN_GDRIVE_CLIENT_SECRET` resolve through a small ladder (environment variable, then a `wingman.env` line, then a placeholder compiled into `gdrive_auth.py`) so a real client can be dropped in later without a code change. These landed as `host_config.HOST_SETTINGS` entries, not `keys.py`'s `KNOWN_KEYS` ladder: the value is the same across every account on a box (it names the app), which is exactly what `HOST_SETTINGS` already models (`WINGMAN_REPO`), not what `KNOWN_KEYS`'s per-account-secret Keychain/`secrets.env` ladder is for.

Authorization itself is the explicit opt-in — resolving the explicit-vs-automatic-egress question named but left open in earlier discussion. Before `wingman drive auth` succeeds, every push attempt is a silent, visible no-op (`DrivePushResult(status="skipped")`); once authorized, `wingman backup` and the digest `wingman overnight` writes push automatically, with a `--drive/--no-drive` (`drive: bool` on the MCP tools) override on any single run. The one deliberate action — approving the device code on Google's own consent screen — is the same shape of consent `wingman keys set anthropic` already establishes for model calls: authorize once, and the ongoing use doesn't re-ask.

Failure is always a skip, never a break: `application/gdrive_push.py`'s `push_backup`/`push_digest` never raise — an expired token, a network error, or a Drive API error is logged and returned as `status="failed"`, exactly the shape `application/pipeline.py`'s `pov`/`brief` steps already use for their own graceful degrade. The push call sits in the CLI/MCP orchestration layer (`cli/main.py`'s `backup`/`overnight` commands, `mcp_server.py`'s matching tools), never inside `application/backup.py` or the digest-writing half of `application/focus.py` — both keep their existing "local files only, nothing here touches the network" invariant intact; the network call is a visible, separate step layered on top, not baked into the artifact-writing function itself.

No SDK dependency: `infrastructure/gdrive_auth.py` (device flow + token refresh) and `infrastructure/gdrive.py` (Drive API v3 folder lookup/creation + simple multipart upload) are both plain `urllib.request`, matching `infrastructure/fetch.py` and `providers/embeddings.py`'s existing house style. Upload is capped at 5 MB (Google's own guidance for when simple multipart, rather than resumable, upload is appropriate) — a backup or digest over that fails the push (caught and skipped, never breaking the local file) until resumable upload is built, itself explicit follow-up scope.

**Alternatives.** The browser-redirect "installed app" OAuth flow (rejected outright — lobster is headless, there is no local browser to catch the redirect; this was never actually a contest). A single shared refresh token for every account, rather than per-account authorization (rejected — defeats RFC-046's whole isolation guarantee the moment two accounts' backups could land in the same Drive; per-account tokens cost one extra `drive_auth` per person and buy back the isolation for free via the existing home-dir-scoped file layout). Baking the Drive push directly into `create_backup`/`overnight_run` instead of the CLI/MCP layer (considered — rejected because it would make "local files only" no longer true of those functions' own docstrings, and would make the push harder to skip per-run; the orchestration-layer call site keeps the invariant legible and the override flag simple). A resumable upload from day one (rejected for this slice — meaningfully more code for artifacts that are usually well under 5 MB; the size cap fails loud and skips rather than silently truncating, so nothing is lost by deferring it). Putting the OAuth client id/secret in `KNOWN_KEYS`/`secrets.env` (considered — rejected because that ladder's whole point is per-account secrecy, and a shared, effectively-public app identifier is the opposite shape; `HOST_SETTINGS` already exists for exactly "same value across every account on a box").

**Rationale.** Every design choice here narrows to the same test: does this touch the live workspace, or only a file that was already finished? The device-code flow, the per-account token isolation, the closed-artifacts-only scope, and the CLI/MCP-layer (not application-layer) push call are all the same answer applied in four places — nothing about how `wingman backup` or `wingman overnight` produce their output changed at all, only what optionally happens to the result afterward, and only after an explicit, once-per-account authorization step.

**Revisit if.** A real Google Cloud OAuth client is created in Console — the placeholder `DEFAULT_CLIENT_ID`/`DEFAULT_CLIENT_SECRET` in `gdrive_auth.py` get overridden via `wingman.env` (or the env vars directly) and this becomes end-to-end testable on lobster for the first time; that manual verification is still outstanding as of this writing. A report type beyond backup/digest needs the same treatment (`export_pdf`, `company_dossier`, `pack`, ...) — `application/gdrive_push.py`'s `_push` helper already generalizes; only a new folder-parts constant and a call site are needed, not a new mechanism. Someone hits the 5 MB upload cap in practice — resumable upload is the natural next step, scoped out here deliberately, not overlooked. RFC-048's shared multi-tenant process gains real Drive-push demand — this RFC's per-account isolation is Unix-home-dir-scoped (`Path.home()`), which has no meaning under one shared OS process serving multiple tenants (`jason`/`bob` have no Unix account at all); that combination needs its own design pass before Drive push could be offered there, the same way RFC-048 itself named per-tenant API keys as needing dedicated handling rather than assuming RFC-046's per-account ladder just carried over.

## RFC-055: The relationship proposer — still deferred, tickler-first, revisit triggers made concrete

**Decision.** #117 asked for a design of "the relationship proposer" — a mechanism that suggests a next move for a relationship, citing the objective's own words plus evidence, no confidence score, riding the existing digest-triage consent surface (RFC-031). That constraint set was already settled by RFC-037's own Alternatives section. What #117 left open was the *shape* of the proposer itself, and the issue's own body already recommended not answering that until its prerequisite had been lived with: "build the RFC-037 tickler first, live with it, and only design the proposer if the tickler's event+objective intersection proves too thin." The tickler shipped (RFC-037, PRs #153/#156/#158/#159), and the issue's own most recent comment — the owner, 2026-07-24, after the tickler was live — restates the same posture in more detail: it names the tickler's two honest failure modes (nudging on pure elapsed time with nothing real behind it; staying silent on real activity that happens off wingman's radar and never gets `relationship_log`ged) as the two signals to watch for, and explicitly declines to judge "too thin" from inside a single implementation session, because that judgment needs lived field experience, not a speculative read.

As of this pass (2026-08-10, seventeen days after that comment): still no field signal. No reported instance of a stale-only nudge the user found useless, and no reported instance of real relationship activity the tickler missed.

One thing HAS changed since this entry was first drafted, and it changes the reason rather than the conclusion. RFC-023's usage journal is now enabled for every workspace on the shared host (#299), and `_instrument_tools` records every tool call, so `action_triage` mutes and snoozes against `relationship:{person}` actions are being written down as they happen. Failure mode (a) below is therefore no longer unobservable-in-principle — it is unanswered-so-far, which is a different thing. The journal has been on for hours, not weeks; it has recorded nothing either way yet. So the deferral stands on "the evidence is now being collected and has not spoken" rather than on "there is no way to know", and the first revisit should start by reading the journal instead of waiting for an anecdote. So this RFC does not specify the proposer's shape — doing that now, without evidence, would be exactly the kind of unaudited judgment call RFC-031 and RFC-037's own Alternatives sections were written to keep out of a trust surface, just aimed at the meta-question ("does the tickler need a bigger sibling?") instead of the digest content itself. What this RFC does instead: record the deferral as a durable decision rather than an artifact of drift (the issue's own stated purpose — "this issue exists so that decision is made deliberately, not by drift"), convert the owner's comment's two prose failure modes into checkable revisit conditions, and state precisely what remains undecided so a future revisit does not restart from a blank page.

**What's genuinely undecided, and why it should stay that way for now:**

1. **Run cadence** — every overnight per objective, vs. only when fresh material and an objective coincide. The tickler already answers this for itself (RFC-037: event+objective intersection, not a per-objective overnight sweep), so this question only re-opens at all if a *separate* proposer mechanism is built alongside the tickler — which is the exact thing being deferred here. Answering it now would be designing machinery for a decision (build a separate proposer) that hasn't been made.
2. **Proposal unit** — one suggested move per person per run, or a menu of candidate moves. This needs a concrete case where a single mechanical next-move nudge (today's tickler output) demonstrably under-serves the user — e.g., a relationship where the objective's `next_move` is stale specifically because there are several live options and no way to surface more than one. No such case has been reported. Speculating a menu UI without one risks building a picker nobody asked for.
3. **Whether "expected outcome" survives.** This is the sharpest of the three: RFC-031's rejection (unauditable, provider-drifting) applies most directly here, because "expected outcome" is the one candidate proposer field with no natural evidence citation — a quote from the objective or the log can ground *why to act*, but not *what will happen if you do*. If this RFC is ever revisited and a proposer gets built, the working default should be that this field drops entirely rather than getting reinterpreted as a hedge ("likely," "possible") that still smuggles in a confidence score under a different name. Not decided here as a standing rule, because there is still no proposer for it to attach to — flagged so a future revisit starts from this leaning rather than re-litigating it from zero.

**Alternatives.** Design the proposer's shape now, since the issue was assigned and a design was requested — rejected: the issue's own text and the owner's own follow-up comment both already answered "what should happen with this issue right now" (stay parked, live with the tickler), and producing a speculative shape anyway would override that standing instruction with exactly the kind of ungrounded judgment call this whole RFC family exists to avoid. Close #117 as resolved by the tickler — rejected: the owner's comment explicitly keeps the question open ("I can't answer that from inside a single implementation session... leave this parked exactly as filed"), and closing would discard that reasoning trail along with the issue. Build lightweight telemetry on `relationship:*` action mute/snooze rates now, as a prerequisite for someday judging "too thin" objectively — no longer needed as a separate build: RFC-023's journal now records every tool call in every workspace on the shared host, so the raw material for failure mode (a) accumulates without a relationship-specific capability being invented for it. What remains unbuilt is the *analysis* over that journal, and that stays unbuilt deliberately — writing a query for a signal that has had no time to accumulate would answer nothing, and it is still a general RFC-031 action-analytics concern rather than a slice of the proposer this issue is about.

**Rationale.** The tickler and the proposer occupy the same territory RFC-037's Alternatives already fenced off: a recommender may propose against the user's written thesis with quoted evidence, never rank or forecast by its own judgment. That fence applies just as much to the process of deciding whether more machinery is warranted as it does to the machinery's output — "the tickler seems thin" is itself a judgment call, and making it without lived evidence is the same failure shape RFC-031 was written to prevent, one level up. Eleven days of a low-friction, low-stakes feature living quietly in production is not evidence of anything, in either direction; the honest position is that the prerequisite the issue set for itself has not yet been met.

**Revisit if.** Either of the two concrete failure modes the owner's 2026-07-24 comment already named actually shows up, with a first-hand example, not a schedule: **(a)** stale-only tickler nudges (fired because `TICKLER_STALE_DAYS` elapsed, not because anything happened) accumulate and get muted or snoozed without ever prompting real action — a pattern of "this fired, and it was noise", now readable from the usage journal as well as from memory; or **(b)** real relationship progress happens through a channel wingman doesn't see, goes un-logged, and the user notices in hindsight that the tickler said nothing while the relationship moved — a pattern of "this should have fired, and it didn't." Either signal is the trigger to actually design the proposer's shape (and resolve the three open questions above); a scheduled speculative check-in, or this issue simply having sat open for a while, is not.

## RFC-056: A value axis's sign comes from a per-item direction, not the nomination's pro/con suffix (issue #340)

**Decision.** `prompts/value_axes_v2.md` (replacing v1; `PROMPT_VERSION = "value_axes_v2"`) requires the model, for every `item_id` it cites under an axis, to also state a `direction` — `"supports"` or `"opposes"` — meaning which way that capture cuts **relative to the axis as the model just named it**. `domain.values.AxisDirection` is that enum, carried per span on `ValueAxisEvidence.direction`; `application.values._signed_weight` now takes magnitude from the item's captured `intensity` (unchanged, RFC-050) and its **sign from that direction**. `_polarity(subtype)` — the old sign rule — is deleted. This amends RFC-051 point 4/5 only in where the sign comes from; the `[-1.0, 1.0]` mean, the `_label_for_score` buckets, the evidence traceability, the storage lifecycle, and "the model never produces the number" are all unchanged, so RFC-052's radar chart consumes the same contract it always did.

**The failure this fixes.** The sign was read off whether the item's subtype ended in `_pro` or `_con`. That is a syntactic tell about the interview question that produced the capture, not a semantic one about the axis. The model names axes as VALUES ("Honesty and the right to informed choice"), and a `_con` nomination is a condemnation of somebody who **violated** that value — which is evidence the person **holds** it. On the owner's real workspace this printed "Honesty and the right to informed choice: -1.00, strongly repelled by" and "Accountability for wrongdoing: -1.00, strongly repelled by": the tool asserting, in its most confident band, the exact opposite of the captures it cited. The same defect appears as cancellation rather than inversion when an axis draws on both sides — a strong `_pro` (Pope Francis) and a strong `_con` (Ratzinger) on "Moral courage in defense of the vulnerable" summed to exactly 0.00, "mixed / ambivalent", when one exemplified the value and the other's absence of it disgusted the user. RFC-051 expected near-zero to mean thin or genuinely conflicted evidence; it could also mean unanimous evidence, silently negated.

**Alternatives.** *Invert the rule — treat a `_con` item as supporting the named value.* Rejected: it is the same mistake pointed the other way, and it breaks the moment the model names an axis as a disvalue ("Growth at any human cost"), where a condemnation is genuinely negative evidence. *Constrain the model to name axes only as values the person holds, then apply the inverted rule.* Rejected: it makes correctness depend on prose the code cannot check — a single axis named as a disvalue silently inverts, with nothing to detect it. (The prompt still *prefers* value-shaped names, because it makes the direction judgment easier; correctness no longer rests on that preference being obeyed.) *Let the model emit the signed weight or the score directly.* Rejected by AGENTS.md's "do not use a model for arithmetic", and it would make the number un-auditable — the split kept here is the one this codebase applies everywhere a model touches a number: direction is semantic judgment (model), weighing is arithmetic (code). *Default a missing/unrecognized direction to "supports".* Rejected: a defaulted sign is precisely the bug. An unusable citation is dropped, exactly as an unknown `item_id` already is, and an axis left with no usable citation is rejected with the rest.

**Backward compatibility.** `ValueAxisEvidence.direction` is `AxisDirection | None`, `None` only for a profile stored before this change. A stored `ValueProfile` is read as-is until an explicit `--refresh` (RFC-051's "rebuilt, not versioned" lifecycle), so hard-requiring the field would have made every pre-existing profile unreadable, and silently defaulting it would have kept showing the inverted numbers as if they were current. Instead `render_value_profile` says so: a profile whose evidence carries no direction is rendered with a line naming that its signs may be wrong and pointing at `wingman values --refresh`. Accepted gap: `values_chart`'s SVG carries no such warning, so a chart exported from a pre-RFC-056 profile still draws the inverted shape with only its own staleness note — the rebuild is one command, and adding a second warning band to the chart's fixed geometry was judged not worth it for a one-time migration window.

**Revisit if.** Real runs show the model classifying direction unreliably — e.g. citing an item as "opposes" on an axis where the reasoning plainly supports it — that is the trigger to add a cross-check (a second pass, or a consistency rule between direction and subtype used as a *warning* rather than as the sign), not to go back to inferring the sign from the subtype. Dropped citations become common enough to hollow out real axes (visible as axes rejected for "no usable direction"), that is the trigger to make the direction field's absence a proposal-level parse failure, so a systematically malformed run fails loudly instead of quietly thinning.

## RFC-057: The interview asks what a nomination tells you that you VALUE (issue #343)

**Decision.** Every Values and Mission-alignment nomination gains one more question, asked AFTER the free-text `why` and BEFORE RFC-050's intensity card: **"What does that tell us you value?"** — captured verbatim in the person's own words as `value_statement`, a third optional field on `capture_interview_reaction`/`interview_react`/`wingman interview` (`--value-statement`), persisted directly on `domain.profile.ProfileItem` next to `intensity`/`company_reason`. Scope is `application.interview.VALUE_STATEMENT_SUBTYPES`, *defined as* `SENTIMENT_INTENSITY_SUBTYPES` rather than as a second list of the same six subtypes — `values_pro/con`, `values_fallback_pro/con`, `mission_alignment_pro/con`; never `alignment_of_perspective_*` (a reaction to content, not a nomination) or `network_admired` (a warm-path identifier, not a values signal). It is free text with no enum, so unlike its two neighbours there is nothing to reject: any non-empty answer is the person's own words, and validating or tidying it would be exactly the paraphrasing BP-06's echo-before-save exists to prevent. Enforcement is RFC-050's, unchanged and deliberately: **protocol, in the calling agent's docstring, never a runtime gate** — an omitted statement leaves the field empty rather than blocking the capture, which is also precisely how every capture predating the question reads, so no existing call site, test, or stored item breaks. `persist_items`' equality check compares it alongside `intensity`/`company_reason`, without which re-capturing a nomination purely to ADD the statement it was missing would read as "already captured — nothing changed" and drop the answer — the one retrofit path the twelve existing captures have. Downstream: `application/values.py`'s `_items_block` puts the statement in the inference prompt next to the quote when present, `ValueAxisEvidence` carries it so `render_value_profile` shows it under the evidence line, and `prompts/value_axes_v3.md` (`PROMPT_VERSION` bumped from `value_axes_v2`; output schema untouched) tells the model to judge `direction` against that statement first where one exists.

**The failure this removes.** A nomination records a verdict about somebody ELSE. Half of the Values and Mission-alignment sections are condemnations by design, and a condemnation reaches the profile only as an inference about its target: `values_con: David Duncan` yields a judgment of Duncan and nothing about the person answering. RFC-056 then asks a model, per citation, which way that verdict cuts relative to an axis it just named — a judgment made at the wrong time, by the wrong party, from evidence that was never asked the question. Asking the person directly turns the same capture into *"I value people having the information they need to choose"*: a statement that is **positive by construction**, so the axis is inferred from the person's own articulation of the value rather than from a model's reading of who they dislike. That is what evidence-before-assertion asks for everywhere else in this codebase, and this was the one place a model was trusted to say what somebody meant. The owner produced exactly this shape unprompted, for one nomination out of twelve; the interview simply never asked for it, so the other eleven do not have one.

**Alternatives.** *Replace RFC-056's `direction` with the sign falling out of the value statement.* Rejected, and this is the load-bearing call: eleven of twelve existing captures have no statement, and a field the interview only started asking for cannot be the only thing the sign rests on — inference has to keep working for captures that predate it, so `direction` stays for every citation and the statement makes that judgment better-informed rather than unnecessary. *Derive the value statement from the `why` with a model, retrofitting the eleven.* Rejected: that is the same model judgment on the same inadequate evidence, one step earlier, and it would launder a derived sentence into a field whose entire worth is that it is the person's own words. *Hard-require it for the six subtypes.* Rejected on RFC-050's own reasoning — it breaks every existing call site for no behavioural gain over a docstring protocol that already governs con-then-pro ordering, ask-#2-first, and echo-before-save. *Preset options, or an illustrative example in the question.* Rejected outright (BP-03: options for structure, prose for substance) — a model naming the value and the person agreeing is precisely the inference this field exists to replace. *Store it in the inbox note only, like `primary_purpose`.* Rejected for the reason RFC-050 rejected it for `company_reason`: the inference pass needs a field to read, not prose to re-parse. *Keep `PROMPT_VERSION` at `value_axes_v2`.* Rejected: the prompt text changed, and `ValueProfile.prompt_version` is provenance — a stored profile must name the prompt that actually produced it.

**Costs, plainly.** One more question per nomination: the Values and Mission-alignment sections go from four steps to five, and interview drop-off is the thing to watch. The question is harder than it looks — "what does that tell us you value?" invites a restatement of the `why` — so the protocol specifies one re-ask, pointed at the person rather than the nominee ("and what does that say about what YOU value?"), and never a third attempt (BP-08: an empty answer is a valid answer). No retrofit: existing captures have no statement, and the only way to add one is to re-capture the nomination, which the equality-check change above makes register as a real update.

**Revisit if.** Real answers keep restating the verdict even after the one re-ask — that is the trigger to change the question's *wording* (and to measure which wording works), not to have a model rewrite the answer. Statements land reliably enough across a full set of captures that `direction` is doing no work on any of them — that is the trigger to reconsider where the sign comes from, and only then, with the pre-#343 captures already migrated or aged out. Drop-off measurably worsens at this question — that is the trigger to scope it to the `_con` subtypes only, where the verdict-to-value gap is widest, rather than to drop it.

## RFC-058: The commentary corpus — the assistant's reading of your material, in a store no evidence path can reach (issue #339)

**Decision.** A new store, `commentary_entries`, holds the assistant's readings OF the user's own material — "your three con nominations are one claim, not three" — with authorship recorded structurally on every entry: `author_model`, `prompt_version` (literally `"none"` when a conversation rather than a versioned prompt produced it), `created_at`, and `drawn_from`, a list of workspace ids the reading was drawn from, resolved and frozen to a label at save time. `domain/commentary.py` defines `CommentaryEntry`/`CommentaryReference`, `application/commentary.py` the save/list/find/show/remove use cases, and both surfaces ship per RFC-008: the `commentary` MCP tool and `wingman commentary {save,list,find,show,remove}`. Nothing else in the codebase reads the table. POV stances, `my_pov`, outreach briefs, fit briefs, `evidence`, workspace `search`, `career.md`/`career.json` and the profile page are unchanged and cannot see it — proven per path in `tests/unit/test_commentary_isolation.py`, which asserts the reading's text appears in neither the output nor the PROMPT each of those paths handed its model.

**The failure this prevents.** Every existing capture surface is deliberately evidence-shaped: `interview_react` stores the user's words, `qa_capture` their answers, `corpus add` their writing. Routing an assistant synthesis through any of them files the MODEL's words as the USER's evidence, and every downstream artifact — POV cards, outreach briefs, fit assessments — cites those stores as things the person said. One saved reading would therefore surface later as a quoted claim of the user's, in a document written to be shown to other people. That is precisely what evidence-before-assertion exists to prevent, and it is silent: nothing about a contaminated card looks wrong. So the reading had nowhere to go and died with the conversation, which is where it is least useful — "people are often struck by what Wingman shows up," and that reaction was unrecoverable.

**Alternatives.** *A new `ProfileItemKind`* — rejected, and this is the load-bearing rejection. Every existing filter over `list_profile_items()` (assess, completeness, pack, career rendering, export, values, interview, persona carve-off, profile management, the web UI — a dozen modules today) would have to learn to exclude the new kind, and the one that forgets contaminates silently. A separate table fails closed: code that does not name `commentary_entries` cannot read from it, so future call sites are safe by default rather than by vigilance. *Writing it into the corpus with a disclaimer* — rejected: `corpus add` is the user's own writing and feeds `my_pov`, and a disclaimer in the prose does not stop an embedding from matching it or a quote-extraction pass from lifting a sentence out of it. *Leaving it in the conversation* — the status quo the issue reports. *An FTS5 index over the commentary text* — rejected for now: an `fts` virtual table is the shape most likely to be swept into a generic full-text query by a future contributor pattern-matching on `corpus_fts`/`external_fts`/`answers_fts`, and the store is small enough that a token scan in `find_commentary` is indistinguishable in practice. *A `confirmed: bool` parameter to enforce the echo-before-save gate in code* — rejected: the store cannot tell a confirmed save from an unconfirmed one, so the flag would only teach callers to pass `True`; the gate is a docstring protocol, exactly as BP-06 already is for `interview_react` and `qa_capture` (RFC-049 makes the same call, in the same words, for `intensity`).

**Workspace `search` does not include it.** The issue flagged this as dangerous *if* search results are ever fed back into a generation step. They are: `resolve_requirement` (mcp_server.py) calls `search_workspace` and its documented protocol then tells the calling model to offer the recalled material as the starting point for an answer and to persist it with `qa_capture` — which writes a profile item, citable evidence. A commentary hit arriving in that stream is one accepted suggestion away from being filed as the user's own answer, which is the exact contamination this RFC exists to prevent, reached by a longer route. `find_commentary` is therefore the store's own retrieval. The omission is stated rather than silent: when the store is non-empty, `search_workspace` appends a note saying commentary was not searched, how many entries there are, and which command searches them, so nobody concludes from an empty result that nothing was saved.

**Where it surfaces.** Its own view (`wingman commentary list` / `commentary(action='list')`), plus one line in `wingman status` and the `status` MCP tool naming the store and its count, plus the search note above. Deliberately NOT the Progress page or the profile page: both are evidence surfaces — the profile page renders cited claims, the Progress page reports how filled-in those claims are — and a labelled commentary block there is one screenshot, one scroll, or one copy-paste away from reading as the user's own claim, which is the failure this whole RFC is built to make structurally impossible. Revisit if the store grows past the point where a flat listing is usable; the answer then is its own web view, not a section on an evidence page.

**Storage shape and migration.** A new table in `_SCHEMA`, `entry_id`/`payload`/`created_at`, the same payload-JSON shape as `heap_items` and `answers`. No migration step is needed or added: `Storage.__init__` replays the whole `CREATE TABLE IF NOT EXISTS` schema on every open, so an existing workspace gains the table the first time any command touches it. This is the established rule in `infrastructure/storage.py` — `_migrate_document_key` exists only because that change added a COLUMN to a table that already existed, which `IF NOT EXISTS` cannot do. A regression test drops the table and reopens the database to prove the path.

**Citations are validated at save time.** A `drawn_from` id that matches no profile item, corpus document, external document, or banked answer is refused, with the error naming what can be cited. Trade-off, stated plainly: a reading about material the user has not captured cannot cite it, and saving with no references at all is allowed rather than blocked — the alternative (storing unresolvable ids) would leave a reading nobody can check against the material, which is the unauditable assertion this codebase refuses everywhere else. The resolved label is frozen at save time and rendering flags a reference whose target has since been deleted, rather than dropping it silently.

**Revisit if.** A reading needs to be revised rather than deleted-and-resaved (entries are immutable today; `remove` then `save` loses the original date — acceptable while volume is low, wrong once these accumulate). Commentary starts wanting to reference another commentary entry (the reference resolver deliberately does not accept its own ids — a reading of a reading is a different thing and should be argued for on its own). Someone wants commentary in `search` after all — that is only safe once the generation-adjacent consumers of search results are enumerated and each one is shown to distinguish stores, and it should be a separate, opt-in `kind` filter rather than a silent new column. The store grows large enough that a token scan in `find_commentary` is visibly slow — an FTS table is then fine, but keep it out of any shared full-text query path.
## RFC-059: The company deep-dive — same provider as the person deep-dive, two source gates instead of none (issue #350)

**Decision.** `wingman company deep-dive "<name>"` / MCP `company_deep_dive` + `company_deep_dive_save` do one-shot open-web research on an ORGANISATION, keeping #222/RFC-004's `research_websearch` contract exactly — confirm before spending, show everything, store only on a second explicit act — and adding the two things a company dossier needs that a person dossier does not:

1. **Findings, not prose.** The model returns JSON; the unit is a `CompanyFinding` — one claim, on one of three closed dimensions (`market_position`, `values`, `culture`), with the source that supports it. `domain/company.py` makes `source_url` a validated field: a finding without a fetchable `http(s)` URL cannot be *constructed*, so no parser, importer or future caller can store an unsourced claim by forgetting to check. Storage is `company_dossiers`, one row per company, rebuilt not versioned (the `person_dossiers`/POV-card lifecycle), and it renders as a labelled section inside the existing `company_dossier` report — `[inference]` claim, `[fact]` verbatim quote, `[source]` link, the RFC-005 shape the rest of that report already uses.
2. **Two source gates.** At research time a finding survives only if its URL appears in the provider's OWN citation metadata — the deterministic `Sources:` block `OpenRouterProvider` builds from OpenRouter's `annotations` array, never the model's prose. At save time the reviewed text is re-parsed and every finding must still carry a fetchable source. Rejected findings are shown to the user with the reason and are structurally unable to come back in: they render without a source line, so the save parser refuses them.

**Provider: OpenRouter's web plugin, the same one #222 uses. Deliberately no new provider, no new capability class, no new key.** The alternatives were real and were weighed. *A dedicated search API (Exa, Brave, Tavily) plus a separate synthesis call* — rejected: it returns URLs and snippets, so a second model call has to turn them into claims, and the claim-to-URL binding is then model-asserted anyway; the same weakness, at twice the calls, with a new key on the ladder and a second failure mode to explain. *A model with native web search (Anthropic's web-search tool, or an agentic search loop)* — rejected: an agentic loop decides for itself how many searches to run, which breaks both the bounded-cost promise the spend confirmation makes and RFC-009's "one shot, not a crawl". *Fetching each cited page and verifying the quote verbatim* — the strongest gate available, and rejected for this slice, not on principle: it turns one bounded call into N fetches of arbitrary pages, which is a crawl by another name and belongs with #349's approved-page retention rather than here. What decided it was citation quality: OpenRouter returns citations as structured `annotations` (url, title, excerpt) rather than as prose the model formatted, which is exactly what a machine-checkable gate needs, and consistency with the person deep-dive is worth a lot on its own.

**The honest limit, stated rather than papered over.** OpenRouter reports citations **per response, not per claim**. So the gate proves "this URL was really retrieved by the search" — enough to catch the failure that actually matters, a fluent model attaching a plausible URL it never fetched — and it does **not** prove "this URL supports this claim". That binding remains the model's assertion. Three things follow, all of them deliberate: the source is rendered next to every single claim so a human can open it in one click; the findings are shown in full before anything is stored, which is what the approval gate is *for*; and the section is labelled `[inference]` in the dossier, never `[fact]`, except for verbatim quotes. A reader who wants certainty must click. If that proves insufficient in practice, the fix is per-claim verification against the fetched page, not a better prompt.

**Comparability is the point, and it is deliberately not implemented here.** The owner's actual goal is cross-company comparison — "who is similar to whom, in market position and values". That is why the output is dimensioned findings rather than a prose blob: the follow-on is `similarity._company_vectors` gaining a third contributor alongside people's documents and org feeds — embed the concatenated claims of each dimension as a per-company, per-dimension vector, and `company_similar`/`companies_like` rank on it with no new machinery. Not built here, because it needs an answer to a question this slice does not raise: whether a stated-values vector should be comparable with a writing vector at all (a values page is marketing; a blog post is behaviour), or whether the two must stay separate reference sets. Building the ranking before answering that would produce confident numbers over incommensurable inputs.

**Cost is quoted, not gestured at.** The spend warning computes the search fee from the provider's own cap (`DEFAULT_MAX_RESULTS` x `SEARCH_RESULT_PRICE_USD`) rather than restating a number in prose, so it cannot drift from what the call actually does, and it names the three dimensions being searched. "Confirm before spending" is worthless if the confirmation cannot be reasoned about.

**Revisit if.** The retrieval gate rejects legitimate findings often enough to hollow out real dossiers — that is the trigger to look at URL normalisation (shared with #348) before loosening the gate, and only then to consider accepting a citation that merely shares a host with a retrieved page. Per-claim verification becomes cheap because #349 already retains the page — then the quote gate this codebase applies to POV cards becomes available here, and it should be taken. A provider appears that reports citations per claim — that changes the honest-limit paragraph above and is worth switching for. Companies start wanting more than three dimensions — resist: the closed set is what makes two dossiers comparable, and an open one silently ends comparison.
## RFC-060: Retained research pages — an approved page kept as citable prose, opt-in per source (issue #349)

**Decision.** `CompanySource` gains one boolean, `retain`, default OFF. When it is on, a successful `company research` fetch additionally keeps the page's prose as an `ExternalDocument` attributed to the company's anchor person (RFC-029's `__company__{key}`, `organization` set) — the same shape a company feed post already has, so `company_pov`, `company_similar`, workspace `search` and `evidence` reach it through the paths they already use, with no new document kind and no new pool. The flag is exposed as `wingman company add-source --retain/--no-retain` and `company_source(action='add', retain=…)`, and it is tri-state on the way in: `None` means "leave retention as it is", so re-running `add` on an already-approved source can never silently switch off a retention the user turned on. Setting it on a source that already exists updates the flag in place rather than forcing a remove-and-re-add, which would throw away the snapshot every RFC-015 diff is computed against. Withdrawing a source withdraws its retained text with it.

**The failure this prevents.** A company's values or about page could tell you *that* it changed and never *what it says*. Nothing citable survived the fetch, so `company_pov` refused the company outright — *"nothing in the workspace is attributable to 'X' … fetch some writing first"* — and `company_similar` could only rank the handful of companies that happened to have a feed attached (4 of 19 watched, in the workspace that produced the issue). The available workaround, attaching the company's blog as a feed, works but answers a different question: **what a company publishes as news is not what it publishes as its values.**

**Opt-in per source, not per company and not global.** A careers page whose job list churns weekly would re-store on every run, filling the document pool with near-duplicate boilerplate and crowding a values page out of the 20-document POV budget; an about page changes twice a year and is exactly the thing a stance should quote. Only the user knows which of their approved pages is which, and they already made that judgment once when they named the URL. Default OFF means every existing workspace behaves exactly as it did — proven by a test asserting a non-retained source produces no documents and no source records at all, only the snapshot.

**Egress is unchanged, stated plainly.** Same approved pages, one read-only GET each, already user-consented at add-source time (RFC-015: adding is the approval). No extra request, no crawl, no new destination, no model call. The only thing that changes is what survives the fetch on the user's own disk. The storage cost is likewise bounded by the user's own choice: one archived page per retained source per *changed* fetch.

**Extraction: the snapshot pipeline's text is NOT good enough to quote from, and is not what gets stored.** `extract_page` exists to be hashed, and joins the text of every element with a space. That is invisible to SHA-256 and fatal to a verbatim gate: `<a>North</a>wind` extracts as `North wind`, `<b>rule</b>:` as `rule :`, `optional<sup>1</sup>.` as `optional 1 .`. Whitespace folding (RFC-026) forgives wrapping; it cannot *remove* a space that was never in the page, so a model quoting the sentence a human reads would have its stance rejected as unquotable — the failure mode the issue predicted. Retained bodies are therefore extracted with `application/corpus.extract_document`, the same extractor every feed post already goes through: it honors block boundaries, skips `script`/`style`/`head`/`nav`/`footer` chrome that has no business being quoted as a company value, and passes all eight quote probes in `tests/unit/test_research_retention.py` where the hashing text fails two. Hashing keeps using `extract_page`, so RFC-015's change signal is bit-for-bit what it was. One limitation remains, shared with feeds: a footnote marker glued to a word (`things<sup>1</sup>`) extracts as `things1`, so a quote ending exactly there is rejected — a rejected stance, never a wrong one.

**Versioning reuses RFC-028 lineage rather than accumulating.** The archived page's basename *is* its document key, derived the same way `ingest_resume` derives one, and it is built from the URL alone — `research-{host-and-path-slug}-{url-digest}.html`. Two pages can never collide, and renaming a company (which re-keys its sources) cannot orphan the lineage and start piling up copies. On a re-fetch whose visible text changed, the new version is stored and `record_ids_for_document` drives deletion of the previous version's document (and its FTS row and embedding) — the source records themselves stay, insert-only, as provenance. An unchanged page is not re-stored at all; the "did it change" answer RFC-015 already computes is what decides, so a retained source costs nothing on a run where nothing happened.

**Alternatives.** *Retaining every approved source* — churn on exactly the pages that change most, for the least quotable content. *A new document kind for research pages* — every consumer (POV pools, similarity, search, dossier) would need to learn about it, and the one that forgets is a silent gap; org-attribution through the anchor makes the existing consumers work untouched. *Storing the hashing text and loosening the verbatim gate to fuzzy matching* — rejected outright: the gate is the fabrication guard, and widening it to accommodate a lossy extractor trades a fixable extraction problem for an unfixable evidence problem. *Snapshot generations as a document archive* — RFC-015 deliberately keeps one snapshot per source; lineage gives "newest version wins" without inventing a history nobody asked for. *Stamping `published_at` with the fetch time* so retained pages sort into the newest-first budget — that is an invented fact (a fetch says when we looked, never when the page was written); retained documents are honestly undated, and the cost is stated below.

**Trade-offs.** Undated documents sort last in the 20-document POV budget, so at a company with twenty-plus recent feed posts a retained values page may not reach the prompt — the companies this feature exists for are precisely the ones with no feed, and inventing a date to fix ordering is not a trade worth making. Retained pages also enter `search` and `evidence`, so a marketing page's language becomes quotable material; the quote is always attributed to the company's own page, which is what it is.

**Revisit if.** `company follow`'s conventional-path probe should default `/about` to retained (it is the one probed path whose content is durable — deliberately left OFF here so following a company never silently starts storing pages). Retained pages need selection within the POV budget rather than pure recency (per-source quotas — the same pressure RFC-016 already flagged). Users want the older versions of a retained page readable rather than only superseded (that is a real archive, and RFC-015's revisit trigger, not this one).

## RFC-061: Wingman records where an artifact was published; it never publishes one

**Decision.** A `published_artifacts` table, one row per `ARTIFACT_KINDS` member (`values_radar`, `completeness`, `profile`), holding the url a Claude client published that view at, plus an optional title and an opaque `built_from` fingerprint. Surfaced as the `artifacts` MCP tool (`list`/`remember`/`show`/`forget`) and `wingman artifacts list|remember|forget` (RFC-008 parity). Wingman does not publish, update or fetch the page; it stores the url and says so in every surface.

**Why store a url at all.** Updating an artifact in place requires knowing its url — a conversation that did not publish it mints a *new* page instead. So without somewhere durable to keep it, every regeneration leaves another orphan and the person accumulates a graveyard of half-true snapshots, each looking as authoritative as the last. It is also the only way a SCHEDULED conversation, which by definition never published the original, can refresh the canonical page rather than adding to the pile. This is the enabling half of #355: staleness cannot be managed for something you cannot address.

**Why wingman cannot do the publishing.** MCP is one-directional — the host exposes tools to the model, and a server has no route back into the client to create or update a page. That is a protocol fact, not a gap to be closed later, so the docstrings state it rather than leaving callers to discover it. The division is: the client publishes and owns the page; wingman owns the workspace and remembers the address.

**Replace, not append.** One current page per kind. A list of former urls is a list of pages that are now wrong, and "update my progress page" has to resolve without asking which one — the same semantics the client itself applies when republishing to a stored url.

**A closed kind set.** Each kind must be regenerable on demand, because an update is only meaningful if the view can be rebuilt. An artifact nothing can rebuild is a dead end rather than a record, so arbitrary kinds are refused rather than stored hopefully.

**What this deliberately does not do.** It makes no claim about whether a recorded page is still true. `built_from` is stored opaquely and never interpreted here: the moment this module reads it, it owns a second opinion about staleness that can drift from the producing view's own. Every listing prints the publication date and says plainly that these are snapshots, because a bare url reads as current.

**The trust boundary, stated.** Publishing sends workspace content — a career profile, named people, verbatim quotes — to claude.ai, which is a departure from RFC-002/006's local-first posture and from what `WALKTHROUGH-HOSTED.md` promises tenants. Artifacts also belong to the Claude account that published them, not to the wingman tenant, so an operator publishing on a tenant's behalf puts that tenant's data in the operator's own gallery. Recording a url does not itself move any data, but this table exists to make publishing routine, so the boundary is named here rather than discovered later.

**Alternatives.** Storing a history of urls per kind (rejected — every entry but the newest is a page that is now wrong, and nothing would ever prune it). Inferring the url from a naming convention (rejected — the client mints it; there is nothing to infer). Having wingman fetch the published page to check it is current (rejected — outbound fetching of a third-party page for verification is RFC-009 territory, and the page is a rendering of data wingman already holds, so asking it is the long way round).

**Revisit if.** Client capabilities change such that an artifact can call back for fresh data, in which case "keep it up to date" stops meaning "republish" and this table's role narrows. Or the kind set stops being enumerable — if arbitrary views become publishable, `kind` becomes a name rather than a contract and the regenerability guarantee goes with it.
